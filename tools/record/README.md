# Session recorder (R.1–R.3)

`tools/record` records a scenario in a temporary project, anonymizes all captured data, verifies it, and publishes it under:

```text
fixtures/sessions/<runtime>/<engine-version>/<surface>/<os>/<scenario>/
```

The OS comes from the recording process: `macos`, `linux`, or `windows`. WSL produces a Linux recording. Version and surface come from the scenario; the recorder does not certify runtime support or update the support matrix.

Build with `pnpm build`. The command accepts an ES module exporting `options` and an asynchronous `run(session)` function:

```sh
node tools/record/dist/main.js record /absolute/path/scenario.mjs
node tools/record/dist/main.js verify fixtures/sessions/claude/VERSION/claude_cli/macos/SCENARIO
```

The module has the same API as `recordSession(options, run)` from `@aang/record`. `options` contains:

| Field | Meaning |
| --- | --- |
| `runtime` | `claude` or `codex` |
| `engineVersion` | Exact engine version, used as a directory segment |
| `appVersion` | Optional Desktop or SDK version |
| `surface` | A surface from the shared contract, matching the runtime |
| `scenario` | Portable directory name |
| `model` | Optional `stub` (scripted local model endpoint) or `live` (real model); stored in the manifest, `null` when absent |
| `expectedFacts` | Nonempty list of expected key facts for the contract run |
| `fixturesRoot` | Destination root, normally `fixtures/sessions` |
| `hookBinary` | Path to the built native `aang-hook` binary; a missing, non-file, or non-executable path is rejected before the scenario runs |
| `codexHome` | `isolated` (default) or `regular`, see below |

The session exposes `os` and the paths `project`, `home`, `claude`, `codex`, `spool`, `plugin`, `hook` (the binary), `work` (scratch space that is never captured), and `otlp`. A scenario may prepare files in these directories, then await `session.run(absoluteExecutable, args, { env, timeoutMs })`, which resolves to the command's `stdout` and `stderr`. Commands run sequentially in the temporary project, without a shell, with temporary `HOME`, `USERPROFILE`, `CLAUDE_CONFIG_DIR`, and `CODEX_HOME`, plus the per-command `env`. Use the native executable or `node` plus a script for npm wrappers on Windows. Existing authorization files are never copied. Environment credentials are inherited.

Claude commands receive `--plugin-dir` for the temporary plugin generated by `@aang/hook`; its hook has the standard exec-form arguments and two-second timeout. The temporary spool has a 24-hour lease. Codex scenarios register the same binary in the temporary `CODEX_HOME`; `AANG_RECORD_HOOK` and `AANG_RECORD_SPOOL` name the binary and spool for hosts.

`codexHome: 'regular'` exists only for the live Codex scenario of ADR-0010: the real model, the owner's regular Codex home (`CODEX_HOME` or `~/.codex`, passed to commands as an absolute `CODEX_HOME`), the real `HOME`, `--ignore-user-config`, and no hooks. Nothing is copied out of that home. Rollouts that already existed are never read; a new rollout is captured only when its first line is `session_meta` whose `cwd` is the temporary project, so concurrent sessions of the owner stay out of the recording. The real home and Codex home are anonymized like the temporary ones.

`otlp` is an OTLP/HTTP logs endpoint (`http://127.0.0.1:<port>/v1/logs`). Each JSON export becomes an `otlp` playback step with its receipt time; a non-JSON or malformed export aborts publication, because the player replays JSON.

Commands use the existing process runner from `@aang/observer`, including process groups on Unix and the hook binary's Job Object launcher on Windows. Each command has a five-minute timeout unless `timeoutMs` is given, and a 16 MiB output limit. A failed command or scenario aborts publication; the error ends with the tail of the command's stderr. Failure also stops outstanding commands before temporary-file cleanup.

## Capture and control events

The recorder scans during commands every 25 ms and at command boundaries and explicit checkpoints. It captures:

- Claude `projects`, `teams`, `tasks`, and session-registry JSON/JSONL files;
- Codex `sessions` and `archived_sessions` JSON/JSONL files;
- JSON/JSONL artifacts under the temporary project;
- complete raw spool files and their replayable payloads;
- OTLP JSON logs exports received on `session.otlp`;
- command stdout and stderr, separately.

Auth files, runtime configuration, databases, and arbitrary files outside these source directories are not collected. Symbolic links are rejected. Complete JSONL lines become append steps; changed JSON files and truncated JSONL become snapshots. Removals become remove steps. The final scan rejects unfinished JSON/JSONL. A move appears as removal plus a write at its new path. Intermediate states that appear and disappear between scans cannot be recovered; use separate awaited commands or checkpoints for transitions that must be retained.

`session.checkpoint(label, target, expectedMapChange)` selects the latest captured event for a file or a matching hook; `occurrence: 'first'` selects the earliest one instead, and a file target with `contains` only matches steps whose content includes that text. File targets use the player's relative paths, for example:

```js
await session.checkpoint(
  'artifact-ready',
  { root: 'home', path: 'project/result.json' },
  'The completed stage has result.json as its output',
)

await session.checkpoint(
  'tool-finished',
  { hook: { event: 'PostToolUse', toolUseId: 'known-tool-id' } },
  'The action is completed and its result is visible',
)
```

Hook selectors also accept `sessionId`. Labels must be unique and each selected step may have one label. Checkpoints are added after awaiting the command. Expected map changes are descriptions for an annotator, as permitted by ADR-0007. Hook control events use the spool file's receipt time; file events use the time the recorder first observed the content.

`manifest.json` stores versions, OS, recording time, expected facts, control events, and artifacts with `observed_at` and original nanosecond `mtime_ns`. `playback.json` uses the existing strict `PlayerManifest`, so it can be passed directly to `loadManifest` and `createPlayer`. The metadata wrapper does not change the shared contract or player format.

## Anonymization

Anonymization runs after capture and before anything is published. A shared mapping across every artifact discovers account, organization, user, and installation IDs, including nested serialized JSON and OTLP attributes. It replaces their references consistently, masks email addresses, home paths on macOS/Linux/Windows, and `%USERPROFILE%`, and normalizes the temporary project and profile paths. Home paths are also recognized inside escaped JSON embedded in text (`\/`, `\\`, `\u002f`, `\u005c`). Identity fields and identity OTLP attributes are masked whatever their length or type; an OTLP `intValue` identity becomes a `stringValue` placeholder. Every other JSON string equal to a discovered ID is replaced too, whatever its length, while numeric counters such as usage are kept. In free text, identity assignments such as `account_id: value` are masked whatever their length; other occurrences are replaced as substrings only for IDs of at least four characters that are not purely numeric. Session, thread, action, and event IDs are preserved. JSON documents and embedded JSON that contain nothing private are kept byte for byte, and string scalars are never reinterpreted as numbers, so nanosecond timestamps and long numeric IDs stay exact. JSON with a repeated key in the same object, including embedded JSON, is rejected by recording and verification: parsing keeps only the last value, so earlier values could hide private data.

Explicit credentials are masked as well: values of fields named like `access_token`, `refresh_token`, `api_key`, `secret`, `password`, or `authorization` (JSON keys, OTLP attributes, `KEY=value` and `key: value` text), and `Bearer` tokens. A credential value is masked when it has at least eight characters including a digit, or at least 24 characters.

`/root` is masked only before a dot directory such as `/root/.codex`: Codex uses `/root/...` as logical agent paths in fields, OTLP attributes, and message text, and `/root` itself identifies nobody.

Machine identities are replaced only where a value is a machine name as a whole, and never in free text. The recorder registers the host name of the recording machine (`os.hostname()` and `COMPUTERNAME`, each with its first DNS label) as `HOST_n` and the Linux `machine-id` as `MACHINE_n`. Host names found in `host.name`/`hostname` fields, machine ids in `machine_id` fields and the second segment of the Claude session registry `pidDomain` (`win32:<host>`, `linux:<machine-id>:pid:[…]`) are registered too. These fields, including OTLP attributes and JSON nested in strings, have their whole value replaced; `serverName` of the Codex app-server is replaced when it equals a registered name; the platform prefix and the rest of `pidDomain` are kept. Names match in any letter case, and `localhost` is not an identity. Nothing else is rewritten for a machine name: free text, addresses, keys and the values of other fields stay exactly as captured, so record types, roles, tool names, stop reasons, command markers such as `<command-name>` and error prefixes such as `Exit code 1` cannot be corrupted by a host that shares their name.

Instead, verification searches every file of the recording for the host names and machine id of the machine it runs on, in any letter case. A name counts when it is not part of a longer word, so `bob` is found in `Connected to bob`, `bob.local`, `bob-server`, `user_bob` and after an escape such as `\nbob`, but not in `bobsled`. If any is found, recording stops with an error that names the file and the name, and nothing is published: keep the name out of the scenario or give the machine another host name, then record again. A host named like a common word, such as `user`, `data` or `1`, therefore usually stops recording, because such words occur in most recordings. Field checks still run on any machine, so a `host.name`, `hostname`, `machine_id` or `pidDomain` value that is not a placeholder is rejected wherever the recording is verified.

Anonymization does not change the structure of a recording. JSON keys and the `key` of an OTLP attribute get path, ID and credential masking only. All replacements in a text are made in a single pass, so placeholders, canonical paths and home prefixes are never matched again. `manifest.json` holds no captured data (versions, OS, times, artifact references, and the scenario's own expected facts, labels and descriptions), so it is written as built; verification still checks it like any other file. In `playback.json`, target paths are masked like keys and hook `env` values like captured text; step kinds, times, labels, sources, runtimes and registrations are kept. The header line of a raw spool file (`aang-spool/1 <runtime> <registration>`) is kept, while its environment and payload are anonymized.

Home placeholders follow the source path syntax (`/Users/USER`, `/home/USER`, `C:\Users\USER`); other identities use numbered placeholders. The mapping itself is never saved. This is the identity/path anonymization required by R.1 plus explicit credential fields, not a general detector of secrets in arbitrary prose or tool output.

Verification examines every file, including files absent from the manifest, with one mapping discovered across all of them, searches every file for the names of the current machine, checks anonymization and control-event references, and loads the playback sources. Publication uses a staging directory and rename; an existing scenario is refused. Temporary raw data is removed on success and ordinary failures. An external kill or machine crash can leave temporary directories for manual cleanup.

Core tests use synthetic external processes, the actual hook binary, existing format samples, and the actual player. They do not invoke real model CLIs.

## Scenarios (R.2, R.3)

The catalog drives the installed runtimes. Each scenario asserts that its behavior really happened (transcripts, rollouts, hooks, OTel, host summaries) and fails instead of publishing a misleading recording; each sets two or three checkpoints with the expected map change.

```sh
node tools/record/dist/main.js scenarios
node tools/record/dist/main.js scenario claude_cli --model stub --fixtures /tmp/sessions
node tools/record/dist/main.js scenario codex_exec resume-compaction --model live
```

Without names, `scenario` records every scenario of the surface that supports the model (default: the scenario's first) on this OS. `--fixtures` defaults to the repository's `fixtures/sessions`, `--hook` to the built `aang-hook`. Engines come from `--claude`, `--codex`, `--claude-sdk`, `--codex-sdk`, `--claude-desktop`, `--codex-desktop`, then from `AANG_RECORD_CLAUDE`, `AANG_RECORD_CODEX`, `AANG_RECORD_CLAUDE_SDK`, `AANG_RECORD_CODEX_SDK`, `AANG_RECORD_CLAUDE_DESKTOP`, `AANG_RECORD_CODEX_DESKTOP`, then from `PATH` and the default Desktop locations. On Windows only native executables are accepted, not npm `.cmd` shims. SDK options take the package directory or an npm prefix containing it. The engine version names the directory: the CLI's `--version`, the SDK's bundled engine (`appVersion` = SDK version), or the Desktop's bundled engine (`appVersion` = application version).

| Surface | OS | Model | Scenarios |
| --- | --- | --- | --- |
| `claude_cli` | macOS, Linux, Windows | stub, live | `tools`, `subagents`, `resume`, `compaction`, `fork`, `plan`, `approval`, `question`, `interrupt`, `reconnect`, `source-loss` |
| `claude_sdk` | macOS, Linux, Windows | stub, live | the same |
| `claude_desktop` | macOS | stub, live | the same |
| `codex_exec` | macOS, Linux, Windows | stub | `tools`, `subagents`, `fork`, `question`, `plan`, `compaction`, `source-loss`, `reconnect` |
| `codex_exec` | macOS, Linux, Windows | live | `resume-compaction` |
| `codex_tui` | macOS, Linux | stub | `tools`, `approval`, `interrupt` |
| `codex_sdk` | macOS, Linux, Windows | stub | `tools`, `subagents`, `question`, `resume` |
| `codex_desktop` | macOS | stub | `tools`, `approval`, `subagents` |

The model stub is the only replaced boundary. It is a local Anthropic Messages or OpenAI Responses endpoint scripted by markers: a prompt carries `[aang:<key>]`, and the n-th model response after that prompt returns the n-th scripted step for the key (Codex subagents are keyed by their task name). Requests without tools, prompts without a marker, and steps past the script get a plain text reply. In `live` mode the same prompts go to the real model.

Claude:

- `claude_cli` runs `claude -p` in stream-json mode with `--permission-prompt-tool stdio`; a host process sends the turns and answers permission requests, `AskUserQuestion` (with `answers`), `ExitPlanMode` and interrupts through the control protocol, the way SDK and Desktop hosts do. `--permission-mode default` is explicit because `-p` starts in `auto` in 2.1.288.
- `claude_sdk` loads `@anthropic-ai/claude-agent-sdk` from the given package and runs `query()` with its bundled engine, `plugins` for the recording plugin, `canUseTool`, `resume`, `forkSession` and `interrupt()`.
- `claude_desktop` emulates the Desktop: the engine bundled in Claude.app with `CLAUDE_CODE_ENTRYPOINT=claude-desktop`, the SDK environment the application sets, the Desktop flags and `initialize`. It is not a Desktop session; the owner's manual checklist still applies (ADR-0010). Desktop on Windows is not verified in the MVP (ADR-0013).
- Live mode needs `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` in the environment: the temporary `CLAUDE_CONFIG_DIR` has no login and none is copied.

Codex:

- Hook scenarios use a temporary `CODEX_HOME` with the stub provider, OTel logs exported to the recorder, and `aang-hook` registered for all twelve events with tag `user` (POSIX quoting, or the PowerShell form `& '<path>' 'codex' 'user' '<spool>'` on Windows). `exec` and the TUI run with `--dangerously-bypass-hook-trust`, which also keeps the TUI in-process. The SDK and the Desktop engine cannot pass that flag, so their hooks are trusted the way a user does: `hooks/list` of the engine's `app-server`, then `trusted_hash` in the temporary `config.toml`.
- The TUI is driven by `expect` (on `PATH`) in a pseudo-terminal. On Windows the TUI needs a ConPTY host; as allowed by the plan, it is recorded manually by the owner instead.
- `codex_desktop` emulates the Desktop: the engine bundled in ChatGPT.app as `app-server` over stdio with client `codex_desktop` and `CODEX_INTERNAL_ORIGINATOR_OVERRIDE=Codex Desktop`; the host answers approvals.
- `resume-compaction` is the live scenario of ADR-0010: the owner's regular Codex home, `--ignore-user-config --disable hooks`, no hooks and no copied authorization; resume runs with a low `model_auto_compact_token_limit` so a remote compaction happens. It leaves its thread in the owner's history; delete it with `codex delete --force <id>` if unwanted.

`pnpm scenarios` runs the catalog with the stub model as integration tests tagged `runtime` (excluded from `pnpm test`); a surface whose engine is not installed is skipped unless it is listed in `AANG_RECORD_REQUIRE`, and `AANG_RECORD_FIXTURES` keeps the recordings. The `Scenarios` workflow runs it on macOS, Linux and Windows with pinned CLI and SDK versions and uploads the recordings; Desktop surfaces are verified locally on macOS. Recordings for the repository with current versions are R.4.
