# Observer scenarios (T.6)

Observer and chat replies for E2E 1, 3, 4, 5, 7, 8, 15, 17 and rejected replies in the inspector (ADR-0012, H.6), as well as for map E2E 14 (H.5). The fake `claude` and `codex` (F.1, F.4) reply from them the same way as the real CLI: the reply is built from the input and references the ids of facts, stages, agents, actions, attention items and the `model_version` from it.

```ts
import { installFakeClaude, observerScenarios } from '@catacomb/testkit'

const fake = installFakeClaude(directory, observerScenarios['since-last-view'].before)
fake.setScenario(observerScenarios['since-last-view'].after)
```

`setScenario` restarts both reply queues from the first reply; the call log is kept.

An `answer` or `script` reply with a `gate` field (a file path) waits until the file appears and only then replies: this way a test keeps the call open while it changes the run. An existing file does not delay the reply, so a repeat of the same reply on the next call goes out immediately.

## Scripts

A `{ kind: 'script', script }` reply is a function of the contract input (`ObserverInput` or `ChatInput` from S.4a, S.4b) with a typed output. An input that fails the strict schema is a scenario error: the CLI exits with code `fakeCliExitCodes.scenario`. Templates `{ kind: 'answer', output }` with `$input` pointers (F.1) remain for simple replies.

| Script | Protocol | What it does |
| --- | --- | --- |
| `map` | observer | Stage `Main work` (created once and found by title in the snapshot), a nested stage for each subagent and teammate, except service ones, with the agent's participation: the stage is found by the agent's full id in the title, and a type, name or description that arrives later updates this same stage (`stage.update`); the batch's actions go to their agent's stage, the rest to `Main work`; a stage summary for the batch, including the catch-up mode summary; a retelling of the task from the human's first prompt; the task criterion `The goal of the run is reached`. A repeat on the next batch duplicates nothing |
| `map-layout` | observer | `map` with the H.4 map layout. While the run has no subagent or teammate, except service ones, the main agent's actions in the batch, except the `Agent` call (`action_kind: agent`), go to stage `Preparation` under `Main work`: it is created in the first such batch and found by title afterwards; if each of these actions in the batch has an `action_end` — `stage.state` `done` with these facts, basis `interpreted`. Other actions — as in `map`. On a final solver text, stage `Report` is created once under `Main work`: `stage.state` `done` with the evidence of the final texts (basis `claimed`), `stage.depends` on the stage of each delegated agent, and the observer question `Is the report accepted?` on it. A repeat on the next batch duplicates nothing |
| `map-branches` | observer | Once, while the snapshot has no stage `Build`: top-level stages `Build` and `Verify`, under them `Compile` and `Test`; `Test` depends on `Compile` (across branches), `Verify` on its substage `Test`. No actions or participants are assigned. After that — an empty reply |
| `map-nested` | observer | Once, while the snapshot has no stage `Release`: top-level stage `Release`, under it `Bundle`, under `Bundle` — `Sign`; `Bundle` and `Sign` depend on `Release`. No actions or participants are assigned. After that — an empty reply |
| `claimed-done` | observer | `map`, and on a final solver text in the batch — `stage.state` `done` and `criterion.assess` `reported_done` with the evidence of the last final text: basis `claimed` |
| `revision` | observer | `map` with stage `Main work, continued`, which replaces `Main work` once (`stage.replace`); one observer question on the new stage; a card for each final solver text of the batch with the coordinates of the whole text |
| `split` | observer | Stage `Main work, continued`, while it is active, is split once (`stage.split`) into two new stages `Changes` and `Checks` with the same parent and the batch's evidence. Without it, the reply is empty |
| `merge` | observer | Stages `Changes` and `Checks`, while both are active, are merged once (`stage.merge`) into a new stage `Changes and checks` with parent `Changes` and the batch's evidence. Without them, the reply is empty |
| `report` | observer | `map`, and each file version from `batch.artifact_versions` produced by an action of the batch becomes an output (`artifact.link`, `output`) of the stage to which `map` assigns this action: the agent's stage or `Main work`. The evidence is the facts of this action in the batch. A repeated link to the same version in the next batch does not duplicate the link: the model finds the link with the same stage, version and direction |
| `rejected` | observer | Nesting `Main work` into itself (`stage.nest` with the stage's `{ kind: 'existing', id }` in `stage` and `parent`). The daemon's check rejects the whole reply with reason `invariant` (`cycle in stage nesting`), the batch's facts return to `pending`. While `Main work` is not in the snapshot, the script replies like `map` |
| `outline` | observer | `map` and five stages nested in `Main work`: `Collect the sources`, `Draft the answer`, `Check the answer`, `Publish the answer`, `Notify the requester`; each is created once |
| `reshape` | observer | `map`, then once: a new stage `Prepare the answer` into which `Collect the sources` and `Draft the answer` are merged (`stage.merge`), and a dependency of `Publish the answer` on it; a split of `Check the answer` into new `Check the facts` and `Check the wording` (`stage.split`) with a new criterion `The answer is checked` on the first; a rename of `Notify the requester` to `Notify the requester and the team`; a task criterion assessment `partial`. The evidence of each operation is the facts of the current batch, so it differs from the evidence of stage creation |
| `attention` | observer | `map`; top-level stages `Checks` and `Release`, where `Release` depends on `Checks` (`stage.depends` without a version); the observer blocker `The checks wait for a missing secret` on stage `Checks`, on which both stages depend in the attention zone; on a final solver text in the batch — a review request `Review the final result` on `Main work` with the evidence of the final text. Stages and items are found by title and text in the snapshot; a repeat on the next batch does not duplicate them. Each open rule item gets an `attention.priority` `high` recommendation with the batch's evidence. An open rule question without a mark gets `attention.likely_resolved` if the text of a human prompt in the batch contains the question text, case-sensitively; the evidence is these prompts |
| `plan` | observer | A stage for each second-level section (`## `) of file `PLAN.md` written by an action of the batch (`action_start` with `file_path` and `content`): in order, without a parent, with provenance `inferred` and the evidence of the write fact. If the plan text in the batch is truncated, the reply requests the raw record of this fact in `needs`, and the follow-up request reads the sections from it; a section whose line is cut off is not read. A stage that already exists in the snapshot is not duplicated |
| `chat-answer` | chat | A reply "By map version V" with references: the stage, its facts and actions for a stage focus; the snapshot's stages, attention items and the evidence of the latest changes for a run focus. Without material — `insufficient_data` |
| `chat-collapse-reviewers` | chat | A `collapse` rule for agents whose type, name or description contains `review`: by `agent_type` if `review` is in the type, otherwise by agent name (a Codex subagent's type is `default`, and `review` occurs only in the path `/root/<task>`, which the adapter puts into the description). Without reviewers — `insufficient_data` without a rule |
| `chat-old-ground` | chat | The focus stage, or without one — the first top-level stage. While the input has no log of this stage, the reply is only `needs` with the stage log. With the log — a reply with references to the stage and to the first log evidence that is nowhere in the input except the materials (old grounds outside the first input); if there is none — `insufficient_data` with a reference to the stage |

## Observer and chat queues

The observer and the chat call the same CLI (ADR-0008). A call with a `question` field in the input is chat; it takes replies from `chatReplies`; other calls take them from `replies`. The queues have separate counters; the last reply of each repeats. The call log stores `purpose`: `observer` or `chat`.

The M.2–M.3 check is performed by `packages/engine/test/observer-scenarios.test.ts`: the records pass through the real adapters and `engine`, the input is assembled from the store per the contract, and the script's reply is applied through `applyObserverResponse`. All replies except `rejected` are accepted, LLM bases are not `observed`, and every piece of evidence leads to a raw record; `rejected` is rejected with reason `invariant`, and its output names `Main work`. Chat replies are checked against the `ChatOutput` schema and for the references being present in the input. The attention zone order for E2E 15 is read from the run snapshot (`view.zone`): waiting requests first, followed by the blocker with two dependent stages; the recommendation does not change the order.

## Limitations

- The functional check runs on the T.5 samples and on records assembled from the spike samples. E2E 7 and 8 (`e2e/codex.test.ts`) run on the R.4 Codex recordings: E2E 7 on `codex_exec/reconnect` with phases `failing` and `recovered`, E2E 8 on `codex_tui/approval`, `codex_exec/subagents` and `codex_exec/fork`.
- The functional check gets the chat input from `startChat` (K.1) and checks the reply's references through `verifyCitations`. The E2E 17 observer input is assembled by F.7b (`startObserverBatch`); the other scenarios still assemble it themselves per the S.4a contract and leave `batch.artifact_versions` empty.
- `artifact.link` is produced only by `report`, and only for outputs: the versions in the observer input are versions produced by the batch's actions, and read files do not yield versions.
- There is no recommendation in the observer input: the snapshot carries stages, open items and criteria (ADR-0007). So `attention` does not see the previous call's recommendation and repeats `high` on every call; the value does not change and no new items appear.
