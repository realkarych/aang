# Collector

When `createCollector` is created, the `openGaps` parameter accepts saved open gaps. From them the collector restores the search for lost streams (`source_lost`), keeping the key, the details and the detection time of the episode. When the source recovers, it returns the closing of the same gap through `CollectorBatch.gaps`.

On restart the caller passes open gaps through `openGaps`, and saved cursors through `start(cursors)`. If the cursor of a lost stream has already been replaced by the cursor of another stream at the same path, the search still continues by `StreamKey` across all runtime roots. A found stream is reread regardless of `lookback`.

Cursors and gap updates are saved together with the batch being ingested, before it is acknowledged. An example of integration with the real store is `packages/daemon/test/collector-recovery.test.ts`.

`CollectorService.requestAttachment(path, stream)` queues a read of Claude's text output from `persistedOutputPath`. The caller requests attachments after the session's scope has been determined. The path must be absolute and lead into `tool-results` inside the configured `<claude>/projects`; escaping this root through a symbolic link is not allowed.

The attachment arrives through `start()` as a `CollectedRecord` of the `transcript` channel, with the passed stream, a `file` position and the SHA-256 of the source bytes. UTF-8 text is saved in full, including the BOM and line breaks; an empty file is allowed. Binary data, invalid UTF-8, directories and read errors are retried with a delay and, on a prolonged failure, produce `read_failed`. A successful read closes the same gap. `close()` cancels pending retries.

`tool-results` files are read only on request, regardless of extension. Concurrent identical requests are merged; a repeated request after delivery reads the file again. Deduplication by path and hash is done by the regular intake into the store. `ack()` does not delete the source file. The request queue lives in memory: after a restart the caller repeats requests from saved facts that do not yet have a raw snapshot. Open attachment `read_failed` gaps from `openGaps` do not start reads by themselves; a repeated request with the same path and stream continues the saved episode: a new error does not change `detected_at`, a successful read closes the gap. Saving through the real `engine` and access after the source is deleted is checked by `packages/engine/test/attachments.test.ts`.

Runtime roots (`<claude>/projects`, `<claude>/sessions`, `<claude>/teams`, `<codex>/sessions`, `<codex>/archived_sessions`) appear in a fresh profile only with the first session. While a root is missing, the collector keeps a non-recursive fs watch on the nearest existing parent of the root. When the next directory on the path to the root appears in the parent, the watch moves to it. A root that has appeared immediately gets its own watch and a scan, so the files of the first session are read within seconds rather than by the once-a-minute scan (ADR-0004, decision 15). The presence of a root is also checked on every scan: a root that has disappeared is again awaited through its parent. With `collector.fsWatch: false` only the scan remains. Tests are `test/roots.test.ts` and intake through the real daemon in `packages/daemon/test/ingest.test.ts`.

On macOS an fs watch does not start reporting changes at the moment it is opened: libuv starts the FSEvents stream asynchronously, and changes made before it starts are not delivered. A directory created in the first milliseconds after the parent's watch is opened would otherwise be noticed neither by the check nor by the watch, and the first session would wait for the once-a-minute scan. So one second after opening any watch the collector repeats what the watch replaces: a parent watch rechecks the next directory on the path to the root, a root watch requests a scan, a spool watch requests a listing. A daemon with a watch that misses the changes of the first half second (`packages/daemon/test/late-watch.ts`) is checked by `packages/daemon/test/ingest.test.ts`.

The collector finds appended lines of transcripts and rollouts through fs watch, through a full scan of the roots and through a check of active files. Once a second it checks via `stat` the tail files changed in the last 10 minutes and reads their new lines without listing directories. So lines appended through a descriptor the writer keeps open are read within a second even on macOS, where FSEvents does not report such a write. A file with an old `mtime` whose growth or replacement the collector noticed in the last 10 minutes also counts as changed: on Windows the write time of an open file is guaranteed to update only when the descriptor is closed. A file that has been idle for more than 10 minutes returns to the check after a scan or a read on a watch event (ADR-0004, decision 14). Intake of such a rollout by the real daemon is checked by `packages/daemon/test/ingest.test.ts`.

Snapshots of JSON files (the registry, `*.meta.json`, `workflows/*.json`, `teams/*/config.json`) are found by the scan by the fingerprint `(dev, ino, size, mtime)`. File system timestamps are coarse: an NTFS tick (15.6 ms by default), a Linux jiffy, 2 s on FAT. An overwrite of the same size within one tick does not change the fingerprint, and the notification about it may be lost, for example when the `ReadDirectoryChangesW` buffer overflows. So if at the moment of reading the file's `mtime` is younger than two seconds, the fingerprint is not yet trusted: the first scan after `mtime` becomes older than two seconds rereads the file once. Such a read will see any write from the same tick, and a later write will get a different `mtime`. The same content is not delivered again.

The processes of Claude registry files (`<claude>/sessions/<pid>.json`, ADR-0004, decision 13) are checked every `collector.processCheckIntervalMs`, starting from the collector's start. Only a file whose content has already been delivered as a snapshot is checked; the pid is taken from the file name, and a non-numeric name is not checked. Signal 0 with no process (`ESRCH`) means the process has exited; any other answer, including `EPERM`, means it is alive. Then the file is reread: if it is gone, this is a normal Claude exit and there is no record; any other read error goes into the regular snapshot read retry and, on a prolonged failure, becomes a `read_failed` gap, and the exit is found by the next check after a successful read; if the content has changed, a new snapshot is delivered first, and the process is checked again at the next step. Otherwise a record of the `registry` channel is delivered with the position `process_exited` (path, pid, content hash), the file content and the detection time. For a tracked file the record is delivered once, until its content changes. After a restart the same remaining file yields the same position and the same content, so the store does not add a duplicate. The check on real processes killed via SIGKILL is done by `test/session-processes.test.ts` and `packages/daemon/test/session-process.test.ts`.

## Rereading and prune boundaries

`rescan(streams, lookbackDays)` rereads the files of the listed streams from the beginning. With a lookback only files changed within it are reread: this is how `catacomb watch` rereads previously dropped streams (ADR-0004). Without a lookback all files of the streams are reread, as when a lagging file is reread on request from `engine`. Repeated requests for the same stream before processing are merged: a request without a lookback takes precedence, otherwise the larger lookback is used.

`CollectorService.backfill(lookbackDays)` on the next scan of the roots reads from the beginning files without a cursor that were changed within the given lookback. These are the files the general `lookback` missed. The general lookback itself does not change: old files that appeared later are not read.

Prune boundaries (`PruneBoundary`, ADR-0005) are passed at startup through `prunedStreams` and while running through `CollectorService.prune(boundaries)`. For a Claude boundary the daemon computes the prefix hash with the function `prefixHash(path, offset)`, and the collector compares it with the same function.

- Claude: the collector compares the prefix hash up to the boundary offset on any read of a stream file from the beginning (backfill, `rescan`, move, inode change). When continuing from a cursor, too, if the file's dev, inode, size or modification time changed since the last check: this makes an in-place overwrite of the file visible, including while the collector was stopped.
  - Match — reading starts from the boundary offset, and line numbering continues the original one. The cursor is delivered even if there are no new lines.
  - Mismatch or the file is shorter — there are no records, and the cursor is reset to the beginning of the file. A `stream_changed_after_prune` gap is delivered, once per stream; an open gap from `openGaps` is not delivered again. A stopped file is rechecked only when its dev, inode, size or modification time changes.
  - A new boundary for the same stream replaces the previous one, lifts the stop and rereads the stopped files from the beginning. The store deletes the previous gap together with the run, so the collector forgets it.
- Codex: on any read of a stream with a boundary, lines with an ordinal not greater than `last_ordinal` are skipped. A line without an ordinal inherits the last one seen, and before the first one it is skipped.

`CollectorService.paused(work)` runs `work` while the collector is stopped between batches: the current read is finished, the consumer has returned the delivered batch with the next `next()` call, and a new read does not start until `work` ends. Pauses run one at a time. The daemon deletes a run and passes boundaries inside a pause, so a batch read before the boundaries does not get into intake after the deletion.
