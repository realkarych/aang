# Web interface

A React application that the daemon serves as static files from the same origin (ADR-0011). `pnpm build` builds it with Vite into `dist/`; the `aang` package finds the directory via `import.meta.resolve('@aang/web')`, which points to `dist/index.html`. The subpaths `@aang/web/map-graph` and `@aang/web/map-layout` point to the sources of the map modules and are needed only by the package's own tests. The `web` code talks to the daemon only through the API and SSE and imports the response schemas from `contract`.

## Shell (H.1)

- **Sign-in.** The page opens only with the cookie from the one-time `aang open` link (ADR-0003). If any request gets 401 — the token was replaced or the cookie is stale — the application shows the "Signed out" screen with a hint about `aang open`.
- **Address.** The run list is `/`, a run is `/?run=<id>`. The daemon serves `index.html` only at `/`, so the run is passed as a parameter, not as a path.
- **Run list** — `GET /api/runs`: state, goal or start time, attention, freshness, support mode, sessions, agents, last event. An empty list explains the scope: `watch --all`, watched directories, or their absence.
- **Run header.** The title is the run goal `run.goal`, the human's first prompt (ADR-0006), marked "goal from the first prompt". A long goal is collapsed to three lines with a "Show all" button. Below the title is the observer's brief with its basis. Without a goal the brief serves as the title; without both, the runtime and start time. In the list and on the usage page the goal is collapsed to two and three lines respectively.
- **The run page** takes the snapshot `GET /api/runs/:run` and subscribes to `GET /api/stream?run=` with `Last-Event-ID` equal to the snapshot's `change_seq`. The stream is read via `fetch`, not `EventSource`, because the very first request already carries `Last-Event-ID`.
  - The `run`, `facts`, `model` and `attention` events are applied to the snapshot: the summary and the view are replaced, observation objects, plan facts, model entities and attention items are updated by `id`, removed agents are dropped. The position is the `id` of the last event.
  - A broken stream — reconnect from the last position with a pause of 0.25–4 s.
  - `reset` — the snapshot is re-read, the subscription starts from its `change_seq`.
  - A stream 404 — the snapshot is re-read. A snapshot 404 — "Run not found"; the snapshot is re-read once a second, and the page comes back when the run reappears.
  - **Data generation.** Everything the run page reads beyond the snapshot — trace action input, facts, raw records and the inspector's stored versions — is cached in the run feed's generation (`generation.ts`). Only the feed creates a new generation: when the snapshot was re-read in place of the one already shown (after `reset` or a stream 404) or the run disappeared. All caches are replaced along with it, and the inspector starts reading the stage over. The cache does not outlive the run page.
- **Status bar** — a panel of lamps above the content. A lamp lights yellow (attention) or red (failure) and always carries an icon and a label (RFC §5). A lamp with details is a button that expands a list under the panel.

| Lamp | Source | Lit when |
| --- | --- | --- |
| Link | polling `/api/status`, stream state | no connection to the daemon, reconnecting, run not found |
| Observer | the run summary's `observer`; on the list — the status's `observer.backends` or the runs | lagging, catch-up mode, retry, unavailable, disabled |
| Model (run) | `observer.last_success_at` and the fact queue | the model was not built while facts were pending or the observer was down, lag of 30 s or more, pending facts while the observer is down |
| Mode (run) | `support_modes` and the run's sessions | "files only", "hooks only" |
| Hooks | the status's `runtimes` | hooks not active in sessions, not installed, not trusted, double registration |
| Sources | status and run gaps: source lost, read error, unknown layout, change after `prune`; on the list — runs with a lost source | such gaps exist |
| Records | `unknown_records` of the status or of the run's sessions | there are unrecognized records |
| Spool | `spool` and spool gaps of the status | threshold exceeded, stopped by `aang stop`, no lease, files dropped by age |
| Versions | the status's `versions`, if present | versions without full support |
| Not observable | the status's `not_observable`, if present | always |

## View before meaning (H.2)

Only the observer builds stages (ADR-0006). Before its first response and while the LLM is unavailable, the run page shows observation objects and plan facts from the same snapshot and stream, without interpretation.

- **Attention** — a bar under the run header with open items; ordering, marks and history are in section H.3. An item has its kind as an icon and label, the text, the session and agent from the linked question or action, the opening time, and the author ("by aang rule" or "from the observer"). Text longer than four lines is collapsed; the "Show all" button expands it.
- **Sessions and agents** — the run trace:
  - session: short id, runtime surface and version, directory, branch, launches, execution, freshness ("events flowing", "no new events", "source lost", "hooks inactive"), support mode and time of the last event;
  - the agent tree by `parent`: the main agent, subagents and teammates with type and description, service agents with a kind label;
  - the agent's steps in time order: actions (outcome or execution, tool, input) and questions (human decision, kind, text). A decision that aang inferred from subsequent events rather than observed is labeled with its basis ("aang interpretation"), as is a similar action outcome. The question text is shown as one line and expanded in full by the "Show all" button. The last six steps and all running ones are visible; earlier ones expand with a button. Action input — command, path, pattern, URL, or prompt and description — is read lazily from the action's start fact `GET /api/facts/:id`; a failed read is retried no sooner than after 5 s while the step is on screen, or the next time it is opened. Actions inherited by a fork are marked.
- **Solver plan** — `plan_update` facts from newest to oldest: source, session and agent, time, plan text and items with status as icon and label, the mark "record format not verified" for formats without a reference session.

State is everywhere shown by color together with an icon and a label (RFC §5); for a successful action the label is visually hidden and remains for screen readers.

## Attention zone (H.3)

- **Contents and order.** The zone shows the snapshot's `view.zone` items in its order (M.8, ADR-0008): unviewed above viewed, then items on which the runtime is waiting for the human, then by the number of dependent stages, then by age. An item dismissed by the user is not in the zone, even if the mark arrived before the new `view.zone`.
- **Order explanation** — in the item's kind line, as icon and label: "viewed", "awaiting an answer" (`waiting_for_human`), "blocks N stages" (`dependent_stages`, stage names in a tooltip) and "by time opened" if the item is not awaiting a reply and blocks nothing.
- **Marks** — on a separate line, so they do not read as a reason for the order:
  - "likely answered" with its basis — `likely_resolved` from the observer; the item stays open;
  - "session ended" — the session of the item's question or action has ended (`state: ended`); for an item without them, all of the run's sessions;
  - "from a hidden element" — the item is in the `attention` of one of the `view.placements`: its element is hidden, collapsed or below the detail level by a view rule;
  - "recommended: high/medium/low priority" — `priority` from the observer; it does not change the order.
- **Marking and dismissing.** The "Mark as viewed" and "Dismiss" buttons call `POST /api/runs/:run/attention/:item/viewed` and `/dismiss` (G.8). A note under the zone header says these are view actions and the solver receives nothing. The daemon's response (`AttentionView`) is applied to the snapshot immediately, so the item changes even with a broken stream; the next `run` event updates the order. After a dismissal, a message appears under the header saying the item is kept in the history, and focus moves to it. A request error stays at the item; 401 leads to the "Signed out" screen.
- **History** — the "History: N items" button under the zone expands closed and dismissed items, newest first: kind, text, outcome ("dismissed by the user", "answered", "decision made", "check passed", "resolved", "wait ended without an answer") and dismissal or closing time.

## Stage map (H.4)

The "Stage map" section on the run page is built from the snapshot and the stream: stages, model links and observation objects. The map code (`stage-map.tsx`, React Flow and ELK) is loaded as a separate chunk, only when the run has stages. Before the observer's first response the section explains that the observer builds the stages.

- **Stages.** The map shows only active stages (`lifecycle: active`). If a parent was replaced, merged or split, the stage hangs on the nearest active ancestor. Stage cards are the same size: name, three axes, origin ("from the plan" or "inferred by aang"), number of substages and actions, participants. Each axis is a line with an icon and a label; color only complements them (RFC §5):
  - execution — the stage's state;
  - the basis of that state — an observed event, a solver claim or an aang interpretation; for an interpretation the tooltip has the rule or the observer call;
  - the human decision.
- **Nesting.** An expanded stage is a frame: its card on the left, substages on the right. A collapsed stage with substages is a "stacked" card. The arrow button next to the name expands and collapses the stage. Top-level stages are expanded by default.
- **Links.** A solid line with an arrow is a result dependency (`dependency`): the stage uses the result of another. A dashed line is time order without a causal link. It connects adjacent stages of one level if one ended before the other began and there is no third between them. A stage's time runs from the start of the first to the end of the last of its actions and delegated participants, including substages; while any of them is running, the stage has no end. A stage whose start and end coincide takes its place in this order like the others; two such stages at the very same moment are not ordered. No dashed line is drawn between stages with a dependency. A link to a hidden substage moves to its collapsed ancestor; there is no line only when both of its ends are collapsed into one card. A dependency of an expanded stage on its own substage, or of a substage on it, goes to the stage's card inside the frame; links with stages outside go to the frame.
- **Layout.** ELK `layered`: time flows left to right; on a narrow screen (up to 760 px), top to bottom. Each nesting level is laid out separately (see "Stable layout"). The card of an expanded stage is a separate ELK node in the first layer of its frame, so lines route around it the same way as around the other cards. Substages are held behind the card by ELK service edges that are not drawn: from the card to each substage that is preceded inside the frame by neither the card nor another substage, and to each substage on a cycle of links between the frame's substages (dependency against time order). If ELK cannot lay out the map with this constraint, the map is laid out without it and without service edges: the card may land in the same layer as the substages, but the whole map is visible. A line between stages of different levels passes through ports on the frame borders: ELK routes its segment inside each frame up to the port and between frames at the common level, and the map joins the segments into one line. Until the user has panned or zoomed the map, it fits entirely after every update and resize; the "Fit the map" button restores this behavior. A click on the map without movement does not pan it.
- **Stable ids.** A map node's `data-id` is the stage id from the API. A line's is `dependency:<from>:<to>` or `order:<from>:<to>` by the ids of the shown stages.
- **Node sizes.** A node gets its size and connection points from the ELK layout (`measured`, `handles`), so React Flow draws lines without measuring the DOM. Nodes are rebuilt on every new `view` from the stream; without ready sizes React Flow reset the measurement on every node replacement, and a node replaced before the redraw after measurement was left without connection points, and its lines were not drawn.

## Updates and selection (H.5)

ADR-0008, "Map on updates": a new model version does not reset the selected stage or the reading position, the selection moves to the successor, the layout is not rebuilt wholesale.

- **Selection.** A click on a card, or Enter and Space on its name, selects the stage and opens the inspector (H.6) for it; a repeat deselects and closes the inspector. The name is a button with `aria-pressed`; the selected card has a solid outline. If the selected stage is hidden inside a collapsed one, a dashed outline is on the collapsed ancestor. There is one selection per page — the `stage` parameter of the run address, `/?run=<id>&stage=<id>` (`route.ts`): a user selection adds a history entry (`selectStage`), moving to a successor replaces the current one (`replaceStage`). So the selection survives a page reload and a snapshot re-read, and the map and the inspector show the same stage: a link in the inspector, "Close", Escape and going back in history also change the highlight on the map. A stage from the address that is not in the snapshot (a stale link, the run was rebuilt) is not highlighted by the map and not removed from the address: the inspector says there is no such stage, and "Close" clears the selection.
- **Updates.** The selection is a stage id, and it is resolved anew on every snapshot, so new model versions do not touch it.
- **Successor.** If the selected stage was replaced, merged or split, the selection moves to the first active successor by the `lifecycle` of the snapshot's stages, including across several revisions. The address is updated, and under the map header, in a `status` live region, the line "Stage "…" was replaced. Selection moved to successor "…"." appears; for a split stage, with the other successors. The line stays until "Hide" or until another stage is selected.
- **Stable layout.** ELK lays out each nesting level separately, with model order (`considerModelOrder` and `forceNodeModelOrder`): nodes already on the map keep their relative order, new ones go after them. Stage order is creation order, and a successor inherits the place of the earliest of its predecessors, so a replaced stage is swapped in the same place. ELK's hierarchical layout (`INCLUDE_CHILDREN`) does not fit this: in ELK 0.12 it reorders substages inside a frame on every addition, and order options on nested graphs crash the layout. That is why a line between different levels is assembled from segments through frame ports rather than routed by ELK across the whole hierarchy at once.
- **Reading position.** The page does not scroll when the map updates. If the user panned or zoomed the map, after a new layout the view shifts so that an anchor card stays at the same spot on the screen: the selected stage if it is at least partially visible, otherwise the card closest to the center. A card the user left partly beyond the edge is not brought back by an update. The anchor when the selection moves is the stage selected before the update: the selection keeps a chain from the user-selected stage to the current successor, and the successor takes the place of the chain link that was on the previous map. So a stage merged from several takes the place of the selected predecessor, not the first of them.
- **Area size.** If the map area changed size (the window became narrower or shorter, the map changed height, the direction changed on a narrow screen) and the anchor card that was visible ended up entirely beyond the edge, the view shifts exactly enough for it to become fully visible with a 16 px margin. Other size changes do not touch the view.
- **Readiness.** The map canvas (`role="application"`) holds `aria-busy="true"` while the shown ELK layout does not match the map view (a new snapshot, expanding or collapsing a stage, a direction change on a narrow screen) or while no view has been set for it yet: fitting or preserving the reading position, including the shift when the new layout changes the area height. `aria-busy="false"` means the nodes and the view belong to the same layout and will not move without a new snapshot, a user action or a window resize. The attribute is computed in the same render where the layout input changes, so right after "Expand" it is already `true`. Before the first view is set, the nodes are hidden (`data-placed="false"`), so the map does not flash at the origin.
## Stage inspector (H.6)

- **Selection.** The inspector is open while a stage is selected in the address: `/?run=<id>&stage=<id>` — the same selection that highlights the stage on the map (H.5). The selection is kept in the address, so it survives a reload and works as a link. The map selects a stage via `selectStage(run, stage)`, inspector links via `stageHref(run, stage)` from `route.ts`; `selectStage(run, null)`, the "Close" button and Escape close the inspector and clear the highlight on the map. If the selected stage was replaced, merged or split, the inspector moves to the successor together with the map selection. From 1100 px the inspector is a column on the right with its own scrolling; on a narrow screen, a sheet over the page. On opening, focus moves to the stage name.
- **Data** — `GET /api/runs/:run/stages/:stage`. The inspector is re-read when the run stream brings a new `change_seq`, no more often than once per 0.4 s; scrolling and expanded blocks are preserved. With a new data generation (see the shell), the stage read, expanded bases, raw records and stored versions start over: nothing from the previous database remains in the inspector. 404 — "This run has no stage …"; after it the stage is read again only on a new `change_seq`, including when the run itself appears. On failure the last state remains with a mark, retry once a second.
- **Header and axes:** name, origin ("inferred by the observer" or "from the solver plan"), replacement, merge or split — from the run snapshot, so the header and the focus on the name survive a generation change; execution, basis and human decision as icon and label. If the observer's claim about execution disagrees with what was observed, the observed state is shown with a contradiction mark; an open failed check gives the mark "Done, but a check failed".
- **Sections:**
  - expected result and summary;
  - stage attention: kind, waiting or resolution, author, "likely answered", recommended priority;
  - criteria: status as icon and label, source and contract, verified commit, for `passed_unversioned` — "version not established" and an informational note about a clean tree, working-tree snapshots (time, reason, HEAD, state under masks). A check-contract criterion applies to the whole run (E.7c) and is shown in the inspector of the stage to which the action of its last check is bound, marked "A whole-run criterion" — the same as the attention item about a failed check. It remains at the run level; if the last check is not bound to any stage, it is not in the inspector;
  - inputs and outputs: path, URL, commit or PR; "saved: …" with the source of the copy, or "reference only" or "hash only". "written by action" — only for a copy from an action payload. For a copy taken by reading a file, the action that wrote to the file is named separately with a note that the copy is not proven to be its result (ADR-0006); for a link and a hash, with no claim about the content. "Open saved version" reads `GET /api/artifact-versions/:id` and shows the text or the reason it is unavailable;
  - time and usage: start, end, active time; the stage's solver tokens and "Not assigned to stages", an output lower bound, cost labeled "at list price; under a subscription it is not a charge";
  - participants and actions: agents, the last eight actions with input, the rest expand;
  - links: "Part of", substages, "Depends on", "Needed by", predecessors and successors; a link selects that stage;
  - bases of the stage, of its execution, of the observer's claims and of the human decision;
  - history by model version: author, version basis, operations with the resulting changes;
  - rejected observer responses: the validation reason, operation number and kind, message.
- **The "basis → fact → raw record" chain.** A claim has a basis (an observed event, a solver claim, or an aang interpretation with a rule or observer call) and a "Grounds: N facts" button. A fact shows kind, speaker, session and agent, time and an excerpt; "Raw record" reads `GET /api/raw/:seq`: file and line or spool file, channel, intake and source time, parse state and payload. Facts not in the inspector response are read via `GET /api/facts/:id`; a fact that disappeared after `reparse` is shown as "Ground unavailable". A long payload and version content are shown as the first 100,000 characters with a "Show all" button.

## Since last view (H.7)

Under the stage map is the run strip: two tabs and a viewed mark (ADR-0008, RFC §5).

- **Tabs.** "Run progress" — sessions, agents and the plan (H.2). "Since last review" — the changes mode; it is kept in the address (`?run=<id>&mode=changes`), so it survives a reload and opens via a link. Tabs switch without a new history entry and keep the selected stage (`&stage=`) with its inspector (H.6), and selecting a stage on the map and inspector links keep the mode. While a mark exists, the mode tab shows the number of changes after it, including when "Run progress" is open.
- **Mark.** Only the "Mark as viewed" button sets it: `POST /api/runs/:run/viewed` with the pair "map version and `change_seq`" of the shown state. In "Run progress" this is the snapshot position: the version is `summary.version` (it is given by the snapshot and the stream's `run` deltas, and a `model` event moves it together with the position); the stored run entity keeps the version of its last change, so `run.version` is not suitable for the mark. In the changes mode it is the `to` of the shown diff: the snapshot may move ahead while the diff is being re-read, and the mark must not hide what is not on screen yet. Until the diff from the current mark has been received, the button is disabled. Opening the page and new events do not move the mark. Next to it are the mark's time and its map version. The mark is for the user only: it does not approve the result and sends nothing to the solver. A write error is shown under the button: the daemon did not respond or refused (with its explanation).
- **Diff.** `GET /api/runs/:run/changes?version=&seq=` from the mark. While a mark exists, the diff is re-read on every shift of the snapshot position, no more than twice a second; an in-flight request is not aborted but is limited to 10 s; a failure or a timeout is retried after 2 s with a mark in the mode, and the last received diff stays on screen. Sections go in order of significance for a returning human; empty ones are not shown:
  - "Questions and requests" — attention items opened and closed after the mark: kind, text, place, author, time and closing outcome;
  - "Revised decisions" — replaced, merged and split stages with successors, and changed criteria (before and after);
  - "Stages" — new and changed stages by their resulting transition: name, execution and human decision "before → after", summary; intermediate states are collapsed;
  - "Solver results" — new final-text cards with stages and a "Show original" button: the source text from `GET /api/facts/:id` with the card's fragment highlighted and the fact's label;
  - "Outputs" — new artifact versions: path, URL or commit, the writing action and place, time, what is stored (a version or only a link);
  - "Solver plan" — new plan facts in the H.2 view;
  - "Agent actions" — a summary of new actions per agent with the number of calls of each tool.
- **Bases.** Items, except the plan and the action summary, have a basis (an observed event, a solver claim or an aang interpretation) and the map journal versions in which the item changed (change numbers in a tooltip). The basis is taken from what the item shows:
  - a replaced, merged or split stage — the basis and evidence of the revision operation itself from the journal: the stage history from `GET /api/runs/:run/stages/:stage`, matched against the diff's changes;
  - a changed stage — the basis of the name and summary, if they are new or changed, of execution, if it is new or changed, and of the human decision, if it appeared; if nothing shown changed (for example, a dependency appeared), the bases of all of the stage's changes from the journal after the mark;
  - a criterion — the basis of its resulting status.

  "Grounds: N records" expands the evidence facts: kind, speaker, time, session and agent, gist and raw record number. The first six are visible, the rest expand separately; a failed read offers a retry.

## Chat and view rules (H.8)

Under the map are the "Chat" and "View rules" sections, side by side on a wide screen (ADR-0008, K.1, K.2).

- **Question.** The "Question" field and the "Ask" button (or Ctrl/Cmd+Enter) send `POST /api/runs/:run/chat`. The question's scope is the stage selected on the map: under the field it says "Question about stage "…"", and the "Ask about the whole run" button clears the stage selection. Without a selection the question is about the whole run. If the question was not sent, the reason is shown under the field, and the text stays in it.
- **History.** The run's messages are read via `GET /api/runs/:run/chat` after every snapshot read, including after `reset`, and are updated by the stream's `chat` events by `id`. Reading the history delays neither the snapshot nor the stream: the map, facts and the attention zone are shown and updated even if the history cannot be read. Until the history is read, the chat shows "Loading chat history…"; on failure, "Chat history not loaded: <reason>. aang keeps retrying."; the request is retried once a second, and messages that arrived via events or were sent in the meantime are visible immediately and merged with the read history. A pending message does not overwrite an already received answer.
- **Answer.** A question has a scope and time. While the observer is answering, "The observer is preparing an answer…" is shown; on a call failure, "No answer: <reason>". An answer has text (without text, "The observer found no answer in the run data."), the marks "not enough data" and "some citations were unconfirmed and removed", links and the label "as of map version V". If the model has changed since, the label adds "the map has since been updated to version N".
- **Links.**
  - stage — a `?run=…&stage=…` link: a click selects the stage on the map (a replaced stage passes the selection to its successor, H.5) and scrolls to the map; a replaced stage has a mark;
  - attention item — its kind and text; the link leads to the item in the attention zone (`#attention-<id>`), a closed item is marked;
  - action — tool and time; expands into outcome, session and agent, input from the start fact;
  - fact — kind and time; expands into speaker, session and agent, raw record number and text (prompt, message, action input, approval request, question);
  - artifact version — path and how it is stored; expands into the stored content (where it came from, file read time, size and text; for binary, a mark) or into the reason there is no content: only a link is known, only a hash is stored, the commit no longer exists, the content vanished from storage.

  Facts and versions are read lazily via `GET /api/facts/:id` and `GET /api/artifact-versions/:id`: the snapshot does not carry artifact versions. A failed read is retried no sooner than after 5 s.
- **Rule from an answer.** An applied rule — "View rule applied: …"; after undo — "The view rule from this answer was undone."; rejected by the daemon — "View rule not applied: <code>: <explanation>".

**Rule list** — the snapshot's `view.rules`: the action and the selector in words (stages by name), the source ("from chat" or "from the UI"), the number of affected elements, creation time and an "Undo" button (`DELETE /api/runs/:run/view-rules/:id`). A rule leaves the list with a stream `run` event; an undo error is shown under the list. Below, it says that rules change only the view and that service agents are collapsed by default, with the number of such agents.

**Effect of rules** — the snapshot's `view.placements`:

- trace:
  - a hidden agent or action is not shown together with its tree (for an action, the actions of its code cell); under the session header it says how many are hidden;
  - a collapsed agent is a line with the mark "collapsed by a view rule" or "collapsed by default" and tree totals: agents, actions, running, outcomes, tokens, outputs; it has no steps or nested agents;
  - a collapsed action is a step with the mark "collapsed by a view rule" and its tree totals (actions, running, outcomes, outputs) next to the outcome of the action itself; actions inside it are not shown;
  - action detail level — a mark on the step; a level below "all actions" hides the actions inside it, as in the engine;
  - group — agents of one level or steps of one agent under the line "Group "…" · N";
  - agent detail level: "stages only" hides its steps and nested agents, "stages and agents" hides the steps of its whole tree;
  - attention items inside a collapsed agent or action, or below their detail level — "N attention items inside, see the attention zone";
- map:
  - a hidden stage is not shown together with its substages; at the map header — "hidden by view rules: N stages";
  - a collapsed stage is closed, without an expand button, with tree totals instead of origin, substages, actions and participants;
  - group — a dashed frame "Group "…" · N stages" around the group's stages that share one visible parent (`role="group"`, "Stage group "…""). Model nesting is preserved: the frame sits inside the parent's frame; stages of one group under different parents get a frame under each. ELK lays out the frame as one more level; lines across its border go through the frame's ports, as through the frame of an expanded stage;
  - detail level — a label on the card; "stages only" removes participants and the action count from the stage and its substages, "stages and agents" removes the action count.

The attention zone is not subject to rules: questions of hidden and collapsed elements stay in it.

## Usage (H.9)

The usage panel shows the `GET /api/admin/usage` report (U.1, ADR-0009): all runs — `/?view=usage`, one run — `/?view=usage&run=<id>`. The "Usage" link is in the header; on the run page it is the "Usage" fact. The period is chosen with a switch: all time, 24 hours, 7 days or 30 days up to the current moment (`period=day|week|month`); the period start is recomputed on every request. The report is re-read every 5 s.

- **Three journals** — solver, observer and chat — stand side by side and are not summed. Each has tokens (uncached input, cache read, cache write, output), money if the CLI reported it, and a "Per active hour" column if the solver had active hours. The observer shows call latency and map lag (median, p95, maximum), and on the all-runs page also admission checks that do not belong to runs. The chat shows answer latency.
- **Runs** — on the all-runs page: time from first to last activity, active hours and each run's journals for the period; the link leads to the run's usage for the same period.
- **Bound and unbound parts** — the "Solver by stage" table on the run page: exact stage totals by names from the snapshot and the "Not assigned to stages" row.
- **Sessions** — reconciliation of "Counted by aang" with the runtime's cumulative totals, which are not summed with the journals: "Claude Code total" (`cost-state`) for Claude sessions and the Codex "Thread total" for threads without `token_usage_record`. The runtime and surface are taken from the session itself, not from the run: after a session is bound to a run of another runtime, its total and marks remain its own. Under the table: whether the Claude Code total is final, or not yet available because an interactive session writes its total only on exit; for a fork (`fork`), that the total includes inherited history that is not in "Counted by aang"; for a Claude Desktop session, that the usage of the auxiliary summary model is unavailable and it is unknown whether it is included in the Claude Code total (ADR-0009); for a thread total, that the solver journal does not include it. In a report for a period, a label reminds that these totals apply to the whole session or thread.
- **Origin** — the header of a branched run. A confirmed `forked_from` link (a Codex fork or a parent assigned by the user) is named directly: "Forked from run" with a link. A `common_origin` link of a Claude fork does not give a confirmed source: the single candidate is labeled as a guess with a basis — of the visible sessions only it contains the same history, but it too may turn out to be a branch; with several sessions having the same history, their runs are listed and the source is not established. For a Claude fork the header adds that the inherited history is not counted here, and does not claim that its usage is counted elsewhere: the source may not be visible to aang.
- **Lower bounds** — output with `output_lower_bound` is shown as "at least N" with an explanation at the bottom. There too is the money label "at list price; under a subscription it is not a charge".

## Codex: LLM failure, OTel, fork (H.11)

- **Observer failure.** While the observer is unavailable, disabled or waiting for a retry, the run's "Observer" lamp explains that facts and attention items keep coming in, and stages will update after it returns. For an unavailable observer the time of the next attempt is visible: CLI authorization checks after an authorization error, observer probes after a limit and transient failures (ADR-0007). The "Model" lamp lights yellow as soon as facts are waiting for a non-working observer, and the details show the growing age of the oldest of them.
- **Catch-up mode.** The `lagging` state with reason `backlog` is labeled "catching up". If the run has `deferred` facts — beyond the working queue or waiting longer than the threshold — the "Observer" lamp says how many early facts the observer sees only as a summary, and the "Model" lamp says the map takes early facts into account only via the summary, with reduced detail. Whether the observer accepted the summary with these facts, `ObserverRunState` does not report, so the lamp says nothing about completed recovery.
- **Decision from OTel.** A human decision that came from `codex.tool_decision` (`source: User`) is observed: the approval request step shows "approved" without the "aang interpretation" mark, which a decision inferred from subsequent events gets.
- **Branch.** The page of a branched run leads to the source run by its name ("Forked from"), the source run lists its branches ("Forks"), and the branch's row in the list names the source run. Names and links come from `GET /api/runs`, which the run page re-reads every 2 s, as does the list. If the request failed, the run page's "Link" lamp says that branches are not updating, and the page keeps the previous data.
- **Codex subagents.** A Codex subagent thread is named by its name from the rollout, and the type (`agent_type`, the Codex role) is shown next to the agent kind if it differs from the name. The tool name wraps after `/` (`collaboration/spawn_agent`), the full name is in a tooltip. Identical session launches from hooks and files are shown once.

## Limitations of the current version

- The daemon does not yet have `status` events in the stream or a stream without `run` (G.5). So the status and the run list are re-read every 2 s; the client accepts a `status` event, but the status bar is updated by polling.
- The daemon does not yet populate versions and "not observable" modes (G.7). The lamps for them display the data as soon as the daemon provides it.
- Stages and cards in the changes mode come only from the observer; criteria come from the observer and from contract checks. Without the observer the diff consists of rule-based attention items, check criteria, artifact versions, the plan and actions.
- Nesting of Codex code mode actions into an `exec` cell is not expanded: steps go flat in time order.
- The client learns of a database replacement only via a stream `reset` or the run disappearing. The stream position is a change number without database identity, so the daemon sends `reset` only if the client's position is ahead of the journal, before `reparse` or the last `prune`. A database replaced by another whose journal is not shorter than the client's position causes neither a reset nor a new generation.
- E2E does not yet verify expanding artifact version content from a chat answer link: the `GET /api/artifact-versions/:id` route came with the inspector (H.6) after this part.
- Adapters do not yet bind an action to a code mode cell (`container_call` is always `null`), so collapsing, hiding and detail level of a cell affecting the actions inside it do not occur in real data, and E2E verifies them on actions without nested ones.
- The daemon does not yet have a chat call (K.1; chat message storage already exists), nor an HTTP route for bindings. So the usage E2E prepares their traces in the database with the daemon stopped: `observer_calls` records of kind `chat` — like the U.1 integration test, a stage with bound actions — via the engine's `applyChangeSet`, session bindings (`attach`, `fork_parent`) — via `engine.bind`. Observer calls (`batch`, `probe`) are also still written to the database by the E2E itself, although the observer is already connected to the daemon (G.6). With K.1 and the bindings route, these preparations will be replaced by real calls to the fake CLI and the API.
