# Запуск и допуск наблюдателя

F.2, F.5 и F.6: `createClaudeBackend` и `createCodexBackend` возвращают backend с обязательным допуском. После создания вызывающий код запускает `await backend.admit(signal?)`; до успешного результата `execute({ input, signal })` отказывает без передачи рабочего входа CLI. Допуск получает только синтетические данные. Каждый рабочий вызов сначала проверяет версию; смена версии требует нового `admit()`. Нарушение изоляции также отзывает допуск. Новый экземпляр backend всегда начинает без допуска, в том числе после изменения модели, effort или списка встроенных компонентов.

`admission()` возвращает результат с версией, ОС, хешем профиля, временем проверки, причиной отказа и пометкой Claude. Результат атомарно записывается в `admissionStatusPath`, по умолчанию — `~/.aang/support/<runtime>-observer.json`. Файл служит локальным статусом, а не разрешением пропустить проверки при старте. `verifiedClaudeVersions` получает версии с успешным локальным контрактным прогоном на текущей ОС из матрицы поддержки. Без такого результата автоматически допущенный Claude включается с пометкой «изоляция от сообщений других сессий на этой версии не проверена». Проверка с сессией-пиром относится к F.10.

Допуск Claude выполняет два малых вызова с одним синтетическим входом. Во временном проекте независимый SessionStart-hook создаёт метку: с `--setting-sources project` она обязательна, с `--setting-sources ""` запрещена. Во время обоих вызовов проверяется маркер реестра, после — отсутствие транскрипта и файла, который синтетическая инструкция просила создать инструментом. `init` и результат проходят те же проверки, что рабочий ответ. Авторизация остаётся штатной, пользовательские учётные данные не копируются.

Допуск Codex выполняет два вызова на локальной заглушке Responses API во временном `CODEX_HOME`. Заглушка проверяет оба расположения инструментов и получает ответы `unsupported` на `exec`, `spawn_agent`, `request_user_input` и `request_user_input_async`. Контрольные ветки отличаются только `--disable hooks`; обе содержат тестовый `--dangerously-bypass-hook-trust`. Проверяется отсутствие rollout и строк сессий в SQLite. Рабочий вызов не получает ни bypass, ни тестовый провайдер, ни временный `CODEX_HOME`.

`model` задаётся обязательно, `effort` — явно, если задан конфигурацией. `builtins` Claude — разрешённый список из матрицы поддержки; по умолчанию он пуст. Путь CLI разрешается до очистки окружения; можно передать абсолютный исполняемый файл и префикс аргументов для npm-обёртки Codex. Авторизация проверяется перед первым рабочим вызовом и заново после ошибки авторизации. Codex обновляет каталог модели при изменении версии.

`status()` возвращает контрактный `ObserverState` и количество занятых процессов; `subscribe()` сообщает изменения. Результат `execute` содержит `stopped` — обещание, которое выполняется после подтверждённой остановки всех процессов вызова. `process_stuck` удерживает слот и запрещает следующие вызовы и допуск. Позднее подтверждение остановки освобождает слот; потеря Windows-лаунчера без файла статуса требует перезапуска. Состояние, пометка и уведомления предназначены для `/api/status` и SSE в G.4–G.6: подключения наблюдателя в текущем демоне ещё нет. Планирование вызовов описано ниже, восстановление после отказов относится к F.9.

`createClaudeLauncher`, `createCodexLauncher` и `createProcessRunner` — низкоуровневые операции запуска F.2/F.5, из которых собран backend. Они проверяют профиль и завершение дерева, но не выполняют допуск. Рабочие порции и чат должны использовать только `createClaudeBackend` / `createCodexBackend`. Тесты низкоуровневого запуска проверяют эти операции отдельно от тестов допуска.

Все процессы запускаются без shell. На Unix runner завершает группу и ждёт `ESRCH`; на Windows использует абсолютный `windowsLauncher` (`aang-hook.exe`, режим D.9). Закрытие каналов не подтверждает остановку. Проверка длится 10 секунд, затем возвращает `process_stuck` и продолжает ждать. Вывод ограничен 16 MiB. Временные файлы удаляются после подтверждения остановки.

Рабочий каталог — `os.tmpdir()/aang-observer/empty`; `temporaryDirectory` задаёт корень временных файлов. Непустой рабочий каталог и инструкции `CLAUDE.md`/`AGENTS.md` в предках, включая физический путь, запрещают запуск. Допуск создаёт отдельный временный каталог рядом с рабочим.

Тесты используют только CLI из testkit и внешние обёртки процессов. Контрольный hook исполняется отдельным Node-процессом и не зависит от самоисключения `aang-hook`. Зомби проверяет тестовый помощник на C (`cc` на macOS/Linux). Реальные CLI эти тесты не запускают и поддержку реальных версий не объявляют.

## Очередь и запуск порций

`createObserverScheduler({ store, backends, backend?, crossVendor?, clock?, limits? })` запускает порции наблюдателя по статусам интерпретации (F.8). Демон (G.6) вызывает `wake()` после каждого приёма; остальное планируют таймеры и уведомления backend.

- Backend прогона — вендор его корневой сессии, `backend` переопределяет его. Backend в состоянии `disabled` или `unavailable` вызовов не получает; смена его состояния, например успешный `admit()`, снова планирует очередь.
- Вызов запускается, когда в очереди прогона есть срочный факт, набралось `batchFacts` (30) фактов или `batchBytes` (96 000 байт payload, около 24k токенов) либо самый ранний факт ждёт `delayMs` (5 с) с момента наблюдения его записи (`observed_at`). Возраст отсчитывается и для фактов, пришедших во время вызова прогона, поэтому созревшая порция уходит сразу после его окончания.
- Между началами вызовов одного прогона проходит не меньше `intervalMs` (10 с), в том числе для срочного факта. Интервал отсчитывается от последнего начала вызова прогона в `observer_calls`, поэтому выдерживается и после перезапуска. Дозапрос `needs` сам интервала не ждёт, но следующий вызов отсчитывается от его начала.
- Одновременно идёт один вызов на прогон и не больше `concurrency` (2) вызовов наблюдателя. При равной готовности первым идёт прогон с более ранним фактом. Слот освобождается только после `stopped` результата backend: при `process_stuck` порция сразу возвращается в `pending`, а слот прогона и общий слот остаются занятыми до подтверждения остановки.
- `chat(work)` выполняет работу чата в отдельном слоте: по одной за раз и без ожидания вызовов наблюдателя. Работа возвращает результат со `stopped`, и следующая работа чата ждёт подтверждения остановки предыдущей. Backend допускает одновременные рабочие вызовы, а допуск ждёт их завершения (`admission_busy`).
- Ответ применяется через M.2–M.5c. Ответ с `needs` сразу получает один дозапрос в том же слоте, без интервала и без траты попытки. Дозапрос начинается в той же транзакции, где записан ответ с `needs`.
- Перенос сессии (E.5) завершает вызов, порция или вход которого её затрагивают. Ответ backend на такой вызов, успешный или ошибочный, не применяется и не меняет статусы фактов: сохраняется только его расход, а `failure` не срабатывает. Слот вызова занят до подтверждения `stopped`.
- Отклонённый ответ и выход, который backend не прочитал по схеме (`invalid_output`), возвращают порцию в `pending` и тратят попытку. Следующая попытка несёт причины прошлого отказа в `previous_attempt`, в том числе после промежуточной ошибки backend или перезапуска. После `attempts` (3) отказов факты получают `not_interpreted` с пробелом.
- Другие ошибки backend (таймаут, отмена, авторизация, лимит) возвращают порцию в `pending` без траты попытки, вызов записывается с результатом `failed`. Паузы, пробы и состояния `backoff` и `unavailable` по таблице ошибок ADR-0007 относятся к F.9.
- Активная очередь прогона ограничена `queueFacts` (2000) фактами и `queueAgeMs` (24 ч). Факты старше предела и самые старые сверх числа получают `deferred` и открытый пробел `summarized_backlog`. Предел проверяется при каждом планировании, в том числе для прогона с текущим вызовом, и по таймеру ближайшего истечения возраста, даже когда backend недоступен и новых событий нет. Сжатая сводка догоняющего режима относится к F.9.
- Факты сессий другого вендора без `crossVendor` получают `not_interpreted` и пробел `cross_vendor_excluded`.
- При создании планировщик завершает с результатом `failed` вызовы, которые прошлый процесс не закончил. Их порции хранилище при открытии уже вернуло в `pending` без траты попытки.
- `idle()` ждёт завершения текущих вызовов вместе с подтверждением остановки их процессов. `close()` отменяет их, возвращает порции в `pending` без траты попытки и ждёт результатов вызовов и работы чата. Подтверждения остановки дерева, о котором backend сообщил `process_stuck`, `close()` не ждёт: после закрытия новых вызовов нет, а такое дерево может не подтвердить остановку до перезапуска. Ошибка хранилища не роняет процесс, а приходит в `failure`.

Тесты планировщика подают hook-события через настоящие адаптеры и `engine`, вызывают поддельные `claude` и `codex` из testkit и управляют временем через часы теста. Правило зависимостей разрешает тестам `observer` импортировать адаптеры.
