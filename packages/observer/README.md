# Observer launch and admission

F.2, F.5 and F.6: `createClaudeBackend` and `createCodexBackend` return a backend with mandatory admission. After creation, the calling code runs `await backend.admit(signal?)`; until it succeeds, `execute({ input, signal })` refuses without passing the working input to the CLI. Admission receives only synthetic data. Every working call checks the version first; a version change requires a new `admit()`. An isolation violation also revokes admission. A new backend instance always starts without admission, including after a change of the model, effort or the list of built-in components. `cliVersion(signal?)` reports the version of the installed CLI with a single `--version` call, without admission and without contacting the model, and returns `null` if the CLI is missing or the version is not recognized.

An isolation violation — during admission or in a working call — is pinned to the CLI version and the profile (ADR-0007: resumption only through a new admission via the `aang doctor --admit` command or on a CLI version change). `admit()` on the same version and with the same profile refuses with the `isolation` class after one `--version` call, without probes and without model calls. Manual admission is `admit(signal, { manual: true })`; it is called by `aang doctor --admit` (G.12). The `isolationViolated` mark is stored in the status file, so a new backend instance with the same profile is immediately in `disabled: isolation` and does not admit the same version even after a restart. A successful admission or a different CLI version clears the mark. The mark applies to the version the call ran on: if a parallel call has already detected a new version, a late failure of a call on the previous version — an isolation violation or any other — does not change the admission state, and the new version is admitted by the regular automatic admission. A different profile (model, effort, CLI path, built-in components) requires a new automatic admission under ADR-0007, so the mark of the previous profile does not apply to it.

`admission()` returns a result with the version, OS, profile hash, check time, refusal reason, isolation violation mark, admitted built-in plugins and the Claude warning. The result is written atomically to `admissionStatusPath`, by default `~/.aang/support/<runtime>-observer.json`. The file serves as a local status, not as permission to skip checks at startup. `verifiedClaudeVersions` receives the versions with a successful local contract run on the current OS from the support matrix. Without such a result, an automatically admitted Claude is enabled with the warning "isolation from other sessions' messages is not verified on this version". The check with a peer session belongs to F.10.

Claude admission performs two small calls with one synthetic input. In a temporary project, an independent SessionStart hook creates a marker: with `--setting-sources project` it is mandatory, with `--setting-sources ""` it is forbidden. During both calls the registry marker is checked, and afterwards the absence of a transcript and of the file that the synthetic instruction asked to create with a tool. The registry entry `~/.claude/sessions/<pid>.json` lives only while the call is running, so the registry is read every 10 ms by a separate thread (`registry-watch.ts`, `worker_threads`) rather than by the daemon's event loop: a synchronous SQLite commit in the daemon can hold the main thread for more than a second, and an entry created and removed during that time would otherwise go unnoticed. Before each call the thread resets what it has seen; after the call it reads the registry once more and returns the markers found. The requirement does not change: exactly one entry with the call's `cwd` must be seen in each call, and its `entrypoint` is `aang-observer`. An unreadable registry directory and a failure of the thread itself also reject admission with the `isolation` class. `init` and the result go through the same checks as a working response, with two differences. First, admission accepts any built-in plugin (`path: builtin`, source `<name>@builtin`). Second, hook events are allowed only in the positive branch with the control hook. Authorization stays standard; the user's credentials are not copied.

Claude built-in plugins (ADR-0007, decision 9). Every call runs with `--include-hook-events`. In the observer profile, a built-in plugin must not give the model any tools (`tools == ["StructuredOutput"]`), MCP servers (`mcp_servers` is empty) or executable hooks (no `system/hook_*` events in the stream). Otherwise admission refuses with the `isolation` class; a non-built-in plugin also causes a refusal. Built-in plugins from `init` of the negative branch are recorded in the admission result (`builtinPlugins`). A working call on this version accepts only them and the plugins from `builtins`; any other plugin or hook event is an isolation violation.

Codex admission performs two calls against a local Responses API stub in a temporary `CODEX_HOME`. The stub checks both tool locations and receives `unsupported` responses for `exec`, `spawn_agent`, `request_user_input` and `request_user_input_async`. The control branches differ only in `--disable hooks`; both contain the test `--dangerously-bypass-hook-trust`. The absence of a rollout and of session rows in SQLite is checked. A working call gets neither the bypass, nor the test provider, nor the temporary `CODEX_HOME`.

On macOS and Linux, every CLI call in the admission of both backends, including `--version` and `auth status`, is checked for descendants leaving the process group (ADR-0013). From launch until the group is confirmed stopped, and once more after that, the process table is sampled in the background: `/proc` on Linux, `ps` on macOS. A descendant is a process linked to the root by a `ppid` chain, or a process in the root's group, and a seen descendant is tracked even after its parent changes. A descendant with a different group rejects admission: the backend becomes `disabled: isolation`, and the reason lists the process names. The exception is the group of the control hook of both CLIs: Codex runs every command hook in a new session, and Claude Code (verified on 2.1.289 and 2.1.292, macOS) in its own process group. Therefore the hook process remains the leader of its group (for Codex the hook command starts with `exec`; for Claude the hook is set without a shell via `command` and `args`) and writes its `pid` into the marker, and processes of the group with this `pid` are not counted as a violation in calls with the control hook. Each seen descendant group is accounted for separately: a descendant that has been in a foreign group remains a violation even after returning to the hook group. A failure of any snapshot during a call also rejects admission, even if the last snapshot succeeded; a table without the daemon itself and an unreadable `/proc` entry also count as failures, except for a process that has disappeared. A process that the Linux kernel is already releasing while its parent waits on it also counts as disappeared: at that moment `/proc/<pid>/stat` still returns it with the same start time, but without a group and parent (`pgid` −1, `ppid` 0). Such an entry says nothing about the process group and is not counted as leaving the group. The check is a safety net, not process accounting: a descendant that left the group and disappeared or lost its link to the root between snapshots may go unnoticed. Working calls do not perform this check. The Codex profile disables the shell snapshot (`--disable shell_snapshot`): otherwise Codex launches the account's login shell via `setsid()`.

`model` is mandatory; `effort` is set explicitly if the configuration specifies it. Claude `builtins` is an allowlist from the support matrix; it is empty by default. Built-in plugins recorded by admission are added to it. The CLI path is resolved before the environment is cleaned; an absolute executable and an argument prefix for the Codex npm wrapper can be passed. Authorization is checked before the first working call and again after an authorization error. Codex refreshes the model catalog when the version changes.

`status()` returns the contract `ObserverState` and the number of busy processes; `subscribe()` reports changes. The `execute` result contains `stopped` — a promise that resolves after all processes of the call are confirmed stopped. `process_stuck` holds the slot and forbids subsequent calls and admission. A late stop confirmation frees the slot; losing the Windows launcher without a status file requires a restart. The state, the warning and the notifications are intended for `/api/status` and SSE. The daemon assembles the backend and the scheduler in G.6 and exposes their state in `/api/status`, the run summary and SSE (`packages/daemon/README.md`). Call scheduling and failure recovery are described below.

A call error carries a class:

- `auth` — "Not logged in" and similar responses, as well as a failed `auth status` / `login status`;
- `limit` — HTTP 429, a rejected Claude `rate_limit_event`, or text about a limit. The reset time is taken from `resetsAt` of the Claude event or from the ISO time after "resets" / "try again at" and passed in `resetsAt`;
- `network` — HTTP 5xx from Claude, connection errors and a broken stream;
- `timeout` — hard process timeout;
- `invalid_output` — output that could not be read according to the schema.

The CLI error text is appended to the message. `authStatus(signal?)` runs `claude auth status` or `codex login status` with the same launch as a working call and does not contact the model. It is subject to the same restrictions as a working call: without admission, during admission and under `process_stuck` it returns a refusal.

`createClaudeLauncher`, `createCodexLauncher` and `createProcessRunner` are the low-level F.2/F.5 launch operations from which the backend is assembled. They check the profile and tree termination but do not perform admission. Working batches and the chat must use only `createClaudeBackend` / `createCodexBackend`. Low-level launch tests check these operations separately from admission tests.

All processes are launched without a shell. On Unix the runner terminates the group and waits for `ESRCH`; on Windows it uses the absolute `windowsLauncher` (`aang-hook.exe`, mode D.9). Closing the pipes does not confirm a stop. The check lasts 10 seconds, then returns `process_stuck` and keeps waiting. Output is limited to 16 MiB. Temporary files are deleted after the stop is confirmed.

The working directory is `os.tmpdir()/aang-observer/empty`; `temporaryDirectory` sets the root of temporary files. A non-empty working directory and `CLAUDE.md`/`AGENTS.md` instructions in ancestors, including the physical path, forbid the launch. Admission creates a separate temporary directory next to the working one.

Tests use only the CLIs from testkit and external process wrappers. The fake Claude in the `admissionGate` scenario waits for a gate file before writing to the registry; the test creates it and synchronously holds its event loop until the entry appears and disappears — this models a daemon busy with an SQLite commit for the whole lifetime of the entry. The fake CLIs in the `groupEscape` scenario start a descendant outside their group, and the fake `codex` does this even without `--disable shell_snapshot`, like the real one. Both fake CLIs on macOS and Linux run the control hook in a new session, i.e. in its own process group, like the real Codex 0.160.0 and Claude Code 2.1.289 and 2.1.292. A process table snapshot failure is modeled by the test at the OS boundary in its own process: the first read of `/proc` or the launch of `/bin/ps` fails. There, on Linux, the kernel releasing a process is also modeled: a terminated process appears once in the `/proc` listing, and its `stat` is what the kernel returns at that moment. The control hook runs as a separate Node process and does not depend on the self-exclusion of `aang-hook`. A zombie and a descendant returning from a foreign group to the control hook group are checked by C test helpers (`cc` on macOS/Linux); the second one is launched in the hook session through a wrapper that prepends it to the hook command, and for Claude wraps the hook in `/bin/sh -c` with `exec` of the original command. These tests do not run real CLIs and do not declare support for real versions.

## Queue and batch launch

`createObserverScheduler({ store, backends, backend?, crossVendor?, claudeConfigDir?, codexHome?, budgetTokensPerHour?, clock?, limits? })` launches observer batches based on interpretation statuses (F.8). The daemon (G.6) calls `wake()` after every intake; the rest is scheduled by timers and backend notifications.

- The run's backend is the vendor of its root session; `backend` overrides it. A backend in the `disabled` or `unavailable` state receives no calls; in `backoff` it receives them only after the pause; a change of its state, for example a successful `admit()`, schedules the queue again.
- A call starts when the run's queue has an urgent fact, `batchFacts` (30) facts or `batchBytes` (96,000 bytes of payload, about 24k tokens) have accumulated, or the earliest fact has waited `delayMs` (5 s) since its record was observed (`observed_at`). Age is also counted for facts that arrived during a call of the run, so a ripe batch goes out immediately after that call ends.
- At least `intervalMs` (10 s) passes between the starts of calls of one run, including for an urgent fact. The interval is counted from the last call start of the run in `observer_calls`, so it is respected even after a restart. A `needs` follow-up does not itself wait for the interval, but the next call is counted from its start.
- One call per run runs at a time, and no more than `concurrency` (2) observer calls overall. With equal readiness, the run with the earlier fact goes first. A slot is freed only after the backend result's `stopped`: under `process_stuck` the batch immediately returns to `pending`, while the run slot and the shared slot stay occupied until the stop is confirmed.
- `chat(work)` performs chat work in a separate slot: one at a time and without waiting for observer calls. The work returns a result with `stopped`, and the next chat work waits for the stop of the previous one to be confirmed. The backend allows concurrent working calls, and admission waits for them to finish (`admission_busy`).
- A batch's input is at most `inputTokens` (24,000 tokens, 4 UTF-8 bytes per token), and so is a `needs` follow-up. Packing is described in the `engine` README ("Observer input").
- The run context (F.7a) is rewritten when the run has a queue and the context has not been written since its last call. The write is asynchronous and does not delay the call: the call takes the last written context, so the run's first urgent call may go out without context. `claudeConfigDir` and `codexHome` are passed to `recordRunContext`: subagent definitions from the Claude configuration directory and Codex agent roles from `config.toml` (F.7d).
- The response is applied via M.2–M.5c. A response with `needs` immediately gets one follow-up in the same slot, without the interval and without spending an attempt. The follow-up starts in the same transaction in which the response with `needs` is recorded. A follow-up is a working call: it runs only if the backend is available and in `ok` at that moment. If a parallel call has already moved the backend to `backoff` or `unavailable`, there is no follow-up: the batch returns to `pending` and the summary to the unsent ones, both without spending an attempt, and after recovery the chain starts with a new first call. If none of the requested materials fits within the limit, there is no follow-up: the response is rejected with the reason `limit` and spends an attempt of the batch.
- A session move (E.5) ends a call whose batch, summary or input touches it, including a summary-only call. The remaining facts of its summary are released for the next summary without spending an attempt. The backend's response to such a call, successful or erroneous, is not applied and does not change fact statuses: only its usage is saved, and `failure` does not fire. The call's slot stays occupied until `stopped` is confirmed.
- A rejected response and output that the backend could not read according to the schema (`invalid_output`) return the batch to `pending` and spend an attempt. The next attempt carries the reasons of the previous refusal in `previous_attempt`, including after an intermediate backend error or a restart. After `attempts` (3) refusals the facts get `not_interpreted` with a gap.
- Other backend errors (timeout, network, cancellation, authorization, limit, isolation violation) return the batch to `pending` without spending an attempt; the call is recorded with the result `failed`. The error class and text are saved in `observer_calls`; a cancellation is recorded without an error. Launch classes outside the contract are saved as the nearest class: `unsafe_workdir` as `isolation`, `launcher_unavailable` as `cli_missing`, `admission_busy` as `version_not_admitted`. How the backend recovers after an error is described in the next section.
- The run's active queue is limited to `queueFacts` (2000) facts and `queueAgeMs` (24 h). Facts older than the limit and the oldest ones beyond the count get `deferred` and an open `summarized_backlog` gap. The limit is checked on every scheduling pass, including for a run with a current call, and by a timer for the nearest age expiry, even when the backend is unavailable and there are no new events. Deferred facts reach the observer only as a compressed summary (below).
- Facts of sessions of another vendor without `crossVendor` get `not_interpreted` and a `cross_vendor_excluded` gap.
- On creation, the scheduler finishes with the result `failed` the calls that the previous process did not complete. Their batches were already returned to `pending` by the store on open, without spending an attempt.
- `idle()` waits for current calls, probes and authorization checks to finish, together with confirmation that their processes stopped. `close()` cancels them, returns batches to `pending` without spending an attempt, and waits for the results of calls, probes and chat work; a cancelled probe is recorded without an error and does not change the recovery state. `close()` does not wait for stop confirmation of a tree that the backend reported as `process_stuck`: after closing there are no new calls, and such a tree may not confirm its stop until a restart. A store error does not crash the process but arrives in `failure`.

## Failures, catch-up mode and budget

F.9 implements the error table of ADR-0007. Each scheduler backend has its own recovery state, and different error classes recover differently. No backend error spends a batch attempt.

| Class | State | Resumption |
| --- | --- | --- |
| `timeout`, `network` | `backoff`: pause `backoffMs` (10 s), doubled up to `backoffMaxMs` (5 min), at most `backoffAttempts` (6) pauses in a row | after the pause — the next working call; the seventh consecutive error gives `unavailable: transient` |
| `limit` | `unavailable: limit` | a probe on synthetic input at the reset time if the CLI reported it, otherwise after `probeMs` (30 min); after a failed probe the interval doubles up to `probeMaxMs` (4 h), but not earlier than the reported reset |
| `transient` | `unavailable: transient` | probes, as for the limit |
| `auth` | `unavailable: auth` | `auth status` every `authCheckMs` (10 min) without a model call |
| isolation violation, CLI missing, version not admitted | `disabled` (backend state from F.6) | only a new `admit()`, after an isolation violation — on a different CLI version or manual (above); no probes or authorization checks |
| `invalid_output`, validation refusal, conflict | `ok` | batch attempts (above) |

- The `backoff` pause is half-open: after it, one working call goes to the backend, and the other runs wait for its result. A model response to a call started after the last state change, including a rejected one, returns the backend to `ok`.
- The result of a call started before the last state change does not change the state. Two simultaneous errors give one pause. A late success of such a call is applied to the model but does not clear `unavailable`: after a limit and transient errors the backend is returned only by a probe, after an authorization error only by `auth status`. A late response with `needs` gets no follow-up (above).
- A probe is the backend's working profile on synthetic input: an empty run `000…0` without sessions, agents and facts, model version 0. Its response is not applied to the model. A successful probe returns the backend to `ok`. A failed one transitions it by the same table: a limit doubles the interval, a network error gives `transient`, authorization gives `auth`.
- Probes and authorization checks count toward the shared observer concurrency. They are recorded in `observer_calls` as completed (`kind` is `probe` or `auth_status`) with the probe's result, error and usage. Probe usage counts toward the budget. A successful `auth status` resumes calls only after an authorization error: under a limit and transient errors it is not performed.
- When a `disabled` backend is admitted again (`admit()`), its recovery state is reset to `ok`.
- The backend's recovery state is stored in the service table `settings` (key `observer_recovery_<runtime>`). It changes in the same transaction as the record of the call, probe or authorization check. Returning to `ok` deletes the record.
- After a restart, including after SIGKILL, the scheduler continues from the saved state: it waits for the limit reset or the end of the pause, and the pause counter and probe interval do not start over.

Catch-up mode. If the earliest fact in a run's queue has waited longer than `catchUpMs` (5 min), the next batch takes the latest facts that fit in a batch and, together with the summary, within the input limit. Earlier facts, including candidates that packing could not fit into the input, get `deferred` with a `summarized_backlog` gap ("meaning restored from a summary"). The run's deferred facts not yet included in an accepted summary — both after catch-up mode and beyond the queue limit — travel with the batch as `batch.backlog`: the time interval, the number of facts, and counters by agent and tool.

- If there are no detailed facts, the summary goes out as a separate call with an empty batch and without a new solver event. This happens, for example, when the whole queue expired while the backend was unavailable.
- If the response is rejected or the call fails, the summary is repeated with the next call. A rejected summary, like a batch, spends an attempt, while a backend error does not. After `attempts` refusals its facts get `not_interpreted` with a gap.
- A repeated summary carries the reasons of its refusal in `previous_attempt`, including when new detailed facts were added to it. The refusal reasons of the batch and the summary are merged without duplicates.
- While the run lags behind by more than the threshold or its summary has not yet been accepted — not sent or awaiting the response of an ongoing call — its state is `lagging: backlog`.

Budget. `budgetTokensPerHour` (from `observer.budgetTokensPerHour`, unlimited by default) is compared with the tokens of batches and probes completed during the last hour. When exceeded, the batch timer grows from `delayMs` to `budgetDelayMs` (60 s), and the backend and its runs get `lagging: budget`. A full batch and an urgent fact go as before, and the 10 s interval between calls of a run is kept. When earlier calls leave the hourly window, the timer returns to 5 s.

Batch delay is the time from the earliest `observed_at` of the batch's records to the acceptance of the response, including the `needs` follow-up. It is saved in `observer_calls.delay_ms` of the accepted call. A summary-only call has no detailed records, and the delay is not written.

States:

- `backendState(runtime)` returns `disabled` and `unavailable` of the backend itself, then `backoff` or `unavailable` of recovery, then `lagging: budget`, otherwise `ok`. A backend that is not in `backends` is `disabled: cli_missing`;
- `state(run)` returns the state of the run's backend, and for `ok` and `lagging` returns `lagging: backlog` if the run lags by more than the threshold or its deferred facts have not yet been included in an accepted summary;
- `subscribe(listener)` reports changes of these states, including when a run crosses the lag threshold or earlier usage leaves the budget window.

## System prompt

`observerSystemPrompt` (F.7b, based on `docs/research/samples/observer/observer-prompt.json`) is passed via `--system-prompt` for Claude and as the `model_instructions_file` file for Codex, including during admission. It declares all input untrusted data, describes the parts of the input, the rules for references, evidence and temporary ids, each protocol operation, the decomposition of an explicit plan (PLAN.md, a task list) directly into planned stages, the `needs` protocol and applying the response as a whole. The input itself is passed in stdin as a single JSON document. The CLI receives the response schema separately (`--json-schema`, `--output-schema`).

Scheduler tests feed hook events through the real adapters and `engine`, call the fake `claude` and `codex` from testkit and control time through the test clock. Failures are injected by fake CLI scenarios: authorization, a limit with and without a reset time, timeout, network, invalid output and a tool attempt. An external CLI wrapper delays the response of one of the concurrent calls so that it arrives after another one's error. State persistence is checked by SIGKILL of a separate process with the scheduler (`TerminateProcess` on Windows). The dependency rule allows `observer` tests to import adapters.

`chatSystemPrompt` (K.1) is the chat system prompt. It also declares the input untrusted data, except for the question itself, describes the parts of the chat input (`ChatInput`, ADR-0008), the reference rules by kinds `stage`, `fact`, `action`, `artifact_version` and `question`, the `insufficient_data` flag, a single `needs` follow-up with `answer: null`, and `view_rule` only when the human asks to change the view. For a view rule (K.2) the prompt describes the actions and their parameters, the selector variants (agents by type, name or role from `run.agents`, service agents, stages by id or a fragment of the title, actions by tool or kind) and the validation requirements: non-empty selector text and group name, only stages of the run. It says that the rule is applied immediately together with the answer and to new elements, that a rule that fails validation is not applied and the human sees the reason, and that questions of hidden elements stay visible as waiting for you (a stage badge or the header chip). Because the map shows stages only, the prompt steers requests to show only, hide, focus on, collapse or group parts of the map to stage selectors (for show only and focus on, hiding the other stages) and asks the answer to say so when only an agent, action or detail rule fits, since such a rule does not change the stage map. The chat does not change the model and sends nothing to the solver.

## Chat

A chat call (K.1, ADR-0008) goes through the same mechanism as the observer: the same admitted backend, isolation profile, version check, environment and working directory. The call protocol is defined by `CallProtocol`: the system prompt, the response JSON Schema for `--json-schema` and `--output-schema`, and the response validation schema. `execute()` works by the observer protocol, `chat()` by the chat protocol (`chatSystemPrompt`, `chatOutputJsonSchema()`, `ChatOutput`). An isolation violation in a chat call revokes the backend's admission in the same way as in an observer working call.

`createChat({ store, backends, backend?, crossVendor?, slot, journal?, now?, limits? })` answers questions about runs:

- `ask(run, { question, stage })` in one transaction assembles the input on the current map version V (`startChat` in `engine`) and records a `pending` question with version V. An unknown run gives `null`. A stage outside the run or outside the input scope, and input that does not fit within the limit, give `ChatError` (`unknown_stage`, `input_limit`), and the question is not recorded. After `close()` — `ChatClosedError`.
- The run's backend is the vendor of its root session; `backend` overrides it; `crossVendor` applies to the input and materials the same way as for the observer. A question stores the backend and `crossVendor` of its input. Without `crossVendor`, the input history includes only answers to questions with the same backend and without `crossVendor`, so after a setting change and a restart an answer assembled from another vendor's data does not go to the new backend.
- The call runs in the chat slot (`slot`; in the daemon, `scheduler.chat`): one at a time, without waiting for the observer, and waiting for confirmed stop of the previous process tree.
- A response with `answer: null` and non-empty `needs` gets one follow-up: the daemon resolves the request (`followUpChat`) and calls the CLI again with the same input of version V and the materials. The follow-up joins the chat slot behind questions already waiting. Its `needs` are not executed. If none of the materials fits within the limit, the question finishes with a `limit` error.
- The answer is saved with version V (`answerChat`): citations that are not in the input of the last call are removed with the `unconfirmed_citations` flag, and an answer without text or with `insufficient_data` is marked as insufficient data. A view rule from the answer (K.2) is applied in the same transaction: the message contains `view_rule` with the rule id or `view_rule_error` explaining why it was not applied. The rule of the first answer that requested `needs` is not applied, nor is that answer itself.
- A backend error finishes the question as `failed` with the error class and text. The chat does not change the observer's recovery state.
- Every completed CLI call is passed to `journal` as a `ChatCallRecord`: run, backend, base version V, the previous call for a follow-up, input, output, verdict (`needs_requested`, `accepted`, `rejected` for unreadable output, `failed`), error, usage and time. This is the minimal interface of the U.1 chat journal (`observerCalls.chat`); without `journal` records are not saved.
- On creation, questions left `pending` by a stopped process finish with the error "the daemon stopped before the chat answered". `close()` forbids new questions and waits for the started ones; a cancelled call finishes the question with the `cancelled` error.

Chat tests (`test/chat.test.ts`) run on the fake `claude` and `codex`: a two-phase call in which the map changes between phases, a removed incorrect citation, insufficient data, a limit and unreadable output, restart and close, history when the backend and `crossVendor` change between restarts.
