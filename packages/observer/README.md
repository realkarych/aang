# Запуск и допуск наблюдателя

F.2, F.5 и F.6: `createClaudeBackend` и `createCodexBackend` возвращают backend с обязательным допуском. После создания вызывающий код запускает `await backend.admit(signal?)`; до успешного результата `execute({ input, signal })` отказывает без передачи рабочего входа CLI. Допуск получает только синтетические данные. Каждый рабочий вызов сначала проверяет версию; смена версии требует нового `admit()`. Нарушение изоляции также отзывает допуск. Новый экземпляр backend всегда начинает без допуска, в том числе после изменения модели, effort или списка встроенных компонентов. `cliVersion(signal?)` сообщает версию установленного CLI одним вызовом `--version` без допуска и без обращения к модели, а если CLI нет или версия не распознана — `null`.

Нарушение изоляции — в допуске или в рабочем вызове — закрепляется за версией CLI и профилем (ADR-0007: возобновление только новым допуском по команде `aang doctor --admit` или при смене версии CLI). `admit()` на той же версии и с тем же профилем отказывает с классом `isolation` после одного вызова `--version`, без проб и без вызовов модели. Ручной допуск — `admit(signal, { manual: true })`, его вызовет `aang doctor --admit` (G.12). Отметка `isolationViolated` хранится в файле статуса, поэтому новый экземпляр backend с тем же профилем сразу находится в `disabled: isolation` и не допускает ту же версию и после перезапуска. Успешный допуск или другая версия CLI снимают отметку. Отметка относится к версии, на которой шёл вызов: если параллельный вызов уже обнаружил новую версию, поздний отказ вызова на прежней версии — нарушение изоляции или любой другой — состояние допуска не меняет, и новую версию допускает обычный автоматический допуск. Другой профиль (модель, effort, путь CLI, встроенные компоненты) по ADR-0007 требует нового автоматического допуска, поэтому отметка прежнего профиля к нему не применяется.

`admission()` возвращает результат с версией, ОС, хешем профиля, временем проверки, причиной отказа, отметкой нарушения изоляции, допущенными встроенными плагинами и пометкой Claude. Результат атомарно записывается в `admissionStatusPath`, по умолчанию — `~/.aang/support/<runtime>-observer.json`. Файл служит локальным статусом, а не разрешением пропустить проверки при старте. `verifiedClaudeVersions` получает версии с успешным локальным контрактным прогоном на текущей ОС из матрицы поддержки. Без такого результата автоматически допущенный Claude включается с пометкой «изоляция от сообщений других сессий на этой версии не проверена». Проверка с сессией-пиром относится к F.10.

Допуск Claude выполняет два малых вызова с одним синтетическим входом. Во временном проекте независимый SessionStart-hook создаёт метку: с `--setting-sources project` она обязательна, с `--setting-sources ""` запрещена. Во время обоих вызовов проверяется маркер реестра, после — отсутствие транскрипта и файла, который синтетическая инструкция просила создать инструментом. `init` и результат проходят те же проверки, что рабочий ответ, с двумя отличиями. Во-первых, допуск принимает любой встроенный плагин (`path: builtin`, источник `<имя>@builtin`). Во-вторых, события hooks разрешены только в положительной ветке с контрольным hook. Авторизация остаётся штатной, пользовательские учётные данные не копируются.

Встроенные плагины Claude (ADR-0007, решение 9). Каждый вызов идёт с `--include-hook-events`. В профиле наблюдателя встроенный плагин не должен давать модели ни инструментов (`tools == ["StructuredOutput"]`), ни MCP-серверов (`mcp_servers` пуст), ни исполняемых hooks (в потоке нет событий `system/hook_*`). Иначе допуск отказывает с классом `isolation`; невстроенный плагин тоже даёт отказ. Встроенные плагины из `init` отрицательной ветки фиксируются в результате допуска (`builtinPlugins`). Рабочий вызов этой версии принимает только их и плагины из `builtins`; любой другой плагин или событие hooks — нарушение изоляции.

Допуск Codex выполняет два вызова на локальной заглушке Responses API во временном `CODEX_HOME`. Заглушка проверяет оба расположения инструментов и получает ответы `unsupported` на `exec`, `spawn_agent`, `request_user_input` и `request_user_input_async`. Контрольные ветки отличаются только `--disable hooks`; обе содержат тестовый `--dangerously-bypass-hook-trust`. Проверяется отсутствие rollout и строк сессий в SQLite. Рабочий вызов не получает ни bypass, ни тестовый провайдер, ни временный `CODEX_HOME`.

`model` задаётся обязательно, `effort` — явно, если задан конфигурацией. `builtins` Claude — разрешённый список из матрицы поддержки; по умолчанию он пуст. Встроенные плагины, зафиксированные допуском, добавляются к нему. Путь CLI разрешается до очистки окружения; можно передать абсолютный исполняемый файл и префикс аргументов для npm-обёртки Codex. Авторизация проверяется перед первым рабочим вызовом и заново после ошибки авторизации. Codex обновляет каталог модели при изменении версии.

`status()` возвращает контрактный `ObserverState` и количество занятых процессов; `subscribe()` сообщает изменения. Результат `execute` содержит `stopped` — обещание, которое выполняется после подтверждённой остановки всех процессов вызова. `process_stuck` удерживает слот и запрещает следующие вызовы и допуск. Позднее подтверждение остановки освобождает слот; потеря Windows-лаунчера без файла статуса требует перезапуска. Состояние, пометка и уведомления предназначены для `/api/status` и SSE. Демон собирает backend и планировщик в G.6 и отдаёт их состояние в `/api/status`, сводке прогона и SSE (`packages/daemon/README.md`). Планирование вызовов и восстановление после отказов описаны ниже.

Ошибка вызова несёт класс:

- `auth` — «Not logged in» и похожие ответы, а также неуспешный `auth status` / `login status`;
- `limit` — HTTP 429, отклонённый `rate_limit_event` Claude или текст о лимите. Время сброса берётся из `resetsAt` события Claude или из ISO-времени после «resets» / «try again at» и передаётся в `resetsAt`;
- `network` — HTTP 5xx у Claude, ошибки соединения и разрыв потока;
- `timeout` — жёсткий таймаут процесса;
- `invalid_output` — выход, который не прочитан по схеме.

Текст ошибки CLI добавляется к сообщению. `authStatus(signal?)` выполняет `claude auth status` или `codex login status` тем же запуском, что и рабочий вызов, и не обращается к модели. Он подчиняется тем же запретам, что и рабочий вызов: без допуска, во время допуска и при `process_stuck` возвращает отказ.

`createClaudeLauncher`, `createCodexLauncher` и `createProcessRunner` — низкоуровневые операции запуска F.2/F.5, из которых собран backend. Они проверяют профиль и завершение дерева, но не выполняют допуск. Рабочие порции и чат должны использовать только `createClaudeBackend` / `createCodexBackend`. Тесты низкоуровневого запуска проверяют эти операции отдельно от тестов допуска.

Все процессы запускаются без shell. На Unix runner завершает группу и ждёт `ESRCH`; на Windows использует абсолютный `windowsLauncher` (`aang-hook.exe`, режим D.9). Закрытие каналов не подтверждает остановку. Проверка длится 10 секунд, затем возвращает `process_stuck` и продолжает ждать. Вывод ограничен 16 MiB. Временные файлы удаляются после подтверждения остановки.

Рабочий каталог — `os.tmpdir()/aang-observer/empty`; `temporaryDirectory` задаёт корень временных файлов. Непустой рабочий каталог и инструкции `CLAUDE.md`/`AGENTS.md` в предках, включая физический путь, запрещают запуск. Допуск создаёт отдельный временный каталог рядом с рабочим.

Тесты используют только CLI из testkit и внешние обёртки процессов. Контрольный hook исполняется отдельным Node-процессом и не зависит от самоисключения `aang-hook`. Зомби проверяет тестовый помощник на C (`cc` на macOS/Linux). Реальные CLI эти тесты не запускают и поддержку реальных версий не объявляют.

## Очередь и запуск порций

`createObserverScheduler({ store, backends, backend?, crossVendor?, claudeConfigDir?, budgetTokensPerHour?, clock?, limits? })` запускает порции наблюдателя по статусам интерпретации (F.8). Демон (G.6) вызывает `wake()` после каждого приёма; остальное планируют таймеры и уведомления backend.

- Backend прогона — вендор его корневой сессии, `backend` переопределяет его. Backend в состоянии `disabled` или `unavailable` вызовов не получает, в `backoff` — получает их только после паузы; смена его состояния, например успешный `admit()`, снова планирует очередь.
- Вызов запускается, когда в очереди прогона есть срочный факт, набралось `batchFacts` (30) фактов или `batchBytes` (96 000 байт payload, около 24k токенов) либо самый ранний факт ждёт `delayMs` (5 с) с момента наблюдения его записи (`observed_at`). Возраст отсчитывается и для фактов, пришедших во время вызова прогона, поэтому созревшая порция уходит сразу после его окончания.
- Между началами вызовов одного прогона проходит не меньше `intervalMs` (10 с), в том числе для срочного факта. Интервал отсчитывается от последнего начала вызова прогона в `observer_calls`, поэтому выдерживается и после перезапуска. Дозапрос `needs` сам интервала не ждёт, но следующий вызов отсчитывается от его начала.
- Одновременно идёт один вызов на прогон и не больше `concurrency` (2) вызовов наблюдателя. При равной готовности первым идёт прогон с более ранним фактом. Слот освобождается только после `stopped` результата backend: при `process_stuck` порция сразу возвращается в `pending`, а слот прогона и общий слот остаются занятыми до подтверждения остановки.
- `chat(work)` выполняет работу чата в отдельном слоте: по одной за раз и без ожидания вызовов наблюдателя. Работа возвращает результат со `stopped`, и следующая работа чата ждёт подтверждения остановки предыдущей. Backend допускает одновременные рабочие вызовы, а допуск ждёт их завершения (`admission_busy`).
- Вход порции не больше `inputTokens` (24 000 токенов, по 4 байта UTF-8 на токен), дозапрос `needs` — тоже. Упаковку описывает README `engine` («Observer input»).
- Контекст прогона (F.7a) записывается заново, когда у прогона есть очередь и с его последнего вызова контекст ещё не записывался. Запись идёт асинхронно и не задерживает вызов: вызов берёт последний записанный контекст, поэтому первый срочный вызов прогона может уйти без контекста. `claudeConfigDir` передаётся в `recordRunContext` для определений субагентов из каталога конфигурации Claude.
- Ответ применяется через M.2–M.5c. Ответ с `needs` сразу получает один дозапрос в том же слоте, без интервала и без траты попытки. Дозапрос начинается в той же транзакции, где записан ответ с `needs`. Дозапрос — рабочий вызов: он идёт, только если backend к этому моменту доступен и в `ok`. Если параллельный вызов уже перевёл backend в `backoff` или `unavailable`, дозапроса нет: порция возвращается в `pending`, а сводка — к неотправленным, обе без траты попытки, и после восстановления цепочка начинается с нового первого вызова. Если в предел не помещается ни один запрошенный материал, дозапроса нет: ответ отклоняется с причиной `limit` и тратит попытку порции.
- Перенос сессии (E.5) завершает вызов, порция, сводка или вход которого её затрагивают, в том числе вызов только со сводкой. Оставшиеся факты его сводки освобождаются для следующей сводки без траты попытки. Ответ backend на такой вызов, успешный или ошибочный, не применяется и не меняет статусы фактов: сохраняется только его расход, а `failure` не срабатывает. Слот вызова занят до подтверждения `stopped`.
- Отклонённый ответ и выход, который backend не прочитал по схеме (`invalid_output`), возвращают порцию в `pending` и тратят попытку. Следующая попытка несёт причины прошлого отказа в `previous_attempt`, в том числе после промежуточной ошибки backend или перезапуска. После `attempts` (3) отказов факты получают `not_interpreted` с пробелом.
- Другие ошибки backend (таймаут, сеть, отмена, авторизация, лимит, нарушение изоляции) возвращают порцию в `pending` без траты попытки, вызов записывается с результатом `failed`. Класс и текст ошибки сохраняются в `observer_calls`; отмена записывается без ошибки. Классы запуска вне контракта сохраняются ближайшим классом: `unsafe_workdir` — как `isolation`, `launcher_unavailable` — как `cli_missing`, `admission_busy` — как `version_not_admitted`. Как backend восстанавливается после ошибки, описано в следующем разделе.
- Активная очередь прогона ограничена `queueFacts` (2000) фактами и `queueAgeMs` (24 ч). Факты старше предела и самые старые сверх числа получают `deferred` и открытый пробел `summarized_backlog`. Предел проверяется при каждом планировании, в том числе для прогона с текущим вызовом, и по таймеру ближайшего истечения возраста, даже когда backend недоступен и новых событий нет. Отложенные факты попадают к наблюдателю только сжатой сводкой (ниже).
- Факты сессий другого вендора без `crossVendor` получают `not_interpreted` и пробел `cross_vendor_excluded`.
- При создании планировщик завершает с результатом `failed` вызовы, которые прошлый процесс не закончил. Их порции хранилище при открытии уже вернуло в `pending` без траты попытки.
- `idle()` ждёт завершения текущих вызовов, проб и проверок авторизации вместе с подтверждением остановки их процессов. `close()` отменяет их, возвращает порции в `pending` без траты попытки и ждёт результатов вызовов, проб и работы чата; отменённая проба записывается без ошибки и состояние восстановления не меняет. Подтверждения остановки дерева, о котором backend сообщил `process_stuck`, `close()` не ждёт: после закрытия новых вызовов нет, а такое дерево может не подтвердить остановку до перезапуска. Ошибка хранилища не роняет процесс, а приходит в `failure`.

## Отказы, догоняющий режим и бюджет

F.9 реализует таблицу ошибок ADR-0007. У каждого backend планировщика своё состояние восстановления, и разные классы ошибок восстанавливаются по-разному. Ни одна ошибка backend не тратит попытку порции.

| Класс | Состояние | Возобновление |
| --- | --- | --- |
| `timeout`, `network` | `backoff`: пауза `backoffMs` (10 с), удваивается до `backoffMaxMs` (5 мин), не больше `backoffAttempts` (6) пауз подряд | после паузы — следующий рабочий вызов; седьмая ошибка подряд даёт `unavailable: transient` |
| `limit` | `unavailable: limit` | проба на синтетическом входе в момент сброса, если CLI его сообщил, иначе через `probeMs` (30 мин); после неудачной пробы интервал удваивается до `probeMaxMs` (4 ч), но не раньше сообщённого сброса |
| `transient` | `unavailable: transient` | пробы, как у лимита |
| `auth` | `unavailable: auth` | `auth status` раз в `authCheckMs` (10 мин) без вызова модели |
| нарушение изоляции, CLI отсутствует, версия не допущена | `disabled` (состояние backend из F.6) | только новый `admit()`, после нарушения изоляции — на другой версии CLI или ручной (выше); проб и проверок авторизации нет |
| `invalid_output`, отказ проверки, конфликт | `ok` | попытки порции (выше) |

- Пауза `backoff` полуоткрыта: после неё к backend идёт один рабочий вызов, остальные прогоны ждут его результата. Ответ модели на вызов, начатый после последней смены состояния, в том числе отклонённый, возвращает backend в `ok`.
- Результат вызова, начатого до последней смены состояния, состояние не меняет. Две одновременные ошибки дают одну паузу. Поздний успех такого вызова применяется к модели, но `unavailable` не снимает: после лимита и временных ошибок backend возвращает только проба, после ошибки авторизации — только `auth status`. Поздний ответ с `needs` дозапроса не получает (выше).
- Проба — рабочий профиль backend на синтетическом входе: пустой прогон `000…0` без сессий, агентов и фактов, версия модели 0. Её ответ к модели не применяется. Успешная проба возвращает backend в `ok`. Неудачная переводит его по той же таблице: лимит удваивает интервал, сеть даёт `transient`, авторизация — `auth`.
- Пробы и проверки авторизации идут в общий параллелизм наблюдателя. Они записываются в `observer_calls` завершёнными (`kind` — `probe` или `auth_status`) с результатом, ошибкой и расходом пробы. Расход проб входит в бюджет. Успешный `auth status` возобновляет вызовы только после ошибки авторизации: при лимите и временных ошибках он не выполняется.
- Когда `disabled` backend снова допущен (`admit()`), его состояние восстановления сбрасывается в `ok`.
- Состояние восстановления backend хранится в служебной таблице `settings` (ключ `observer_recovery_<runtime>`). Оно меняется в той же транзакции, что и запись вызова, пробы или проверки авторизации. Возврат в `ok` удаляет запись.
- После перезапуска, в том числе после SIGKILL, планировщик продолжает с сохранённого состояния: ждёт сброса лимита или конца паузы, а счётчик пауз и интервал проб не начинаются заново.

Догоняющий режим. Если самый ранний факт очереди прогона ждёт дольше `catchUpMs` (5 мин), следующая порция берёт самые поздние факты, которые помещаются в порцию и вместе со сводкой — в предел входа. Более ранние факты, в том числе кандидаты, которые упаковка не уместила во вход, получают `deferred` с пробелом `summarized_backlog` («смысл восстановлен по сводке»). Отложенные факты прогона, ещё не вошедшие в принятую сводку, — и после догоняющего режима, и сверх предела очереди — едут с порцией как `batch.backlog`: интервал времени, число фактов и счётчики по агентам и инструментам.

- Если подробных фактов нет, сводка уходит отдельным вызовом с пустой порцией без нового события решателя. Так бывает, например, когда вся очередь истекла, пока backend был недоступен.
- Если ответ отклонён или вызов не удался, сводка повторяется со следующим вызовом. Отклонённая сводка, как и порция, тратит попытку, а ошибка backend — нет. После `attempts` отказов её факты получают `not_interpreted` с пробелом.
- Повтор сводки несёт причины её отказа в `previous_attempt`, в том числе когда к ней добавились новые подробные факты. Причины отказа порции и сводки объединяются без повторов.
- Пока прогон отстаёт больше порога или его сводка ещё не принята — не отправлена или ждёт ответа идущего вызова, — его состояние — `lagging: backlog`.

Бюджет. `budgetTokensPerHour` (из `observer.budgetTokensPerHour`, по умолчанию без ограничения) сравнивается с токенами порций и проб, завершённых за последний час. При превышении таймер порции растёт с `delayMs` до `budgetDelayMs` (60 с), а backend и его прогоны получают `lagging: budget`. Полная порция и срочный факт идут как раньше, а интервал 10 с между вызовами прогона сохраняется. Когда ранние вызовы выходят из часового окна, таймер возвращается к 5 с.

Задержка порции — время от самого раннего `observed_at` записей порции до принятия ответа, вместе с дозапросом `needs`. Она сохраняется в `observer_calls.delay_ms` принятого вызова. У вызова только со сводкой подробных записей нет, и задержка не пишется.

Состояния:

- `backendState(runtime)` возвращает `disabled` и `unavailable` самого backend, затем `backoff` или `unavailable` восстановления, затем `lagging: budget`, иначе `ok`. Backend, которого нет в `backends`, — `disabled: cli_missing`;
- `state(run)` возвращает состояние backend прогона, а для `ok` и `lagging` — `lagging: backlog`, если прогон отстаёт больше порога или его отложенные факты ещё не вошли в принятую сводку;
- `subscribe(listener)` сообщает о смене этих состояний, в том числе когда прогон пересекает порог отставания или ранний расход выходит из окна бюджета.

## Системный промпт

`observerSystemPrompt` (F.7b, основа — `docs/research/samples/observer/observer-prompt.json`) передаётся `--system-prompt` у Claude и файлом `model_instructions_file` у Codex, в том числе при допуске. Он объявляет весь вход недоверенными данными, описывает части входа, правила ссылок, свидетельств и временных id, каждую операцию протокола, протокол `needs` и применение ответа целиком. Сам вход передаётся в stdin одним JSON-документом. Схему ответа CLI получает отдельно (`--json-schema`, `--output-schema`).

Тесты планировщика подают hook-события через настоящие адаптеры и `engine`, вызывают поддельные `claude` и `codex` из testkit и управляют временем через часы теста. Отказы внедряют сценарии поддельных CLI: авторизация, лимит со временем сброса и без него, таймаут, сеть, невалидный выход и попытка инструмента. Внешняя обёртка CLI задерживает ответ одного из одновременных вызовов, чтобы он пришёл после ошибки другого. Сохранение состояния проверяется SIGKILL отдельного процесса с планировщиком (`TerminateProcess` на Windows). Правило зависимостей разрешает тестам `observer` импортировать адаптеры.

`chatSystemPrompt` (K.1) — системный промпт чата. Он тоже объявляет вход недоверенными данными, кроме самого вопроса, описывает части входа чата (`ChatInput`, ADR-0008), правила ссылок по видам `stage`, `fact`, `action`, `artifact_version` и `question`, пометку `insufficient_data`, один дозапрос `needs` с `answer: null` и `view_rule` только по просьбе человека изменить вид. Чат не меняет модель и ничего не отправляет решателю.

## Чат

Вызов чата (K.1, ADR-0008) идёт через тот же механизм, что и наблюдатель: тот же допущенный backend, профиль изоляции, проверка версии, окружение и рабочий каталог. Протокол вызова задаёт `CallProtocol`: системный промпт, JSON Schema ответа для `--json-schema` и `--output-schema` и схема проверки ответа. `execute()` работает по протоколу наблюдателя, `chat()` — по протоколу чата (`chatSystemPrompt`, `chatOutputJsonSchema()`, `ChatOutput`). Нарушение изоляции в вызове чата отзывает допуск backend так же, как в рабочем вызове наблюдателя.

`createChat({ store, backends, backend?, crossVendor?, slot, journal?, now?, limits? })` отвечает на вопросы прогонов:

- `ask(run, { question, stage })` в одной транзакции собирает вход на текущей версии карты V (`startChat` в `engine`) и записывает вопрос `pending` с версией V. Неизвестный прогон — `null`. Этап вне прогона или вне области входа и вход, который не помещается в предел, — `ChatError` (`unknown_stage`, `input_limit`), вопрос не записывается. После `close()` — `ChatClosedError`.
- Backend прогона — вендор его корневой сессии, `backend` переопределяет его; `crossVendor` применяется к входу и материалам так же, как у наблюдателя. Вопрос хранит backend и `crossVendor` своего входа. Без `crossVendor` в историю входа попадают только ответы на вопросы с тем же backend и без `crossVendor`, поэтому после смены настройки и перезапуска ответ, собранный на данных другого вендора, не уходит новому backend.
- Вызов идёт в слоте чата (`slot`; в демоне — `scheduler.chat`): по одному, без ожидания наблюдателя и с ожиданием подтверждённой остановки предыдущего дерева процессов.
- Ответ с `answer: null` и непустым `needs` получает один дозапрос: демон разрешает запрос (`followUpChat`) и снова вызывает CLI с тем же входом версии V и материалами. Дозапрос встаёт в слот чата за уже ждущими вопросами. Его `needs` не исполняются. Если в предел не помещается ни один материал, вопрос завершается ошибкой `limit`.
- Ответ сохраняется с версией V (`answerChat`): цитаты, которых нет во входе последнего вызова, удаляются с пометкой `unconfirmed_citations`, а ответ без текста или с `insufficient_data` помечается как недостаточно данных. Правило вида из ответа применяет K.2; здесь `view_rule` сообщения пока `null`.
- Ошибка backend завершает вопрос как `failed` с классом и текстом ошибки. Состояние восстановления наблюдателя чат не меняет.
- Каждый завершённый вызов CLI передаётся в `journal` записью `ChatCallRecord`: прогон, backend, базовая версия V, предыдущий вызов для дозапроса, вход, выход, вердикт (`needs_requested`, `accepted`, `rejected` для нечитаемого выхода, `failed`), ошибка, расход и время. Это минимальный интерфейс журнала чата U.1 (`observerCalls.chat`); без `journal` записи не сохраняются.
- При создании вопросы, оставшиеся `pending` от остановленного процесса, завершаются ошибкой «the daemon stopped before the chat answered». `close()` запрещает новые вопросы и ждёт начатых; отменённый вызов завершает вопрос ошибкой `cancelled`.

Тесты чата (`test/chat.test.ts`) идут на поддельных `claude` и `codex`: двухфазный вызов, при котором карта меняется между фазами, удалённая неверная цитата, недостаточно данных, лимит и нечитаемый выход, перезапуск и закрытие, история при смене backend и `crossVendor` между перезапусками.
