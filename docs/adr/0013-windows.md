# ADR-0013: Поддержка Windows

Статус: требование принято владельцем 2026-10-01 — MVP поддерживает macOS, Linux и нативный Windows, включая Claude Desktop и Codex Desktop на Windows без WSL. Обработчик hook на Go принят владельцем 2026-10-01. Остальные технические решения ниже — предложено 2026-10-01.

## Контекст

ADR-0004 предлагал ограничить MVP macOS и Linux. Владелец решил иначе: нативный Windows входит в MVP.

Спайк проводился только на macOS, поэтому всё, что касается Windows, не проверено:

- раскладка `~/.claude` и `~/.codex`;
- способ, которым Claude Code и Codex запускают команды hooks;
- поведение fs watch и блокировок файлов;
- запуск CLI наблюдателем и хранение авторизации;
- данные обоих Desktop.

Обработчик hook из ADR-0004 написан на POSIX sh, которого на Windows нет. Обработчик на Node стартует десятки миллисекунд и не укладывается в бюджет 10 мс на событие.

## Решение

### Обработчик hook

- `aang-hook` — один нативный исполняемый файл на Go для всех платформ: macOS, Linux, Windows, архитектуры amd64 и arm64. Он заменяет sh-скрипт (принято владельцем 2026-10-01).
- Контракт ADR-0004 не меняется:
  - синхронный вызов с `timeout: 2` с в конфиге hooks;
  - всегда `exit 0`, пустые stdout и stderr;
  - без сети;
  - формат spool с заголовком и NUL-разделителями;
  - аренда и маркеры наблюдателя;
  - вычитывание stdin до конца.
- Срок аренды обработчик сравнивает с системным временем внутри процесса. Файл создаётся во временном каталоге spool и переименовывается в `spool/new`.
- **`exit 0` на Go** обеспечивает сам бинарь:
  - ожидаемые ошибки обрабатываются без вывода;
  - аргументы разбираются без завершающего парсера: `flag` с `ExitOnError` завершает процесс с кодом 2. Неверные или отсутствующие аргументы — выход без записи;
  - паника перехватывается на верхнем уровне (`recover`) и завершается `exit 0` без вывода: необработанная паника Go даёт код 2;
  - stdin копируется в файл потоком, без накопления в памяти; обработчик работает в одной горутине.
- **Пределы гарантии.** Фатальную ошибку среды Go (например, нехватку памяти) и внешнее завершение — по таймауту рантайма, ОС или пользователем — бинарь пережить не может. `timeout: 2` ограничивает ожидание решателя, но не обеспечивает успешный выход, а вычитывание stdin действует, только пока процесс жив.
  - По документации Claude отмена по таймауту и код, отличный от 2, при пустом stdout не блокируют действие. Исключение — `PreModelSwitch`: отменённый по таймауту hook блокирует смену модели, поэтому aang его не регистрирует (ADR-0004).
  - Поведение Codex при таймауте и ненулевом коде проверяют D.5 и D.8 (план).
- **Почему Go:**
  - статический бинарь без рантайма;
  - запуск за миллисекунды на всех ОС;
  - кросс-компиляция без C-тулчейна (`CGO_ENABLED=0`).

  Rust сопоставим по скорости, но тулчейн тяжелее. Скомпилированные Node, Deno и Bun стартуют десятки миллисекунд. PowerShell стартует сотни миллисекунд, а `cmd` не читает stdin без искажений.
- Это исключение из ADR-0001, ограниченное одним компонентом (принято владельцем 2026-10-01). Правила AGENTS.md, включая запрет комментариев, действуют и для Go.
- **Бюджет** — p95 ≤ 10 мс на событие на всех трёх ОС, измеренный со стороны рантайма: от запуска команды hook до выхода процесса, включая launcher (shell или прямой запуск) и передачу stdin типичного размера, в конфигурации, которую ставит `aang install`.
  - Бенчмарк самого бинаря (план, D.1) — необходимое условие и регрессионная проверка в CI, но не итоговое значение.
  - Итоговое значение даёт бенчмарк с тем же launcher, что у рантайма, и живая проверка: прирост времени серии событий в настоящем CLI с hooks aang относительно серии без них (план, D.5 для macOS и Linux, D.8 для Windows).
  - Создание процесса на Windows дороже. Если итоговая задержка на какой-либо ОС превышает бюджет, измеренное значение выносится владельцу, а не принимается молча.
- **Поставка:** бинари идут в npm необязательными пакетами по платформам (`aang-hook-<os>-<arch>`), как у esbuild. `aang install` копирует нужный бинарь без изменений в `<AANG_HOME>/bin/aang-hook` (`aang-hook.exe` на Windows).
  - Обновление на месте: новый файл пишется рядом и переименовывается поверх старого.
  - На Windows занятый `.exe` нельзя перезаписать или удалить, но можно переименовать. Поэтому старый файл сначала переносится в сторону, затем новый занимает его место; старые копии удаляются позже, когда не заняты. Вызов в окне между двумя переименованиями не запустится — это потеря события, как при недоступном spool, а не блокировка.
- **Вызов из конфигов hooks** — по абсолютному пути с тегом регистрации и абсолютным путём spool.
  - Claude вызывает `aang-hook` в exec form: `command` — абсолютный путь, аргументы — в `args`. Без `args` Claude передаёт команду shell: `sh -c` на macOS и Linux, Git Bash или PowerShell на Windows, и запуск shell на Windows сам превышает бюджет. Exec form проверяется контрактным тестом установки на версиях матрицы; версия без него запустит бинарь без аргументов, событие не запишется, и сессия будет видна как «hooks не активны».
  - Как Codex исполняет команду hook на Windows (напрямую, через `cmd`, Git Bash или PowerShell), не проверено. Это выясняет D.8 до установки hooks на Windows, и по её итогу строка команды формируется для каждой ОС.
  - Пути с пробелами и не-ASCII символами (профиль Windows вида `C:\Users\Имя Фамилия`) проверяются для обоих рантаймов.

### Пути и файлы

- Корни по умолчанию:
  - `%USERPROFILE%\.claude` или `CLAUDE_CONFIG_DIR`;
  - `%USERPROFILE%\.codex` или `CODEX_HOME`;
  - `AANG_HOME` — `%USERPROFILE%\.aang`.

  Пути строятся через `os.homedir()` и модуль `path`, а не склейкой строк.
- Кодирование `cwd` Windows (буква диска, обратные слеши) в имени каталога проекта Claude и расположение данных Desktop не проверены. Адаптер берёт пути транскриптов из payload hooks (`transcript_path`) и из обхода корней, а имя каталога проекта из `cwd` не восстанавливает.
- Идентичность файла — `fs.stat` с `bigint`: `dev` (серийный номер тома) и `ino` (индекс файла NTFS).
- Чтение файла, который держит другой процесс: Node открывает файлы с разрешением совместного доступа. Если пишущий процесс держит исключительную блокировку, чтение повторяется с паузой; затяжная неудача становится пробелом.
- Разбор строк принимает `\r\n`.
- Права: на macOS и Linux каталог `AANG_HOME` имеет права 0700. На Windows aang не меняет ACL и полагается на ACL профиля пользователя по умолчанию (доступ у пользователя, SYSTEM и администраторов).
- Пути в значениях `-c` для Codex (TOML) записываются с прямыми слешами: в обычных строках TOML обратный слеш — это экранирование.

### Наблюдение за файлами

- Рекурсивный `fs.watch` на Windows работает через `ReadDirectoryChangesW`. При переполнении буфера события теряются, и каталог нужно перечислить заново.
- По ADR-0004 и ADR-0006 fs watch — только сигнал на всех ОС. Гарантию дают периодические обходы:
  - корни рантаймов — обход по `stat` раз в 60 с;
  - `spool/new` — перечисление каталога раз в 5 с: потерянное уведомление задерживает `PermissionRequest` не больше чем на этот интервал;
  - событие watcher без имени файла, ошибка или закрытие watcher запускают немедленный обход и пересоздание watcher.
- `collector.fsWatch: false` выключает watch и оставляет только обходы — для файловых систем без надёжных уведомлений (например, сетевых). Интервалы настраиваются.

### Процессы и связь между ними

- Unix-сокеты не используются нигде. API демона по умолчанию слушает loopback TCP, явный `--bind` из ADR-0003 сохраняется; приёмник OTel — только loopback. CLI обращается к демону по HTTP. Схема одинакова на всех ОС.
- Демон запускается отсоединённым процессом (`detached`, `windowsHide`).
- Остановка — авторизованным `POST /api/admin/shutdown` на всех ОС: SIGTERM на Windows нет, а единый путь проще тестировать.
  - Демон завершает текущую транзакцию приёма, удаляет аренду spool и выходит. Файлы без `ack` остаются в spool.
  - Если API недоступен (демон упал или завис), `aang stop` сам удаляет аренду и сообщает состояние процесса по pid-файлу: явная остановка прекращает рост spool и без демона (ADR-0004).
  - В тестах сбой моделируется через SIGKILL, на Windows это `TerminateProcess`. Штатную остановку проверяет только shutdown через API.
- **Наблюдатель на Windows** запускается без shell (ADR-0007).
  - CLI, установленные через npm, — это шимы `.cmd`, которые Node без shell не запускает. Поэтому демон находит настоящий исполняемый файл (`claude.exe`, `codex.exe`) или запускает `node` со скриптом пакета. Если найти не удалось, backend выключается с причиной.
  - Скрипт пакета может быть обёрткой: npm-скрипт Codex запускает настоящий `codex.exe` дочерним процессом. Корень и настоящий CLI тогда — разные процессы.
  - Перечень переменных чистого окружения задаётся для каждой ОС. На Windows это `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `SystemRoot`, `TEMP`, `TMP`, `USERNAME`, системный `PATH` и маркеры.
  - Хранение авторизации CLI на Windows не проверено. Работу проверяют допуск версии (ADR-0007) и проверка D.8.
  - Рабочий каталог — `os.tmpdir()/aang-observer/empty`. На Windows он лежит внутри профиля, поэтому проверка предков на `CLAUDE.md` и `AGENTS.md` обязательна; если она не проходит, backend выключается с причиной.
- **Завершение дерева процессов.** Все запуски CLI демоном (наблюдатель, чат, допуск, пробы) завершаются по таймауту одной операцией backend на всех ОС:
  - macOS и Linux — процесс запускается лидером новой группы, по таймауту группа получает SIGKILL;
  - Windows — групп процессов нет, а `TerminateProcess` завершает только корень. Дерево завершает `%SystemRoot%\System32\taskkill.exe /PID <pid> /T /F` без shell, пока корень жив: обёртка ждёт свой дочерний процесс, поэтому дерево находится от корня;
  - слот наблюдателя или чата освобождается только после выхода корня и закрытия всех его каналов: выживший потомок держит унаследованный канал. Если этого не произошло за 10 с после завершения, backend получает `unavailable: process_stuck` до выхода процесса, и следующий вызов не запускается;
  - Job Object надёжнее: `taskkill /T` не находит потомков, чей родитель уже вышел. Но Node не даёт к нему доступа без нативного кода. Если D.8 обнаружит у CLI такие процессы, способ выносится владельцу.
- Git на Windows — Git for Windows, который нужен и самому Claude Code. Команды те же, только для чтения, с `GIT_OPTIONAL_LOCKS=0`.

### Поверхности и среды

- На Windows работают те же адаптеры: CLI обоих рантаймов, Agent SDK, Codex SDK, Claude Desktop (вкладка Code) и Codex Desktop. Desktop на Windows не проверен; ручной чек-лист владельца выполняется и на Windows.
- WSL — это среда Linux. Сессии внутри WSL наблюдает aang, установленный в WSL. aang на Windows не читает файловые системы WSL, и наоборот. При смешанной работе запускаются два демона.
- Docker на Windows запускает контейнеры Linux, это среда Linux.
- В матрице поддержки (ADR-0010) ОС — отдельное измерение ключа, а эталонные записи хранятся по ОС. Поддержка на macOS и Linux не переносится на Windows без записей и проверок на Windows, и наоборот.

### Проверка и CI

- До объявления поддержки на Windows выполняется проверка, аналогичная спайку (план, D.8):
  - форма исполнения команд hooks у обоих CLI, exec form Claude, пути с пробелами и не-ASCII символами;
  - задержка установленного hook со стороны рантайма;
  - поведение Codex при таймауте hook и ненулевом коде выхода;
  - пути и форматы транскриптов и rollout;
  - fs watch и блокировки файлов;
  - запуск наблюдателя, авторизация и допуск; дерево процессов CLI и его завершение по таймауту;
  - чек-листы Desktop.

  Эталонные сессии записываются и на Windows, отдельно от записей других ОС (ADR-0010).
- CI на GitHub Actions идёт по матрице macOS, Linux и Windows: линтер, типы, интеграционные, функциональные, контрактные и E2E-тесты. Бинарь `aang-hook` собирается и тестируется на каждой ОС.

## Последствия

- В репозитории два языка: TypeScript и Go (один небольшой компонент). В CI нужен тулчейн Go.
- Внешнее завершение обработчика и фатальная ошибка среды Go остаются возможными: событие теряется и отмечается пробелом, как при недоступном spool.
- До проверки D.8 всё, что связано с Windows, остаётся непроверенным. Отличия в исполнении hooks или данных Desktop могут потребовать правок адаптеров; ограничения выносятся владельцу (RFC §4).
- Остановка демона — через API на всех ОС, без сигналов.
- CI дороже: тесты идут на трёх ОС.

## Решения владельца

Принято владельцем 2026-10-01:

1. MVP поддерживает macOS, Linux и нативный Windows, включая Claude Desktop и Codex Desktop без WSL.
2. Обработчик hook — нативный бинарь на Go для всех ОС; это исключение из ADR-0001, ограниченное `aang-hook`.

## Вопросы владельцу

1. Права на Windows по ACL профиля пользователя без собственной настройки ACL. → принять для MVP.
