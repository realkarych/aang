# ADR-0013: Поддержка Windows

Статус: требование принято владельцем 2026-10-01 — MVP поддерживает macOS, Linux и нативный Windows, включая Claude Desktop и Codex Desktop на Windows без WSL. Технические решения ниже — предложено 2026-10-01.

## Контекст

ADR-0004 предлагал ограничить MVP macOS и Linux. Владелец решил иначе: нативный Windows входит в MVP.

Спайк проводился только на macOS, поэтому всё, что касается Windows, не проверено:

- раскладка `~/.claude` и `~/.codex`;
- способ, которым Claude Code и Codex запускают команды hooks;
- поведение fs watch и блокировок файлов;
- запуск CLI наблюдателем и хранение авторизации;
- данные обоих Desktop.

Обработчик hook из ADR-0004 написан на POSIX sh, которого на Windows нет. Обработчик на Node стартует десятки миллисекунд и не укладывается в бюджет 10 мс на событие.

## Решение

### Обработчик hook

- `aang-hook` — один нативный исполняемый файл на Go для всех платформ: macOS, Linux, Windows, архитектуры amd64 и arm64. Он заменяет sh-скрипт.
- Контракт ADR-0004 не меняется:
  - синхронный вызов с `timeout: 2` с в конфиге hooks;
  - всегда `exit 0`, пустые stdout и stderr;
  - без сети;
  - формат spool с заголовком и NUL-разделителями;
  - аренда и маркеры наблюдателя;
  - вычитывание stdin до конца.
- Срок аренды обработчик сравнивает с системным временем внутри процесса. Файл создаётся во временном каталоге spool и переименовывается в `spool/new`.
- **Почему Go:**
  - статический бинарь без рантайма;
  - запуск за миллисекунды на всех ОС;
  - кросс-компиляция без C-тулчейна (`CGO_ENABLED=0`).

  Rust сопоставим по скорости, но тулчейн тяжелее. Скомпилированные Node, Deno и Bun стартуют десятки миллисекунд. PowerShell стартует сотни миллисекунд, а `cmd` не читает stdin без искажений.
- Это исключение из ADR-0001, ограниченное одним компонентом. Правила AGENTS.md, включая запрет комментариев, действуют и для Go.
- **Бюджет** — p95 ≤ 10 мс на событие на всех трёх ОС. Он проверяется локальным бенчмарком на каждой ОС; в CI пороги взяты с запасом по ОС. Создание процесса на Windows дороже: если бюджет там не выдерживается, измеренное значение выносится владельцу, а не принимается молча.
- **Поставка:** бинари идут в npm необязательными пакетами по платформам (`aang-hook-<os>-<arch>`), как у esbuild. `aang install` копирует нужный бинарь в `<AANG_HOME>/bin/aang-hook` (`aang-hook.exe` на Windows).
- **Вызов из конфигов hooks** — по абсолютному пути с тегом регистрации. Как Claude Code и Codex исполняют команду hook на Windows (напрямую, через `cmd`, Git Bash или PowerShell), не проверено. Это выясняется проверкой Windows до установки hooks на Windows (план, D.8), и по её итогу строка команды формируется для каждой ОС.

### Пути и файлы

- Корни по умолчанию:
  - `%USERPROFILE%\.claude` или `CLAUDE_CONFIG_DIR`;
  - `%USERPROFILE%\.codex` или `CODEX_HOME`;
  - `AANG_HOME` — `%USERPROFILE%\.aang`.

  Пути строятся через `os.homedir()` и модуль `path`, а не склейкой строк.
- Кодирование `cwd` Windows (буква диска, обратные слеши) в имени каталога проекта Claude и расположение данных Desktop не проверены. Адаптер берёт пути транскриптов из payload hooks (`transcript_path`) и из обхода корней, а имя каталога проекта из `cwd` не восстанавливает.
- Идентичность файла — `fs.stat` с `bigint`: `dev` (серийный номер тома) и `ino` (индекс файла NTFS).
- Чтение файла, который держит другой процесс: Node открывает файлы с разрешением совместного доступа. Если пишущий процесс держит исключительную блокировку, чтение повторяется с паузой; затяжная неудача становится пробелом.
- Разбор строк принимает `\r\n`.
- Права: на macOS и Linux каталог `AANG_HOME` имеет права 0700. На Windows aang не меняет ACL и полагается на ACL профиля пользователя по умолчанию (доступ у пользователя, SYSTEM и администраторов).
- Пути в значениях `-c` для Codex (TOML) записываются с прямыми слешами: в обычных строках TOML обратный слеш — это экранирование.

### Наблюдение за файлами

- Рекурсивный `fs.watch` на Windows работает через `ReadDirectoryChangesW`. При переполнении буфера события теряются.
- По ADR-0004 и ADR-0006 fs watch — только сигнал. Гарантию даёт обход по `stat` раз в 60 с, и на Windows она та же.

### Процессы и связь между ними

- Unix-сокеты не используются нигде. API демона и приём OTel работают по loopback TCP (это допускает ADR-0003), CLI обращается к демону по HTTP. Схема одинакова на всех ОС.
- Демон запускается отсоединённым процессом (`detached`, `windowsHide`).
- Остановка — авторизованным `POST /api/admin/shutdown` на всех ОС: SIGTERM на Windows нет, а единый путь проще тестировать. В тестах сбой моделируется через SIGKILL, на Windows это `TerminateProcess`.
- **Наблюдатель на Windows** запускается без shell (ADR-0007).
  - CLI, установленные через npm, — это шимы `.cmd`, которые Node без shell не запускает. Поэтому демон находит настоящий исполняемый файл (`claude.exe`, `codex.exe`) или запускает `node` со скриптом пакета. Если найти не удалось, backend выключается с причиной.
  - Перечень переменных чистого окружения задаётся для каждой ОС. На Windows это `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `SystemRoot`, `TEMP`, `TMP`, `USERNAME`, системный `PATH` и маркеры.
  - Хранение авторизации CLI на Windows не проверено. Работу проверяют допуск версии (ADR-0007) и проверка D.8.
  - Рабочий каталог — `os.tmpdir()/aang-observer/empty`. На Windows он лежит внутри профиля, поэтому проверка предков на `CLAUDE.md` и `AGENTS.md` обязательна; если она не проходит, backend выключается с причиной.
- Git на Windows — Git for Windows, который нужен и самому Claude Code. Команды те же, только для чтения, с `GIT_OPTIONAL_LOCKS=0`.

### Поверхности и среды

- На Windows работают те же адаптеры: CLI обоих рантаймов, Agent SDK, Codex SDK, Claude Desktop (вкладка Code) и Codex Desktop. Desktop на Windows не проверен; ручной чек-лист владельца выполняется и на Windows.
- WSL — это среда Linux. Сессии внутри WSL наблюдает aang, установленный в WSL. aang на Windows не читает файловые системы WSL, и наоборот. При смешанной работе запускаются два демона.
- Docker на Windows запускает контейнеры Linux, это среда Linux.
- В матрице поддержки (ADR-0010) Windows — отдельная среда: поддержка на macOS и Linux не переносится на Windows без проверки.

### Проверка и CI

- До объявления поддержки на Windows выполняется проверка, аналогичная спайку (план, D.8):
  - форма исполнения команд hooks у обоих CLI;
  - пути и форматы транскриптов и rollout;
  - fs watch и блокировки файлов;
  - запуск наблюдателя, авторизация и допуск;
  - чек-листы Desktop.

  Эталонные сессии записываются и на Windows.
- CI на GitHub Actions идёт по матрице macOS, Linux и Windows: линтер, типы, интеграционные, функциональные, контрактные и E2E-тесты. Бинарь `aang-hook` собирается и тестируется на каждой ОС.

## Последствия

- В репозитории два языка: TypeScript и Go (один небольшой компонент). В CI нужен тулчейн Go.
- До проверки D.8 всё, что связано с Windows, остаётся непроверенным. Отличия в исполнении hooks или данных Desktop могут потребовать правок адаптеров; ограничения выносятся владельцу (RFC §4).
- Остановка демона через API на всех ОС; сигналы не используются.
- CI дороже: тесты идут на трёх ОС.

## Вопросы владельцу

1. Обработчик hook на Go как исключение из ADR-0001 для всех ОС. → принять: одна реализация вместо sh и отдельного варианта для Windows, при этом быстрее sh с внешними командами.
2. Права на Windows по ACL профиля пользователя без собственной настройки ACL. → принять для MVP.
