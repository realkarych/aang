# ADR-0013: Поддержка Windows

Статус: требование принято владельцем 2026-10-01 — MVP поддерживает macOS, Linux и нативный Windows без WSL. Обработчик hook на Go принят владельцем 2026-10-01. Остальные технические решения приняты владельцем 2026-10-01. Решением владельца 2026-10-02 Claude Desktop и Codex Desktop на Windows в MVP не проверяются (решение 3).

## Контекст

ADR-0004 предлагал ограничить MVP macOS и Linux. Владелец решил иначе: нативный Windows входит в MVP.

Спайк проводился только на macOS, поэтому всё, что касается Windows, не проверено:

- раскладка `~/.claude` и `~/.codex`;
- способ, которым Claude Code и Codex запускают команды hooks;
- поведение fs watch и блокировок файлов;
- запуск CLI наблюдателем и хранение авторизации;
- данные обоих Desktop.

Обработчик hook из ADR-0004 написан на POSIX sh, которого на Windows нет. Обработчик на Node стартует десятки миллисекунд и не укладывается в бюджет 10 мс на событие.

## Решение

### Обработчик hook

- `aang-hook` — один нативный исполняемый файл на Go для всех платформ: macOS, Linux, Windows, архитектуры amd64 и arm64. Он заменяет sh-скрипт (принято владельцем 2026-10-01).
- Контракт ADR-0004 не меняется:
  - синхронный вызов с `timeout: 2` с в конфиге hooks;
  - всегда `exit 0`, пустые stdout и stderr;
  - без сети;
  - формат spool с заголовком и NUL-разделителями;
  - аренда, маркер остановки и маркеры наблюдателя;
  - вычитывание stdin до конца.
- Срок аренды обработчик сравнивает с системным временем внутри процесса. Файл создаётся во временном каталоге spool и переименовывается в `spool/new`.
- **`exit 0` на Go** обеспечивает сам бинарь:
  - ожидаемые ошибки обрабатываются без вывода;
  - аргументы разбираются без завершающего парсера: `flag` с `ExitOnError` завершает процесс с кодом 2. Неверные или отсутствующие аргументы — выход без записи;
  - паника перехватывается на верхнем уровне (`recover`) и завершается `exit 0` без вывода: необработанная паника Go даёт код 2;
  - stdin копируется в файл потоком, без накопления в памяти; обработчик работает в одной горутине.
- **Пределы гарантии.** Фатальную ошибку среды Go (например, нехватку памяти) и внешнее завершение — по таймауту рантайма, ОС или пользователем — бинарь пережить не может. `timeout: 2` ограничивает ожидание решателя, но не обеспечивает успешный выход, а вычитывание stdin действует, только пока процесс жив.
  - По документации Claude отмена по таймауту и код, отличный от 2, при пустом stdout не блокируют действие. Исключение — `PreModelSwitch`: отменённый по таймауту hook блокирует смену модели, поэтому aang его не регистрирует (ADR-0004).
  - Поведение Codex при таймауте и ненулевом коде проверили D.5 (macOS, Linux) и D.8 (Windows): таймаут завершает процесс hook и действие не блокирует, `exit 1` не блокирует, `exit 2` в `PreToolUse` блокирует вызов на macOS и Linux.
- **Почему Go:**
  - статический бинарь без рантайма;
  - запуск за миллисекунды на всех ОС;
  - кросс-компиляция без C-тулчейна (`CGO_ENABLED=0`).

  Rust сопоставим по скорости, но тулчейн тяжелее. Скомпилированные Node, Deno и Bun стартуют десятки миллисекунд. PowerShell стартует сотни миллисекунд, а `cmd` не читает stdin без искажений.
- Это исключение из ADR-0001, ограниченное одним компонентом (принято владельцем 2026-10-01). Правила AGENTS.md, включая запрет комментариев, действуют и для Go.
- На Windows тот же бинарь работает и лаунчером процессов CLI — режим `aang-hook launch` (раздел «Процессы и связь между ними»). Режим выбирается первым аргументом: `launch` не является рантаймом, поэтому вызов из конфига hooks в него не попадает. Это принято владельцем 2026-10-01 и расширяет назначение исключения, но не число Go-компонентов.
- **Бюджет** — p95 ≤ 10 мс на событие на всех трёх ОС, измеренный со стороны рантайма: от запуска команды hook до выхода процесса, включая launcher (shell или прямой запуск) и передачу stdin типичного размера, в конфигурации, которую ставит `aang install`.
  - Бенчмарк самого бинаря (план, D.1) — необходимое условие и регрессионная проверка в CI, но не итоговое значение.
  - Итоговое значение даёт бенчмарк с тем же launcher, что у рантайма, и живая проверка: прирост времени серии событий в настоящем CLI с hooks aang относительно серии без них (план, D.5 для macOS и Linux, D.8 для Windows).
  - Строгий бенчмарк бинаря на Linux и Windows выполняет D.8 на раннерах GitHub Actions; на Windows ориентиром служит замер CI (решение 5).
  - Создание процесса на Windows дороже. Если итоговая задержка на какой-либо ОС превышает бюджет, измеренное значение выносится владельцу, а не принимается молча.
  - Замеры D.8 на раннере CI (ориентир для Windows, решение 5; `docs/research/windows-runtimes.md`):
    - прямой запуск `aang-hook.exe`, как в exec form Claude, — p95 18–24 мс, почти всё — создание процесса; строгий бенчмарк D.1 даёт p95 40–100 мс;
    - прирост серии Claude — 23–29 мс на событие;
    - hook Codex через PowerShell — 0,25–0,4 с на событие;
    - на Linux те же замеры — p95 2,4–3,3 мс и 3–7 мс на событие, в бюджете.

    Значения для Windows выше бюджета и вынесены владельцу.
  - Замеры D.5 установленной конфигурации на macOS и в Linux-контейнере (`docs/research/d5-plugin-delivery-live.md`): прямой запуск `aang-hook` в exec form Claude — p95 2,5–3,6 мс на macOS и 1,4 мс в Linux; команда Codex через shell учётной записи — 5,2–6,2 мс и 1,7 мс; прирост серии — 3,7–5,6 мс на событие у Claude и 4–6,4 мс у Codex на macOS. Всё в бюджете.
- **Поставка:** бинари идут в npm необязательными пакетами по платформам (`aang-hook-<os>-<arch>`), как у esbuild. `aang install` копирует нужный бинарь без изменений в `<AANG_HOME>/bin/aang-hook` (`aang-hook.exe` на Windows).
  - Обновление на месте: новый файл пишется рядом и переименовывается поверх старого.
  - На Windows занятый `.exe` нельзя перезаписать или удалить, но можно переименовать. Поэтому старый файл сначала переносится в сторону, затем новый занимает его место; старые копии удаляются позже, когда не заняты. Вызов в окне между двумя переименованиями не запустится — это потеря события, как при недоступном spool, а не блокировка.
- **Вызов из конфигов hooks** — по абсолютному пути с тегом регистрации и абсолютным путём spool.
  - Claude вызывает `aang-hook` в exec form: `command` — абсолютный путь, аргументы — в `args`. Без `args` Claude передаёт команду shell: `sh -c` на macOS и Linux, Git Bash или PowerShell на Windows, и запуск shell на Windows сам превышает бюджет. Как поведёт себя версия без exec form, не гарантируется: она может отбросить `args`, передать `command` shell, где абсолютный путь с пробелами распадётся на слова, или отвергнуть конфиг. Поэтому exec form проверяется контрактным тестом установки на версиях матрицы, и версия, на которой он не проходит, не считается поддержанной (ADR-0010).
  - Claude на Windows в exec form запускает `aang-hook.exe` напрямую (D.8). Без exec form он передаёт команду Git Bash: два лишних процесса и ещё 35–60 мс на событие.
  - Codex исполняет команду hook только через shell: формы с аргументами у hooks Codex нет (D.8). На Windows это PowerShell — `pwsh.exe -NoProfile -Command "<команда>"`, причём Codex находит `pwsh` и вне PATH. Строка команды формируется для каждой ОС:
    - на Windows — вызов оператором `&` с путями в одинарных кавычках: `& '<путь>\aang-hook.exe' 'codex' 'user' '<spool>'`, одинарная кавычка внутри пути удваивается. В одинарных кавычках PowerShell не раскрывает `$` и обратную кавычку. Без `&` PowerShell принимает строку в кавычках за выражение и бинарь не запускает;
    - на macOS и Linux — пути в одинарных кавычках POSIX. Codex запускает команду через shell учётной записи из базы пользователей, а не `sh` и не `$SHELL`: `/bin/zsh -c` на macOS, `/bin/bash -c` в Linux (D.5). Флага `-l` нет, но zsh на каждое событие читает `~/.zshenv` пользователя, и его время входит в задержку hook.
  - Запуск PowerShell на каждое событие стоит 0,25–0,4 с (D.8) — это в 25–40 раз выше бюджета; вынесено владельцу.
  - `pwsh -Command` переводит код выхода команды, отличный от 0 и 1, в 1. Поэтому на Windows `exit 2` hook действие Codex не блокирует. Таймаут hook Codex завершает процесс hook вместе с потомками и действие не блокирует (D.8).
  - Пути с пробелами и не-ASCII символами (профиль вида `C:\Users\Имя Фамилия`) проверены D.8 для обоих рантаймов: в exec form Claude и в форме с `&` у Codex они доходят без искажений.

### Пути и файлы

- Корни по умолчанию:
  - `%USERPROFILE%\.claude` или `CLAUDE_CONFIG_DIR`;
  - `%USERPROFILE%\.codex` или `CODEX_HOME`;
  - `AANG_HOME` — `%USERPROFILE%\.aang`.

  Пути строятся через `os.homedir()` и модуль `path`, а не склейкой строк.
- Claude находит корень по `USERPROFILE`, а Codex — по профилю учётной записи ОС: переменные `HOME` и `USERPROFILE` он не учитывает (D.8). У пользователя оба совпадают с `%USERPROFILE%`. Там, где профиль подменяется (тесты, инструменты), `CODEX_HOME` задаётся явно.
- Имя каталога проекта Claude кодирует `cwd` с потерями: каждый символ, кроме латинских букв и цифр (включая `:`, `\`, пробел и кириллицу), заменяется на `-` (D.8). Адаптер берёт пути транскриптов из payload hooks (`transcript_path`) и из обхода корней, а имя каталога проекта из `cwd` не восстанавливает. Данные Desktop на Windows не проверяются (решение 3).
- Идентичность файла — `fs.stat` с `bigint`: `dev` (серийный номер тома) и `ino` (индекс файла NTFS).
- Чтение файла, который держит другой процесс: Node открывает файлы с разрешением совместного доступа. Если пишущий процесс держит исключительную блокировку, чтение повторяется с паузой; затяжная неудача становится пробелом.
- Оба CLI и на Windows пишут JSONL с `\n` (D.8); разбор строк всё равно принимает `\r\n`.
- Права: на macOS и Linux каталог `AANG_HOME` имеет права 0700. На Windows aang не меняет ACL и полагается на ACL профиля пользователя по умолчанию (доступ у пользователя, SYSTEM и администраторов).
- Пути в значениях `-c` для Codex (TOML) записываются с прямыми слешами: в обычных строках TOML обратный слеш — это экранирование.

### Наблюдение за файлами

- Рекурсивный `fs.watch` на Windows работает через `ReadDirectoryChangesW`. При переполнении буфера события теряются, и каталог нужно перечислить заново.
- По ADR-0004 и ADR-0006 fs watch — только сигнал на всех ОС. Гарантию дают периодические обходы:
  - корни рантаймов — обход по `stat` раз в 60 с;
  - `spool/new` — перечисление каталога раз в 5 с: потерянное уведомление задерживает `PermissionRequest` не больше чем на этот интервал;
  - событие watcher без имени файла, ошибка или закрытие watcher запускают немедленный обход и пересоздание watcher.
- `collector.fsWatch: false` выключает watch и оставляет только обходы — для файловых систем без надёжных уведомлений (например, сетевых). Интервалы настраиваются.
- D.8 на настоящих CLI подтвердила: рекурсивный watch на корнях и на `spool\new` приносит события с именами файлов. Ни Claude, ни Codex не держат исключительную блокировку файла при записи. Сборщик и адаптеры разобрали файлы Windows без ошибок.

### Процессы и связь между ними

- Unix-сокеты не используются нигде. API демона по умолчанию слушает loopback TCP, явный `--bind` из ADR-0003 сохраняется; приёмник OTel — только loopback. CLI обращается к демону по HTTP. Схема одинакова на всех ОС.
- Демон запускается отсоединённым процессом (`detached`, `windowsHide`).
- Остановка — авторизованным `POST /api/admin/shutdown` на всех ОС: SIGTERM на Windows нет, а единый путь проще тестировать.
  - Первым делом `aang stop` записывает маркер намеренной остановки `spool/stopped`. Маркер хранится на диске и снимается только явным `aang start`.
  - Демон завершает текущую транзакцию приёма, удаляет аренду spool и выходит. Файлы без `ack` остаются в spool.
  - Если API недоступен (демон упал или завис), `aang stop` сам удаляет аренду и сообщает по pid-файлу, жив ли процесс. Если жив, `stop` прямо говорит, что остановка процесса не подтверждена.
  - Маркер действует сам по себе, независимо от аренды и от того, что делает демон:
    - hook при маркере ничего не пишет даже с действующей арендой (ADR-0004). Маркер и аренду он видит одним перечислением каталога spool, поэтому задержка не растёт. Продление, начатое демоном до маркера, запись не возобновит;
    - при маркере демон аренду не создаёт и не продлевает: ни по часовому продлению, ни после разбора очереди при пороге объёма. Каждое создание аренды сопровождается проверкой маркера; аренду, созданную в гонке со `stop`, демон удаляет сам;
    - живой демон, обнаружив маркер (проверка раз в минуту вместе с объёмом spool), завершается так же, как по shutdown.
  - `aang start` снимает маркер только после захвата lock хранилища, затем создаёт аренду. Если прежний демон ещё жив, lock занят: `start` отклоняется, маркер остаётся.
  - В тестах сбой моделируется через SIGKILL, на Windows это `TerminateProcess`. Штатную остановку проверяет только shutdown через API.
- **Наблюдатель на Windows** запускается без shell (ADR-0007).
  - CLI, установленные через npm, — это шимы `.cmd`, которые Node без shell не запускает. Поэтому демон находит настоящий исполняемый файл (`claude.exe`, `codex.exe`) или запускает `node` со скриптом пакета. Если найти не удалось, backend выключается с причиной.
  - Скрипт пакета может быть обёрткой: npm-скрипт Codex запускает настоящий `codex.exe` дочерним процессом. Корень и настоящий CLI тогда — разные процессы.
  - Расположение по D.8:
    - Codex из npm: шим `codex.cmd` вызывает `node <пакет>\bin\codex.js`, а тот — `codex.exe` из `@openai\codex-win32-x64\vendor\x86_64-pc-windows-msvc\bin`. Без shell `spawn('codex')` даёт `ENOENT`, `spawn('codex.cmd')` — `EINVAL`;
    - Claude из npm: шим `claude.cmd` вызывает `<пакет>\bin\claude.exe` — нативный бинарь, который туда копирует `postinstall`. Если `postinstall` не выполнен (например, политика скриптов npm), на этом месте лежит заглушка, поэтому найденный файл проверяется запуском `--version`;
    - нативный установщик Claude кладёт `claude.exe` в `%USERPROFILE%\.local\bin` без шима и в PATH текущего сеанса его не добавляет.
  - Перечень переменных чистого окружения задаётся для каждой ОС. На Windows это `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `SystemRoot`, `TEMP`, `TMP`, `USERNAME`, `PATHEXT`, системный `PATH` и маркеры. `PATHEXT` добавлена по итогу D.8: без неё Codex не запускает команды hooks, и положительная ветка допуска (ADR-0007) не проходит. Остальных переменных обоим CLI в профиле наблюдателя хватает.
  - Хранение настоящей OAuth-авторизации CLI на Windows не проверено: D.8 идёт в CI с поддельным endpoint модели (решение 4). Авторизацию на машине пользователя проверяет допуск версии (ADR-0007).
  - Рабочий каталог — `os.tmpdir()/aang-observer/empty`. На Windows он лежит внутри профиля, поэтому проверка предков на `CLAUDE.md` и `AGENTS.md` обязательна; если она не проходит, backend выключается с причиной.
- **Завершение дерева процессов.** Все запуски CLI демоном (наблюдатель, чат, допуск, пробы, `auth status`) идут через одну операцию backend на всех ОС. Вызов заканчивается выходом корня, таймаутом или отменой. После этого backend завершает всё дерево вызова, даже если корень вышел сам, и подтверждает его остановку.
  - **macOS и Linux.** CLI запускается лидером новой группы процессов (`detached`), дерево завершает SIGKILL группе.
    - Остановка подтверждена, когда `kill(-pgid, 0)` возвращает `ESRCH`. Успех или `EPERM` значат, что в группе ещё есть процессы: на macOS незабранный зомби даёт `EPERM`.
    - Единица учёта — группа. Потомок, который сам из неё вышел (`setsid`, `setpgid`), этой проверкой не виден; это предел гарантии на macOS и Linux. F.3 проверяет, что настоящие CLI в профиле наблюдателя так не делают. Если делают, способ выносится владельцу.
    - F.3 показал: Claude Code 2.1.289 из группы не выходит, а Codex 0.160.0 выходит в каждом вызове. Функция `shell_snapshot` запускает login shell учётной записи через `setsid()`, и он вместе с процессами стартовых файлов оказывается вне группы. При медленных стартовых файлах такие процессы переживают подтверждённую остановку группы. Поэтому профиль Codex-наблюдателя выключает снимок оболочки, а допуск версии проверяет, что за вызов ни один потомок не покинул группу (решение 3 по техническим вопросам; ADR-0007).
  - **Windows.** Групп процессов нет, `TerminateProcess` завершает только корень, а `taskkill /T` не находит потомков вышедшего родителя. Поэтому CLI запускается через лаунчер — режим `aang-hook launch` Go-бинаря (Job Object из Node без нативного кода недоступен):
    - лаунчер создаёт Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` без права выхода из задания (`BREAKAWAY_OK` и `SILENT_BREAKAWAY_OK` не заданы). Он запускает CLI приостановленным, включает его в задание и возобновляет. Все потомки попадают в задание с момента создания и остаются в нём, даже если их родитель вышел, а каналы они не наследуют;
    - первые n байт своего stdin (n — аргумент) лаунчер передаёт во вход CLI. Закрытие stdin после них — команда остановки: демон закрывает его по таймауту или отмене, а при выходе демона его закрывает ОС. Stdout и stderr лаунчер передаёт CLI как есть, и демон читает их напрямую;
    - по выходу корня или по команде остановки лаунчер завершает задание (`TerminateJobObject`) и ждёт, пока в нём не останется активных процессов. Только после этого он записывает файл статуса с кодом выхода корня и подтверждением остановки и выходит;
    - лаунчер, вышедший без файла статуса (завершён извне, сбой), остановку не подтвердил. Kill-on-close при этом завершает процессы задания средствами ОС, но подтвердить это некому;
    - если задание не удалось создать или назначить, CLI не запускается, и backend выключается с причиной.
    - D.8 проверила эту схему обвязкой с обоими CLI: в сессии с hooks и в профиле наблюдателя.
      - Все потомки остаются в задании, и CLI в задании работают.
      - Остановка подтверждается сразу после завершения задания.
      - Процессов, которые CLI порождали бы через службы ОС, не найдено.
      - Codex оставляет после своего выхода живые процессы `git`; их завершает задание.
      - Повторная проверка D.8 выявила задержку `Win32_ProcessStartTrace`: событие короткого `aang-hook.exe` отсутствовало через 1,569 с после остановки задания и появилось в позднем снимке. Дерево стало 47/47, активных процессов в задании уже было 0. Это дефект момента снятия трассы; выхода процесса CLI из задания не обнаружено ([доказательства и регрессия](../research/windows-runtimes.md#101-расследование-расхождения-счётчиков-в-pr--26)).
      - Стенд сохраняет исходное окно наблюдения 1,5 с, затем ждёт точного совпадения дерева с `TotalProcesses`, не дольше 10 с после остановки задания. Окончательная трасса проверяется заново после выхода обвязки; неполнота, неоднозначность дерева, ошибка трассировки или ненулевое число активных процессов дают ошибку проверки.
  - **Слот** наблюдателя или чата освобождается только при подтверждённой остановке всего дерева. Выход корня и закрытие его каналов подтверждением не считаются: потомок может не наследовать каналы или закрыть их.
  - **Остановка не подтверждена за 10 с** — слот остаётся занятым, backend получает `unavailable: process_stuck`, следующий его вызов не запускается. Состояние с причиной видно в `/api/status`, SSE и UI.
    - Позднее подтверждение освобождает слот: группа опустела или лаунчер записал статус.
    - Если подтверждать больше нечем (лаунчер исчез без статуса), состояние держится до перезапуска демона, и UI предлагает перезапуск.
- Git на Windows — Git for Windows, который нужен и самому Claude Code. Команды те же, только для чтения, с `GIT_OPTIONAL_LOCKS=0`.

### Поверхности и среды

- На Windows работают те же адаптеры: CLI обоих рантаймов, Agent SDK и Codex SDK.
- Claude Desktop (вкладка Code) и Codex Desktop на Windows в MVP не проверяются: это сужение RFC §4 (решение 3).
  - Строки матрицы поддержки (ADR-0010) для Desktop на Windows явно отмечены `unverified` — «не проверено».
  - Ручной чек-лист Desktop владелец выполняет только на macOS; на Windows чек-лист покрывает интерактивный TUI Claude.
  - Сессии Desktop на Windows, если их файлы окажутся в корнях рантаймов, обрабатываются как любые сессии строки `unverified` (ADR-0010).
- WSL — это среда Linux. Сессии внутри WSL наблюдает aang, установленный в WSL. aang на Windows не читает файловые системы WSL, и наоборот. При смешанной работе запускаются два демона.
- Docker на Windows запускает контейнеры Linux, это среда Linux.
- В матрице поддержки (ADR-0010) ОС — отдельное измерение ключа, а эталонные записи хранятся по ОС. Поддержка на macOS и Linux не переносится на Windows без записей и проверок на Windows, и наоборот.

### Проверка и CI

- До объявления поддержки на Windows выполняется проверка, аналогичная спайку (план, D.8):
  - форма исполнения команд hooks у обоих CLI, exec form Claude, пути с пробелами и не-ASCII символами;
  - задержка установленного hook со стороны рантайма;
  - поведение Codex при таймауте hook и ненулевом коде выхода;
  - пути и форматы транскриптов и rollout;
  - fs watch и блокировки файлов;
  - запуск наблюдателя и допуск; дерево процессов CLI в задании лаунчера и его завершение; процессы, которые CLI порождает вне своего дерева (через службы ОС).
- Проверка идёт в GitHub Actions на `windows-latest` (решение 4). Настоящие `claude` и `codex` ставятся на раннер и направляются на локальные поддельные endpoint модели: Claude — через `ANTHROPIC_BASE_URL`, Codex — через заглушку Responses API, как в спайке. Секреты в CI не нужны. Настоящая OAuth-авторизация на раннере не проверяется.

  Эталонные сессии записываются и на Windows, отдельно от записей других ОС (ADR-0010).
- CI на GitHub Actions идёт по матрице macOS, Linux и Windows: линтер, типы, интеграционные, функциональные, контрактные и E2E-тесты. Бинарь `aang-hook` собирается и тестируется на каждой ОС.

## Последствия

- В репозитории два языка: TypeScript и Go (один небольшой компонент). В CI нужен тулчейн Go.
- Внешнее завершение обработчика и фатальная ошибка среды Go остаются возможными: событие теряется и отмечается пробелом, как при недоступном spool.
- D.8 проверила CLI обоих рантаймов на Windows (`docs/research/windows-runtimes.md`). Непроверенными остаются Desktop (решение 3), хранение OAuth-авторизации (решение 4) и интерактивный TUI. Задержка hooks на Windows выше бюджета и вынесена владельцу.
- Остановка демона — через API на всех ОС, без сигналов. Намеренная остановка устойчива: маркер снимает только `aang start`, а живой демон, увидев его, завершается сам.
- Вызов CLI, остановку дерева которого нельзя подтвердить, занимает слот до подтверждения или перезапуска демона. Это сознательный выбор безопасности в ущерб доступности наблюдателя.
- У Go-бинаря два режима: hook на всех ОС и лаунчер на Windows.
- CI дороже: тесты идут на трёх ОС.

## Решения владельца

Принято владельцем 2026-10-01:

1. MVP поддерживает macOS, Linux и нативный Windows, включая Claude Desktop и Codex Desktop без WSL.
2. Обработчик hook — нативный бинарь на Go для всех ОС; это исключение из ADR-0001, ограниченное `aang-hook`.

Принято владельцем 2026-10-02:

3. Claude Desktop и Codex Desktop на Windows в MVP не проверяются. Это сужение RFC §4 и решения 1: в матрице поддержки строки Desktop на Windows явно отмечены «не проверено» (`unverified`).
4. D.8 выполняется в GitHub Actions на `windows-latest`: настоящие `claude` и `codex` на раннере, поддельный endpoint модели, отчёт в `docs/research/` по результатам CI. Хранение настоящей OAuth-авторизации на Windows помечается непроверенным.
5. Строгий бенчмарк `aang-hook` на нативных Linux и Windows входит в D.8; на Windows ориентир берётся из CI (решение по PR #11).

## Решения владельца по техническим вопросам

Принято владельцем 2026-10-01:

1. Права на Windows по ACL профиля пользователя без собственной настройки ACL. Принято для MVP.
2. Лаунчер на Windows — режим `aang-hook launch` того же Go-бинаря с Job Object. Альтернативы хуже: нативный модуль Node — второй нативный компонент с C/C++-тулчейном и сборкой по платформам, а `taskkill /T` не находит потомков вышедшего родителя. Режим расширяет назначение исключения ADR-0001, но не число Go-компонентов. Принято.

Принято владельцем 2026-10-04 по отчёту F.3 ([`docs/research/f3-observer-measurement.md`](../research/f3-observer-measurement.md), раздел 2, п. 1; PR #96):

3. Выход Codex из группы процессов устраняется в профиле, а не принимается как предел гарантии и не заменяется другим учётом процессов (subreaper или cgroup в Linux).
   - В профиль Codex-наблюдателя добавлен `--disable shell_snapshot` (ADR-0007, решение 9). Снимок оболочки нужен только инструментам shell, а они у наблюдателя выключены. С этим флагом F.3 не нашёл процессов вне группы и вызовов `setsid`/`setpgid` на обеих ОС; ответы и задержка те же.
   - Допуск версии (ADR-0007) на macOS и Linux проверяет каждый вызов CLI: ни один потомок не покинул группу процессов, иначе допуск не пройден. Проверка нужна, чтобы новая версия CLI с другим источником `setsid` не прошла незамеченной. Это защитная сетка допуска, а не учёт процессов: гарантию остановки дерева она не расширяет.
   - Проверка идёт снимками таблицы процессов. Процесс, который вышел из группы и исчез или потерял связь с корнем между снимками (например, после двойного `fork` с выходом промежуточного родителя), может остаться незамеченным. Ошибка снимка в любой момент вызова — провал допуска, даже если последний снимок удался.
   - На Windows проверка не нужна: задание лаунчера создаётся без права выхода, и все потомки остаются в нём.
