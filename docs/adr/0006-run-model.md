# ADR-0006: Модель прогона и связей

Статус: принято владельцем 2026-10-01; отзыв объектов наблюдения при уточнении идентичности (решение 7) принят владельцем 2026-10-03. Дополнение о `PermissionRequest` к инструменту-вопросу (раздел «Объекты наблюдения и их ключи») предложено в PR #180 и ждёт одобрения владельца.

## Контекст

RFC §6 задаёт единицу наблюдения — прогон. Связи устанавливаются по идентификаторам рантайма или явной привязке; совпадения каталога недостаточно. Выполнение, основание вывода и решение человека показываются независимо, вложенность, зависимость результата и порядок по времени различаются. Спайк (разделы 6–9, 5.2-G) показал различия рантаймов:

- fork Claude копирует историю без ссылки на родителя, fork Codex ссылается на родителя явно;
- агент сжатия Claude даёт ложный `SubagentStop`;
- teammates Claude связываются по имени;
- в code mode Codex одна JS-ячейка порождает несколько команд.

## Решение

Модель имеет два слоя. **Объекты наблюдения** строятся демоном детерминированно из фактов. **Семантическая модель** (этапы и связанное с ними) меняется только через журнал (ADR-0005), изменения предлагают наблюдатель, правила демона и пользователь.

### Факты

- Факт несёт:
  - вид;
  - `entity_key` объекта, к которому относится;
  - `speaker` — `human`, `solver`, `tool` или `runtime`; по нему вычисляется основание `claimed`;
  - признак `urgent`, который запускает наблюдателя без ожидания (ADR-0007): конец хода, финальное сообщение, завершение субагента, ошибка, план, сжатие, вопрос.
- Мышление модели (Claude `thinking`, Codex `reasoning`) фактом содержания не становится и наблюдателю не передаётся: скрытый ход рассуждений не восстанавливается (RFC §6).

### Объекты наблюдения и их ключи

Id прогона и объектов — хеш ключа; при пересборке проекций они не меняются.

| Объект | Claude | Codex |
| --- | --- | --- |
| Сессия | `sessionId` | id корневого треда (`session_meta.session_id` корня) |
| Агент | основной — `sessionId`; субагент — `agent_id`; teammate — `name@team`; служебный — по виду | id треда; guardian — тред с `thread_source: guardian_review` |
| Действие | `tool_use_id` | `call_id`; в code mode действие — вложенная команда `exec-<uuid>` (она же `tool_use_id` hooks), а JS-ячейка `custom_tool_call` — контейнер действий |
| Сообщение и промпт | `uuid` | `(thread_id, ordinal)` |
| Вопрос | `AskUserQuestion` — `tool_use_id`; `PermissionRequest`, `Notification`, `Elicitation` — имя файла spool | `AgentMessage` с `questions` — id элемента; `PermissionRequest` — имя файла spool |
| Запись usage | `message.id` | `(thread_id, response_id)` |
| Артефакт | нормализованный абсолютный путь, URL, коммит или PR | то же |

- **Сессия.**
  - Атрибуты: рантайм, поверхность (с основанием), версия, `cwd` при старте, git.
  - Запуски: `startup` и `resume`; `continue` по hooks от `resume` не отличается. Сжатие — событие сессии, а не запуск.
  - Состояние: ход идёт, ход завершён, сессия завершена или неизвестно.
- **Агент** — основной, субагент, teammate или служебный: guardian Codex, агент сжатия Claude, вспомогательная модель сводок Desktop.
- **Действие** — начало, конец, исход (`ok`, `error`, `denied`, `interrupted`, `unknown`), ссылки на вход и выход.
- **Вопрос** — явный запрос к человеку:
  - `PermissionRequest`, `AskUserQuestion`, `ExitPlanMode`, `Elicitation`;
  - `Notification` с `elicitation_*`, `agent_needs_input`;
  - Codex `AgentMessage{delivery:"async", questions}`.

  `Notification(permission_prompt)` приходит через 6 с после `PermissionRequest` и сливается с ним. `Notification(idle_prompt)` вопросом не считается: это состояние сессии «ход завершён, ждёт ввода».

  Дополнение по ревью владельца от 2026-10-08, предложено в PR #180 и ждёт одобрения владельца: `PermissionRequest` к инструменту-вопросу Claude (`AskUserQuestion`, `ExitPlanMode`) — тот же диалог, что и вопрос этого вызова, и отдельным вопросом не становится. Факт запроса относится к сессии или агенту, остаётся основанием ожидания человека и не открывает пункт `permission`. Адаптер различает такой запрос по его собственному `tool_name` и не связывает записи между собой (ADR-0011). Версия нормализатора Claude при этом не меняется: правило действует для записей, принятых после изменения, а сохранённые раньше прогоны сохраняют второй вопрос и его пункт, и `aang reparse` их не пересобирает. Убрать их переразбором можно только отзывом вопроса вместе с закрытием его пункта, а отзыв объектов, кроме агента, — отдельное решение (раздел «Уточнение идентичности и отзыв объекта»).
- **Версия артефакта** — состояние файла, URL, коммита или PR в прогоне; идентичность версии — хеш содержимого. Версия бывает:
  - **сохранённой** — содержимое лежит в хранилище blob aang или воспроизводится из коммита, доступного в репозитории;
  - **известной только по ссылке** (путь, URL, хеш без содержимого) — так и показывается и не выдаётся за сохранённую (RFC §6).
- **Удержание версий-оснований.** Когда версия артефакта становится основанием (выход этапа, карточка, критерий, проверка), демон сохраняет содержимое в хранилище blob, адресуемом по хешу (ADR-0005):
  - из payload действия, если там есть полное содержимое или патч к уже сохранённой версии. Только такая копия считается версией, которую произвело действие;
  - иначе — чтением файла. Такая копия помечается «состояние файла на момент чтения T» и не выдаётся за версию, произведённую действием: связь с действием не доказана;
  - файлы больше предела (по умолчанию 5 МБ, решение 2) сохраняются только хешем с пометкой.
- **Снимок рабочего дерева** — запись канала `snapshot`. Демон снимает её только для чтения, с `GIT_OPTIONAL_LOCKS=0`, по маскам путей контракта:
  - `git rev-parse HEAD`;
  - `git status --porcelain --ignored -- <маски>`.

  Снимок отвечает на один вопрос: чиста ли версия под масками, то есть совпадает ли всё содержимое под масками, включая игнорируемые файлы, с зафиксированным коммитом. Чистый снимок идентифицирует версию коммитом; содержимое восстанавливается из репозитория, пока коммит доступен. Нечистый снимок версию не идентифицирует, и такая версия не используется для подтверждения.

### Уточнение идентичности и отзыв объекта

- Ключ объекта может уточниться после того, как объект уже сохранён. В MVP так бывает только у teammate Claude: строки его транскрипта `subagents/agent-<id>.jsonl` и hooks, если они несут файловый `agent_id`, могут прийти раньше `meta.json` с `name` и `teamName`. До `meta.json` эти факты дают субагента с ключом `agent_id`, после — teammate с ключом `name@team`. Ключи сессий, действий и вопросов известны из первого факта и не уточняются, поэтому контракт допускает отзыв только агента; другие виды добавляются отдельным решением.
- При уточнении демон в той же транзакции приёма (ADR-0005):
  - сохраняет объект с уточнённым ключом;
  - отзывает прежний объект с указанием замены `replaced_by`;
  - пересохраняет объекты наблюдения, которые ссылались на прежний (действия, вопросы, записи usage, дочерние агенты), со ссылкой на замену;
  - перенацеливает связи модели правилом через журнал. `link.retarget` переносит конец связи на замену. `link.remove` снимает связь, если такая же связь с заменой уже есть или если id связи выводится из ключа прежнего объекта; связь замены с выводимым id добавляется обычным `link.add`.
- Отзыв — видимое изменение со своим `change_seq`. Лента изменений и событие `facts` (`removed`) сообщают потребителям, что прежний объект исчез и чем он заменён. Снимок прогона отозванных объектов не содержит.
- Замена — хранимый объект того же вида. Если отзывают саму замену, ранее отозванные объекты перенаправляются на новую замену, поэтому `replaced_by` всегда указывает на хранимый объект. Повторное сохранение отозванного объекта снимает его отзыв.
- Итог не зависит от порядка доставки. После приёма одного набора записей в любом порядке совпадают объекты наблюдения и связи модели; различаться могут только id связей, которые назначают наблюдатель и правила, а не ключ объекта.
- Журнал не переписывается: прежние изменения сохраняют ссылки на отозванный объект, а его замена видна по отзыву. Ссылку на отозванный объект в ответе наблюдателя проверка отклоняет как ссылку на отсутствующий объект (ADR-0007).

### Прогон и его границы

- Прогон создаётся корневой сессией: новой сессией, которая не является resume, субагентом или служебным тредом. Id прогона — хеш ключа корневой сессии.
- В прогон входят:
  - все запуски корневой сессии (resume и continue сохраняют её id);
  - субагенты, teammates и служебные агенты, транзитивно.
- Связи по идентификаторам рантайма:
  - субагент Claude — `meta.toolUseId` и `toolUseResult.agentId`;
  - субагент Codex — `parent_thread_id`, `thread_spawn`, `SubAgentActivity`;
  - teammate Claude — `(sessionId, meta.name, meta.teamName)` ↔ `toolUseResult` и `teams/*/config.json`;
  - уведомление о фоновом субагенте — `origin.kind`/`promptSource` транскрипта, а не разбор текста промпта.
- **Охват** решается один раз для корневой сессии по её первому `cwd` (ADR-0004) и наследуется продолжениями и агентами. Последующая смена `cwd` охват не меняет.
- **Fork Codex** (`forked_from_id`) создаёт новый прогон со связью «ответвлён от», основание — наблюдаемое событие.
- **Fork Claude** распознаётся по `SessionStart.source=fork` или по самому файлу: после открывающих строк запуска (`queue-operation`) идут записи со временем раньше этого запуска.
  - Унаследованными считаются записи до первой собственной записи запуска, время которых раньше запуска форка. Правило не зависит от наличия оригинала и порядка приёма.
  - Унаследованные записи не повторяются как новые действия и расход (ADR-0009).
  - Создаётся новый прогон со связью «общее происхождение» и перечнем видимых сессий с теми же `uuid`. Перечень пересчитывается при появлении новых сессий.
  - Непосредственный родитель не назначается; единственный кандидат показывается как предположение с основанием.
- Новая сессия после `/clear` и сессии, порождённые Desktop без проверенных метаданных, становятся отдельными прогонами без связи.
- Ложный `SubagentStop` агента сжатия (`agent_type: ""`, без `SubagentStart`, путь транскрипта не существует, рядом `PreCompact`) распознаётся как событие сжатия, а не агент.
- Пользователь может явно привязать сессию к прогону, назначить родителя форка или отвязать сессию. Привязки журналируются и отменяемы.
- **Перенос сессии между прогонами** (привязка, позднее распознавание связи субагента или форка):
  - записывается в журнал обоих прогонов;
  - факты сессии становятся необработанными в целевом прогоне (ADR-0007);
  - этапы исходного прогона, ссылающиеся на её действия, получают пометку «сессия перенесена»;
  - расход обоих прогонов пересчитывается проекцией;
  - отметки просмотра и правила вида остаются за своими прогонами.
- Совпадение каталога проекта никогда не связывает сессии.
- В MVP одна корневая сессия соответствует одному прогону; смена цели внутри сессии отражается этапами.

### Виды связей

Каждая связь хранит основание.

| Связь | Между | Источник |
| --- | --- | --- |
| вложенность | прогон ⊃ сессия ⊃ агент ⊃ действие; этап ⊃ подэтап | рантайм; подэтапы — наблюдатель |
| порождение | агент → субагент через действие | идентификаторы рантайма |
| ответвление / общее происхождение | прогон → прогон | см. выше |
| участие | агент ↔ этап, многие ко многим | наблюдатель или привязка действий к этапу |
| зависимость результата | этап B использует результат этапа A | наблюдаемая, если версия артефакта из A — вход действия в B; иначе интерпретация наблюдателя |
| порядок по времени | этапы и действия | время и порядок в файле; не означает причинности |

### Семантическая модель

- **Этап.** Поля: `id`, название, ожидаемый результат, краткая сводка, родитель, участники, привязанные действия, входы и выходы (версии артефактов), критерии, состояние по трём осям, история (создание, переименование, объединение, разделение, замена, перенос сессии).
  - Происхождение `plan` — этап взят из явного плана. Демон принимает его, только если среди оснований есть факт плана:
    - Claude — инструменты задач (`Task*`), hooks `TaskCreated`/`TaskCompleted`, `ExitPlanMode`;
    - Codex — `thread_goal_updated` и записи плана rollout.

    Кроме `thread_goal_updated`, эти записи в спайке не наблюдались. Источники плана для каждой версии определяет эталонная сессия «план» (ADR-0010); до неё разбор плана помечен как непроверенный.
  - Происхождение `inferred` — этап восстановлен наблюдателем; такие этапы помечаются.
  - Этапы создаёт только наблюдатель. До его первого ответа UI показывает факты плана в виде до смысла.
- **Перепланирование.** Заменённый этап сохраняется в состоянии `replaced` со ссылкой на замену и не удаляется.
- **Критерий.** Текст, источник (`task`, `plan`, `contract`), статус (`not_checked`, `confirmed`, `passed_unversioned`, `partial`, `failed`, `stale`, `reported_done`), свидетельства, версия, на которой он проверен.
  - `confirmed` с основанием «наблюдаемое событие» выдаётся только по контракту проверки, который связывает успешный результат с действительно проверенным коммитом. Условия:
    - контракт задаёт регулярное выражение, которое извлекает проверенный коммит из вывода проверки;
    - вывод успешной проверки его содержит;
    - коммит существует в репозитории.

    Версия — этот коммит. За то, что проверка действительно читала этот коммит, отвечает контракт: например, проверка запускается в изолированной копии зафиксированного коммита (`git worktree`, чистый checkout) и печатает его хеш, или система проверки сама сообщает проверенную версию. Связь задана выводом самой проверки, поэтому `confirmed` возможен и для проверки, прочитанной бэкфиллом.
  - Во всех остальных случаях успешная проверка получает `passed_unversioned` — «проверка прошла, версия не установлена». Подтверждением это не считается. В том числе:
    - дерево под масками было чистым на одном `HEAD` до и после проверки. Такое наблюдение показывается справочной пометкой «дерево было чистым на коммите X в обоих снимках», но версию не доказывает: вход могли изменить и вернуть между снимками, а `PreToolUse` демон обрабатывает асинхронно, без точной границы начала проверки;
    - незафиксированные или игнорируемые изменения, работа вне git-репозитория.
  - fs watch — только сигнал изменений для пересчёта `stale`, а не доказательство их отсутствия.
  - После `confirmed` для коммита X демон снимает снимок по сигналу fs watch, в конце каждого хода и после перезапуска. Если `HEAD` отличается от X или дерево под масками не чистое, текущее состояние уже не та версия, что проверена, и критерий переходит в `stale` («проверено на другой версии»). Пропущенное уведомление поймает ближайший снимок.
  - Оценка достаточности, сделанная LLM, остаётся интерпретацией.
  - Без оснований сохраняется `reported_done` — «агент сообщил о завершении».
- **Контракт проверки** задаётся в `~/.aang/config.json` для отслеживаемого корня: имя, регулярное выражение по строке команды, условие успеха (код выхода), маски путей входа проверки, регулярное выражение для проверенного коммита в выводе. Без него контракт распознаёт проверки и их исход, но подтверждения не даёт. Действует для прогонов, корневой `cwd` которых лежит в этом корне.
- **Проверка** — действие, совпавшее с контрактом (основание наблюдаемое) или отмеченное наблюдателем (интерпретация). Упавшая проверка без последующего успеха той же проверки:
  - создаёт в зоне внимания пункт, который закрывается успешным повтором или снятием пользователем (ADR-0008);
  - не даёт показать этап как просто «завершено»: этап показывается как «завершено, есть упавшая проверка».
- **Карточка результата** — фрагмент финального текста агента, привязанный к этапам, с координатами в исходном сообщении. Оригинал всегда доступен.
- **Пункт внимания.** Вид (`question`, `permission`, `review_request`, `blocker`, `failed_check`), автор (`rule`, `observer`), основание, свидетельства, этап, открыт или закрыт, рекомендованный LLM приоритет. Открытие, закрытие и порядок задаёт ADR-0008.
- **Описание прогона** — цель из первого промпта (наблюдаемое) и её пересказ наблюдателем (интерпретация).

### Три независимые оси

- **Выполнение:** `planned`, `running`, `waiting` (с причиной: человек, субагент или фоновая задача, простой после ответа, неизвестно), `done`, `failed`, `cancelled`, `unknown`.
  - У действий, агентов и сессий выполнение выводится из фактов.
  - У этапа выполнение сначала вычисляет правило по привязанным действиям, агентам и известным ожиданиям:
    - есть идущее действие или агент — `running`;
    - есть активное ожидание человека в рантайме — `waiting` (человек). Это открытый запрос одобрения, `AskUserQuestion`, `Elicitation` или `ExitPlanMode` в незавершённом ходе либо `status: waiting` в реестре.

    Открытый неблокирующий вопрос (например, асинхронный вопрос Codex, запрос ревью, вопрос после конца сессии) этап в `waiting` не переводит: он отражается только на оси решения человека.

    Состояния, которые правило не выводит (`done`, `failed`, `planned`, `cancelled`), устанавливает наблюдатель. Если наблюдаемое правилом противоречит утверждению LLM (например, «завершено» при идущем действии), показывается наблюдаемое, а противоречие видно в инспекторе.
  - Свежесть источника показывается отдельно от выполнения:
    - `ok`;
    - `quiet` — нет новых событий 5 минут при незавершённом ходе (настраивается);
    - `lost` — источник потерян;
    - `hooks_inactive`.

    Молчание не переводит этап в `failed` или `waiting`.
- **Основание:** `observed`, `claimed`, `interpreted`; у интерпретации указан интерпретатор — `rule:<имя>` или `llm:<id вызова>`.
  - Основание вычисляет демон.
  - Утверждения наблюдателя получают `claimed`, если все свидетельства — факты со `speaker: solver`, и `interpreted` в остальных случаях; `observed` LLM не производит.
  - Вывод отказа по отсутствию `PostToolUse` и связь `PermissionRequest` с вызовом — это `interpreted` с правилом.
  - У `PermissionRequest` нет `tool_use_id`. Он связывается с `PreToolUse` той же сессии и агента без последующего `Post*` по `(tool_name, tool_input)`. Порядок разрешает только равенства; если кандидатов несколько, связь помечается неоднозначной.
- **Решение человека:** `none`, `requested`, `approved`, `rejected`, `answered` — только если это видно в исходной сессии, иначе `unknown`.
  - `codex.tool_decision` даёт решение человека с основанием `observed` только при `source: User`. `source: AutomatedReviewer` — решение служебного агента guardian, `source: Config` — политика (безопасная команда, сохранённое правило, `never`). Ни то ни другое не показывается как решение человека.
  - Claude `answers` и `ElicitationResult` дают `observed`.
  - По последующим событиям решение выводится правилом (`interpreted`) для обоих рантаймов:
    - одобрение — `Post*` или `item_completed` вызова после запроса;
    - отказ — `PostToolBatch` без `Post*` у Claude, `declined` или `turn_aborted` у Codex.
  - Если не видно ни того ни другого, решение — `unknown`.
  - У этапа решение — `requested`, пока открыт хотя бы один его вопрос, в том числе неблокирующий; иначе это последнее решение по его вопросам.

## Последствия

- Карта никогда не связывает сессии по каталогу и не придумывает родителя форка.
- До первого ответа наблюдателя UI показывает объекты наблюдения: сессии, агентов, действия, вопросы и факты плана.
- Подтверждение с наблюдаемым основанием возможно только по контракту, в котором проверка сама сообщает проверенный коммит. Пока пользователь такой контракт не настроил, успешные проверки остаются `passed_unversioned` — сознательно консервативно, без попыток вывести версию из наблюдений за деревом.
- Демон выполняет в рабочем каталоге решателя только читающие команды git без блокировок индекса и читает файлы под масками контрактов и файлы-основания.
- Хранилище растёт за счёт blob версий-оснований (ADR-0005).

## Решения владельца

Принято владельцем 2026-10-01:

1. Fork — новый прогон со связью; пользователь может объединить прогоны привязкой.
2. Принят контракт проверки с коммитом, который сообщает сама проверка. Снимки рабочего дерева используются для `stale`, версии-основания копируются в хранилище blob с пределом 5 МБ на файл (настраивается).
3. Teammates Claude связываются по имени и команде как наблюдаемая связь в пределах сессии.
4. Служебные агенты по умолчанию скрыты на карте, их расход учитывается.
5. Одна корневая сессия — один прогон в MVP.
6. Этапы создаёт только наблюдатель; факты плана видны сразу в виде до смысла.

Принято владельцем 2026-10-03:

7. При уточнении идентичности объект наблюдения может быть отозван с указанием замены (`replaced_by`). Связи и ссылки на него перенацеливаются журналируемым правилом, отзыв виден в ленте изменений по `change_seq`, итог не зависит от порядка доставки.
