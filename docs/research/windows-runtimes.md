# Проверка рантаймов на Windows (D.8)

Статус: отчёт по пункту D.8 плана (`docs/plan/mvp.md`). Это не ADR: расхождения с ADR-0013 внесены в ADR-0013, вопросы, которые решает владелец, собраны в разделе 2.
Дата: 2026-10-02. Ветка: `feat/d8-windows-ci-check`.

## 0. Область, версии, метод

Проверка идёт в GitHub Actions по решению владельца 2026-10-02 (ADR-0013, решения 3–5): настоящие `claude` и `codex` ставятся на раннер `windows-latest` и направляются на локальные поддельные endpoint модели. Секретов нет, настоящая авторизация не используется.

**Версии и среда** (прогоны workflow `Runtime check` на ветке: [1](https://github.com/realkarych/aang/actions/runs/37005795334), [2](https://github.com/realkarych/aang/actions/runs/37006364193), [3](https://github.com/realkarych/aang/actions/runs/37008157609), [4](https://github.com/realkarych/aang/actions/runs/37009527541) и прогон PR [5](https://github.com/realkarych/aang/actions/runs/37012137462) после перебазирования на `master` с адаптерами B.2 и C.4; таблицы ниже — по прогонам 2–5, прогон 1 дал только бенчмарк D.1):

- Windows 10.0.26100 x64 (раннер `windows-latest`), AMD EPYC 7763 или 9V74, защита Defender в реальном времени выключена (`RealTimeProtectionEnabled: False`);
- Claude Code 2.1.286: нативный установщик (`install.ps1 2.1.286`) и npm `@anthropic-ai/claude-code@2.1.286`;
- Codex CLI 0.159.3: npm `@openai/codex@0.159.3` — обёртка `bin/codex.js` и нативный `codex.exe` из `@openai/codex-win32-x64`;
- Node 26.10.0, `aang-hook.exe` из этой ветки, Git for Windows 2.55, PowerShell 7 (`pwsh`) и Windows PowerShell 5.1;
- контроль — тот же прогон на `ubuntu-latest`. Это не D.5: D.5 проверяет macOS и Linux локально.

**Метод.** Инструмент `tools/runtime-check` (`node tools/runtime-check/dist/main.js --out <каталог>`), workflow `.github/workflows/runtime-check.yml`. Отчёт инструмента — `report.json` в артефакте прогона.

- Модель — заглушки в процессе инструмента: Messages API для Claude (`ANTHROPIC_BASE_URL`, ключ-заглушка в `ANTHROPIC_API_KEY`) и Responses API для Codex (провайдер `aang_stub` без авторизации, как в спайке). Заглушки отвечают по сценарию: N вызовов инструмента, затем текст. Claude вызывает `Read`, Codex — `apply_patch`, чтобы сам инструмент не порождал процессов.
- Профиль — каталог `…\Users\Имя Фамилия` с пробелом и кириллицей. Внутри `.claude`, `.codex`, `.aang` (копия `aang-hook.exe` и spool с арендой) и проект `проект с пробелами`. `HOME` и `USERPROFILE` указывают на этот каталог, `CLAUDE_CONFIG_DIR` и `CODEX_HOME` заданы явно. Учётная запись Windows с таким именем не создавалась.
- Hooks Claude — плагин aang в exec form на все события, кроме `Worktree*`, `MessageDisplay` и `PreModelSwitch`, `timeout: 2`. Плагин ставится через локальный маркетплейс (`claude plugin marketplace add`, `claude plugin install`), как это будет делать D.2. Зонды подключаются отдельным плагином через `--plugin-dir`.
- Hooks Codex — `hooks.json` во временном `CODEX_HOME`; доверие — тестовым `--dangerously-bypass-hook-trust`.
- Зонд — Node-скрипт вместо обработчика. Он записывает argv, размер stdin и цепочку родительских процессов: имя и командную строку из `Win32_Process`.
- Задержка измеряется двумя способами. Первый — серия запусков `aang-hook` через тот же launcher, что у рантайма: командная строка родителя зонда воспроизводится с заменой команды зонда на команду aang. Второй — серии сессий настоящего CLI с hooks aang и без них.
- Сборщик и адаптеры aang (`@aang/collector`, `@aang/adapter-claude`, `@aang/adapter-codex`) прогоняются по файлам, которые пишут настоящие CLI.
- Дерево процессов проверяет обвязка `tools/runtime-check/assets/job-run.ps1` по схеме лаунчера D.9: Job Object с `KILL_ON_JOB_CLOSE` без права выхода из задания, запуск CLI приостановленным, назначение в задание, возобновление. Запуски процессов в системе за то же время пишет `Win32_ProcessStartTrace`.

**Обозначения:** **Э(CI)** — наблюдали в прогоне CI; **Д** — по строкам бинаря или документации.

**Ограничения:**

- модель поддельная: проверяются исполнение hooks, файлы и процессы, а не поведение модели;
- хранение настоящей OAuth-авторизации на Windows не проверено (решение 4): Claude работает с ключом заглушки, Codex — с провайдером без авторизации;
- Claude Desktop и Codex Desktop на Windows не проверялись (решение 3);
- TUI не запускался, поэтому `PermissionRequest`, `Notification` и вопросы не вызывались;
- раннер — виртуальная машина CI. Абсолютные задержки на машине пользователя будут другими; на Windows это ориентир (решение 5).

## 1. Главное

1. **Claude: exec form работает.** `claude.exe` запускает `aang-hook.exe` напрямую; путь с пробелом и кириллицей и аргументы доходят без искажений. Плагин ставится через локальный маркетплейс и включён.
2. **Codex исполняет команду hook только через PowerShell** (`pwsh.exe -NoProfile -Command`). Рабочая строка — `& '<путь>\aang-hook.exe' 'codex' 'user' '<spool>'`, обычные строки в кавычках не запускаются. Формы без shell у hooks Codex нет.
3. **Задержка выше бюджета 10 мс на Windows** (вынесено владельцу):
   - прямой запуск `aang-hook.exe` — p95 18–24 мс, почти всё — создание процесса;
   - прирост серии Claude — 23–29 мс на событие;
   - hook Codex — 0,25–0,4 с на событие, сессия Codex с hooks aang в 7–19 раз дольше.

   На Linux всё в бюджете.
4. **Сбой hook не блокирует рантайм.** Таймаут Codex завершает процесс hook с потомками. `exit 2` через `pwsh` превращается в 1 и Codex не блокирует.
5. **Файлы.**
   - Пути в payload — нативные пути Windows;
   - каталог проекта Claude кодирует `cwd` с потерями;
   - JSONL пишется с `\n`;
   - Claude берёт корень по `USERPROFILE`, Codex — по профилю учётной записи ОС;
   - fs watch работает, исключительных блокировок нет;
   - сборщик и адаптеры aang разбирают файлы Windows без `invalid`.
6. **Исполняемые файлы.** npm-шимы `claude.cmd` и `codex.cmd` без shell не запускаются (`EINVAL`). Настоящие файлы и обёртка Codex найдены (раздел 8).
7. **Допуск наблюдателя на Windows проходит** с окружением ADR-0013, дополненным `PATHEXT`: без неё Codex не запускает hooks, и положительная ветка допуска не проходит.
8. **Job Object по схеме D.9 работает с обоими CLI.** Все потомки остаются в задании, остановка подтверждается. Codex оставляет живые процессы `git` после своего выхода.

## 2. Вынесено владельцу

По ADR-0013 превышение бюджета hook выносится владельцу. Блокирующего поведения рантаймов и процессов CLI вне задания D.8 не нашла.

1. **Hooks Codex на Windows — 0,25–0,4 с на событие.** Codex запускает PowerShell на каждое событие, и настройкой это не обойти: формы без shell у hooks Codex 0.159 нет. Сессия с 20 вызовами инструмента с hooks aang занимает 12–14 с вместо 0,8–1,7 с.

   Варианты:
   - а) ставить hooks Codex на Windows как на других ОС и показывать цену в `aang install` и `status`;
   - б) на Windows не ставить hooks Codex по умолчанию. Сессии Codex тогда идут в режиме «только файлы» («ожидания одобрений не видны», ADR-0004), а hooks включаются явно;
   - в) ждать формы запуска без shell от OpenAI. До этого Codex на Windows работает по варианту а или б.

   Без решения D.3 на Windows не включается.
2. **Прямой запуск `aang-hook.exe` на Windows — p95 18–24 мс** (бенчмарк D.1 — 40–100 мс), прирост серии Claude — 23–29 мс на событие. Почти всё время — создание процесса Windows; без записи в spool p95 меньше всего на 1–3 мс, так что ускорение самого бинаря значения не изменит. Нужно решение по бюджету для Windows (решение по PR #11): принять измеренное значение как бюджет Windows или искать другой транспорт hooks.
3. **Перечень окружения наблюдателя на Windows** дополнен `PATHEXT`, иначе положительная ветка допуска Codex не проходит. Это уточнение ADR-0013 по итогу D.8, на рабочий профиль оно не влияет: hooks там выключены.

## 3. Исполнение команд hooks

### Claude

- **Exec form работает** (Э(CI)). Плагин aang с `command` — абсолютным путём `aang-hook.exe` — и `args` `["claude", "plugin", "<spool>"]` ставится через локальный маркетплейс и включён (`claude plugin list`: `enabled`). `claude.exe` запускает `aang-hook.exe` напрямую, без shell. Путь бинаря и путь spool с пробелом и кириллицей доходят без искажений: файлы появляются в `spool\new` с верным заголовком.
- За сессию с двумя вызовами `Read` доставлено 10 событий: `SessionStart`, `UserPromptSubmit`, по два `PreToolUse`, `PostToolUse`, `PostToolBatch`, `Stop`, `SessionEnd` — как на macOS и Linux.
- `CLAUDE_PLUGIN_ROOT` указывает на каталог плагина в локальном маркетплейсе (`<AANG_HOME>\claude-plugin\aang`), копии в кеш плагинов нет.
- **Без exec form** (`command` строкой без `args`) Claude запускает команду через Git Bash: `claude.exe` → `C:\Program Files\Git\bin\bash.exe -c "<команда>"` → `Git\usr\bin\bash.exe -c "<команда>"` → процесс команды. Строка с путями Windows в двойных кавычках при этом работает. Цена — два лишних процесса на событие (раздел 4).

### Codex

- **Codex исполняет команду hook через PowerShell** (Э(CI)): `codex.exe` → `"C:\Program Files\PowerShell\7\pwsh.exe" -NoProfile -Command "<команда>"`. Codex находит `pwsh` и без каталога PowerShell 7 в PATH. Что Codex запускает на машине без PowerShell 7, не проверено (вероятно, Windows PowerShell 5.1).
- **Какая строка работает.** Из шести форм с путями в профиле `Имя Фамилия` бинарь запускают только две — с оператором вызова `&`:

  | Форма | Пример | Windows | Linux |
  | --- | --- | --- | --- |
  | двойные кавычки | `"C:\…\aang-hook.exe" "codex" "user" "C:\…\spool"` | не запускается: PowerShell видит строковое выражение | работает |
  | двойные кавычки, прямые слеши | `"C:/…/aang-hook.exe" …` | не запускается | работает |
  | оператор `&`, одинарные кавычки | `& 'C:\…\aang-hook.exe' 'codex' 'user' 'C:\…\spool'` | **работает** | не запускается |
  | оператор `&`, двойные кавычки | `& "C:\…\aang-hook.exe" "codex" "user" "C:\…\spool"` | **работает** | не запускается |
  | одинарные кавычки | `'C:\…\aang-hook.exe' 'codex' …` | не запускается | работает |
  | без кавычек | `C:\…\aang-hook.exe codex user C:\…\spool` | не запускается: путь с пробелом распадается | не запускается |

  Для установки стоит брать `& '<путь>' 'codex' 'user' '<spool>'`: в одинарных кавычках PowerShell не раскрывает `$` и обратную кавычку, экранировать нужно только саму одинарную кавычку (удвоением).
- **Формы без shell у hooks Codex нет** (Д, строки бинаря 0.160.0): у `HookHandlerConfig::Command` поля `command`, `commandWindows`, `timeout`, `async`, `statusMessage`; поля аргументов нет. `commandWindows` — отдельная строка для Windows, она тоже идёт через PowerShell.
- **Код выхода.** `pwsh -Command` переводит код выхода команды, отличный от 0 и 1, в 1 (документированное поведение PowerShell). Поэтому на Windows `exit 2` из hook действие не блокирует (раздел 5).

### Контроль на Linux

Claude без exec form идёт через `sh -c`. У Codex родитель зонда — сам `codex`; это совместимо с заменой shell командой через `exec`, но снимок родителей не устанавливает исходную команду shell. Работающие формы — в таблице выше.

## 4. Задержка

Бюджет ADR-0013 — p95 ≤ 10 мс на событие со стороны рантайма. Серии запуска — 500 после 20 прогревочных, stdin — `PreToolUse.Bash.json`, окружение — из конверта плагина спайка, как в бенчмарке D.1. Defender на раннере выключен (`RealTimeProtectionEnabled: False`), поэтому на машине пользователя с включённой защитой значения, вероятно, выше.

**Задержка запуска `aang-hook`** (мс, p50 / p95 / max). Launcher воспроизведён по командам родителей зонда, кроме Codex на Linux: там измерен только бинарь с аргументами Codex, без стоимости shell.

## 5. Codex: таймаут и ненулевой код выхода hook

Hook — зонд, который выходит с заданным кодом или спит 20 с при `timeout: 2` (Э(CI), прогоны 2–5):

| Случай | Windows | Linux |
| --- | --- | --- |
| `PreToolUse`, `exit 1` | действие выполнено, сессия завершилась нормально | так же |
| `PreToolUse`, `exit 2` | **действие выполнено**: `pwsh -Command` вернул Codex код 1 | действие заблокировано (`Command blocked by PreToolUse hook`), как в спайке |
| `PreToolUse`, таймаут 2 с | процесс hook завершён (зонд, запущенный через `pwsh`, тоже), действие выполнено, сессия длиннее примерно на 2 с | так же |
| `UserPromptSubmit`, таймаут 2 с | процесс hook завершён, ход продолжился | так же |
| `Stop`, таймаут 2 с | процесс hook завершён, сессия завершилась нормально | так же |

Выводы:

- Сбой или зависание hook не блокируют Codex: при таймауте он завершает процесс hook вместе с потомком и продолжает работу.
- Для aang, который всегда выходит с кодом 0, различие в обработке `exit 2` на Windows значения не имеет.

## 6. Пути и форматы файлов

- **Пути в payload hooks** (Э(CI)) — нативные пути Windows с `\` и кириллицей без искажений: `cwd` — `D:\…\Users\Имя Фамилия\проект с пробелами`, `transcript_path` — существующий файл.
  - Claude: `<CLAUDE_CONFIG_DIR>\projects\<каталог проекта>\<sessionId>.jsonl`.
  - Codex: `<CODEX_HOME>\sessions\YYYY\MM\DD\rollout-<время>-<thread_id>.jsonl`.
- **Каталог проекта Claude.** Каждый символ `cwd`, кроме латинских букв и цифр, заменяется на `-`: двоеточие диска, `\`, `_`, пробел и кириллица. Пример: `D:\a\_temp\aang check 1790943995155\Users\Имя Фамилия\проект с пробелами` → `D--a--temp-aang-check-1790943995155-Users-------------------------------`. Правило то же, что на macOS. Восстановить `cwd` по имени нельзя; адаптер так и не делает (ADR-0013).
- **Концы строк.** И транскрипты Claude, и rollout Codex на Windows пишутся с `\n`, без `\r\n` (0 из 80 и 0 из 25 строк). Разбор `\r\n` в сборщике остаётся на случай правки файлов другими средствами.
- **Корни по умолчанию** (без `CLAUDE_CONFIG_DIR` и `CODEX_HOME`; `HOME` и `USERPROFILE` указывают на разные временные каталоги):
  - Claude пишет транскрипт и `.claude.json` в `%USERPROFILE%\.claude`, `HOME` не учитывает;
  - Codex не учитывает ни `HOME`, ни `USERPROFILE` и пишет rollout в профиль учётной записи ОС (`C:\Users\runneradmin\.codex`).

  Для пользователя оба совпадают с `%USERPROFILE%`, как в ADR-0013. Тесты и инструменты, которые подменяют профиль, должны задавать `CODEX_HOME` явно; временный HOME из T.1 так и делает.
- Реестр `<CLAUDE_CONFIG_DIR>\sessions\<pid>.json` существует во время сессии: запись с `entrypoint: aang-observer` видна у наблюдателя. После выхода процесса запись удаляется.

## 7. Наблюдение за файлами, блокировки, сборщик и адаптеры

Во время сессий Claude и Codex с hooks aang одновременно работали (Э(CI)):

- сборщик aang (`createCollector`, `fsWatch: true`) на `<CLAUDE_CONFIG_DIR>`, `<CODEX_HOME>` и spool;
- отдельные `fs.watch` с `recursive: true` на `projects`, `sessions` и `spool\new`;
- чтение всех `*.jsonl` каждые 50 мс.

Результаты:

- **Блокировки.** 730–840 чтений файлов за прогон, в которые CLI в это время пишут, — ни одного отказа. Ни Claude, ни Codex не держат исключительную блокировку при записи.
- **Сборщик.** Все файлы spool приняты и удалены после `ack`, пробелов нет.
- **Адаптеры** (прогон 5, адаптеры `master` с B.2 и C.4). Записи разобраны без `invalid`; `unknown` — у тех же служебных типов, что на macOS и Linux.

  | транскрипт Claude | 80 | 71 | 9 |
  | hooks Claude | 13 | 13 | 0 |

## 8. Исполняемые файлы и шимы

Прогон 4: нативный установщик и npm-установка Claude, npm-установка Codex (Э(CI)).

| CLI | Как установлен | Что в PATH | Настоящий исполняемый файл |
| --- | --- | --- | --- |
| Claude | npm `@anthropic-ai/claude-code` | шим `claude.cmd` и sh-скрипт `claude` в `C:\npm\prefix`. Шим вызывает `node_modules\@anthropic-ai\claude-code\bin\claude.exe` напрямую, без `node` | `…\claude-code\bin\claude.exe` — копия нативного бинаря из `@anthropic-ai\claude-code-win32-x64\claude.exe`, её кладёт `postinstall` |
| Claude | нативный установщик (`install.ps1 2.1.286`) | ничего: установщик кладёт `claude.exe` в `%USERPROFILE%\.local\bin` и только советует добавить каталог в PATH | `%USERPROFILE%\.local\bin\claude.exe` |
| Codex | npm `@openai/codex` | шим `codex.cmd` → `node …\@openai\codex\bin\codex.js` | `…\@openai\codex\node_modules\@openai\codex-win32-x64\vendor\x86_64-pc-windows-msvc\bin\codex.exe`; `codex.js` запускает его дочерним процессом |

- Запуск из Node без shell: `spawn('claude')` и `spawn('codex')` — `ENOENT`, `spawn('…\claude.cmd')` и `spawn('…\codex.cmd')` — `EINVAL`, настоящий `.exe` и `node codex.js` — работают. Это подтверждает ADR-0013: демон ищет настоящий исполняемый файл или запускает `node` со скриптом пакета.
- Особенности установки:
  - npm на раннере предупреждает, что `postinstall` Claude Code не покрыт политикой `allowScripts`. Если `postinstall` не выполнен (`--ignore-scripts`, политика скриптов), `bin\claude.exe` остаётся заглушкой — sh-скриптом с сообщением об ошибке (Д, содержимое пакета);
  - нативный установщик, запущенный после npm-установки, убрал глобальную npm-копию Claude: `bin\claude.exe` и шимы исчезли (Э(CI), прогоны 2 и 3; в прогоне 4 порядок обратный, и обе копии на месте).

  Поиск исполняемого файла в F.2 должен проверять, что найденный `claude.exe` — настоящий бинарь, а не заглушка.
- Хранение авторизации не проверялось (решение 4). Без входа в учётную запись CLI работали только с заглушками модели.

## 9. Допуск наблюдателя

Профили наблюдателя из спайка (раздел 12) и ADR-0007 запускались из Node без shell, с настоящим исполняемым файлом и очищенным окружением ADR-0013: `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `SystemRoot`, `TEMP`, `TMP`, `USERNAME`, системный `PATH` из реестра и маркеры. Для заглушек добавлялись `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` и `CLAUDE_CONFIG_DIR` у Claude и `CODEX_HOME` с провайдером `aang_stub` в `-c` у Codex. Рабочий каталог — `os.tmpdir()\aang-observer\empty`; на раннере это `C:\Users\RUNNER~1\AppData\Local\Temp\…`, `CLAUDE.md` и `AGENTS.md` в предках нет. Результаты одинаковы в прогонах 2–5 (Э(CI)).

**Claude** — все условия допуска ADR-0007 выполнены:

- exit 0, `is_error: false`, `structured_output: {"ok": true}`;
- в `init` — `tools: ["StructuredOutput"]`, MCP-серверов нет, плагины только встроенные (`cc-plugin-agents-md`, `cc-plugin-plugin-authoring`), скиллов нет; модели передан один инструмент `StructuredOutput`;
- транскрипт не записан; запись реестра несёт `entrypoint: aang-observer`;
- контрольный hook в проектном `.claude/settings.json`: с `--setting-sources project` метка появляется, с `--setting-sources ""` — нет.

**Codex** — изоляция выполнена, допуск требует `PATHEXT`:

- каталог модели из `codex debug models --bundled`: 11 моделей, выбрана `gpt-6.1-sol`;
- exit 0, `turn.completed`, `last.json` — `{"ok":true}`; `originator: aang_observer`;
- `body.tools` нет, `input[additional_tools].tools` пуст; пробные вызовы `exec`, `spawn_agent` и `request_user_input` получили `unsupported`, в stderr есть `codex_core::tools::router: error=unsupported`;
- после `--ephemeral` rollout нет;
- контрольный hook в `hooks.json` временного `CODEX_HOME` с тестовым `--dangerously-bypass-hook-trust`:
  - с `--disable hooks` метки нет;
  - **без `--disable hooks` в окружении ADR-0013 метки тоже нет**, а с полным окружением — есть. Перебор переменных показал, что достаточно одной `PATHEXT`; `ComSpec` не нужна. Без `PATHEXT` Codex не находит, чем запустить команду hook. Перечень окружения наблюдателя на Windows дополнен `PATHEXT` (ADR-0013). С ним в прогоне 5 положительная ветка даёт метку, отрицательная — нет, и допуск проходит.

## 10. Дерево процессов в Job Object

Обвязка повторяет схему лаунчера D.9 (ADR-0013) на PowerShell с C# через `Add-Type`. Шаги:

1. Job Object с `KILL_ON_JOB_CLOSE` без `BREAKAWAY_OK`.
2. `CreateProcessW` с `CREATE_SUSPENDED` и явным блоком окружения; назначение в задание; возобновление.
3. Ожидание выхода корня; список процессов задания.
4. `TerminateJobObject` и ожидание, пока в задании не останется активных процессов.

Число процессов задания (`TotalProcesses`) сверяется с деревом, восстановленным по `Win32_ProcessStartTrace`. Таблица — прогон 4; в прогонах 3 и 5 те же выводы, у профиля наблюдателя Claude в прогоне 5 — 23 процесса (Э(CI)):

| Запуск | Корень | Процессов в задании | Дерево по трассе | Остались после выхода корня | Активных после завершения задания |
| --- | --- | --- | --- | --- | --- |
| Claude: сессия с hooks, `Read` и `Bash` | exit 0 | 90 | 90 | — | 0 |
| `codex.exe`: сессия с hooks и командой shell | exit 0 | 49 | 49 | 2 `git.exe` и `conhost.exe` | 0 |
| Codex через обёртку npm (`node codex.js`) | exit 0 | 47 | 47 | 2 `git.exe` и `conhost.exe` | 0 |
| Claude: профиль наблюдателя | exit 0 | 20 | 20 | — | 0 |
| Codex: профиль наблюдателя | exit 0 | 1 | 1 | — | 0 |

- Все потомки обоих CLI остаются в задании. Попыток выйти из задания, которые сломали бы `CreateProcess`, нет: оба CLI в задании работают, включая hooks, Git Bash, `pwsh`, `git` и `git-remote-https`.
- **Codex оставляет живых потомков после своего выхода**: два процесса `git` (`git-remote-https`) ещё работали, когда `codex.exe` уже вышел. Их завершило задание. Это подтверждает, что слот нельзя освобождать по выходу корня (ADR-0013).
- Остановка подтверждается сразу после `TerminateJobObject`: активных процессов 0.
- Вне дерева за время запусков стартовали только посторонние процессы: `WmiPrvSE.exe` и `CompatTelRunner.exe` от `svchost.exe`, `wsl.exe` от службы раннера `provjobd`, `BfeToolWin8.exe` от `WindowsAzureGuestAgent.exe` и компилятор обвязки `csc.exe`. Процессов, которые CLI порождали бы через службы ОС, не найдено.
- Состав дерева:
  - Claude в сессии запускает `bash.exe` (Git Bash, по 2 процесса на команду), `git.exe`, `reg.exe`, `where.exe`, `cmd.exe`, `conhost.exe` и сам себя (3 процесса `claude.exe`);
  - Claude в профиле наблюдателя — те же `git`, `reg`, `where`, `cmd`, без Git Bash;
  - Codex в профиле наблюдателя — ни одного потомка.

## 11. Не проверено

- Хранение настоящей OAuth-авторизации на Windows — решение владельца 4. Допуск версии (ADR-0007) проверяет авторизацию на машине пользователя.

## 12. Как воспроизвести

- В CI: workflow `Runtime check` запускается на PR, меняющих `tools/runtime-check/**`, `packages/hook/**` или сам workflow, и вручную (`workflow_dispatch`). Результат — артефакты `runtime-check-Windows` и `runtime-check-Linux` (`report.json`, `summary.md`) и сводка задания.
- Локально: `pnpm build`, затем `node tools/runtime-check/dist/main.js --out <каталог>` с `claude` и `codex` в PATH (или `--claude <путь> --codex <путь>`). Основные секции работают во временном профиле с явными `CLAUDE_CONFIG_DIR` и `CODEX_HOME`. Job Object проверяется только на Windows. Проба корней по умолчанию локально пропускается: без `CODEX_HOME` Codex использует настоящий профиль учётной записи ОС, несмотря на подмену `HOME`/`USERPROFILE`. Флаг `--disposable-profile` разрешает эту пробу только в выделенной одноразовой учётной записи или среде CI; workflow передаёт его на одноразовом раннере GitHub Actions.
