# Ранний замер наблюдателя на настоящих CLI (F.3)

Статус: отчёт по пункту F.3 плана (`docs/plan/mvp.md`). Это не ADR: решения не меняются, вопросы владельцу собраны в разделе 2.
Дата: 2026-10-04. Ветка: `research/f3-observer-measurement`.

## 0. Область, версии, метод

Пункт F.3 требует двух замеров:

- задержки и расхода обоих backend на входе спайка `samples/observer/observer-input.json`, по 10 повторов;
- дерева процессов обоих CLI в профиле наблюдателя на macOS и Linux: выходит ли потомок из группы процессов (ADR-0013).

Замер на записях R.4 остаётся за пунктом: записей ещё нет.

**Версии и среда:**

- macOS 27.0.1 (Darwin 27.0.0), Apple M4 Pro, 12 ядер, arm64; Node 26.10.0;
- Claude Code 2.1.289 из нативного установщика (`~/.local/bin/claude`), подписка (`authMethod: claude.ai`);
- `codex-cli 0.160.0` из Homebrew, вход через ChatGPT;
- Linux: образ на основе `node:26` (Debian 13, ядро 7.0.14-linuxkit, aarch64) в Docker Desktop 29.8.1 на той же машине. В нём Claude Code 2.1.289 и `@openai/codex@0.160.0` из npm и `strace` 6.13. Прогон идёт от пользователя `node`, его оболочка — `/bin/bash`. Контейнер запускается с `--init`: PID 1 — `tini`, он забирает осиротевших зомби, как init обычной системы. Без него PID 1 — `su`, зомби потомка, убитого SIGKILL группы, остаются в группе, и остановка не подтверждается (проверка стенда ниже).

Машина не была выделенной: работали другие сессии разработки, Codex Desktop и посторонние процессы `codex`. Живая серия началась сразу после сборки образа Docker: load average — 24 в начале и 4,7 в конце серии.

**Профиль.** Сценарий [`samples/observer-measurement/run.mjs`](samples/observer-measurement/run.mjs) берёт профиль из собранного `@aang/observer`, а не из копии командной строки:

- argv — `claudeArguments` и `codexArguments` (F.2, F.5). Это профиль ADR-0007: команды раздела 12 спайка, `--settings '{"crossSessionInbound":"hold"}'` у Claude и явная модель;
- окружение — `cleanEnvironment`;
- рабочий каталог — `prepareWorkspace`, то есть `<tmp>/aang-observer/empty` с проверкой предков;
- путь к CLI — `resolveCli`.

Заменены только схема и системный промпт: вместо контрактных — `observer-schema.json` и `system_prompt_override` из `observer-prompt.json` спайка. Stdin устроен как в спайке: инструкции, строка `Run marker: aang-observer-run <uuid>` с новым uuid на каждый вызов и `observer-input.json`. Это 10 событий ETL-задачи и этапы S1–S3 (`model_version: 7`), с инъекцией в выводе теста `e05` и вопросом `AskUserQuestion` в `e10`. Модели — `claude-opus-5-5` и `gpt-6.1-sol` (решение 2 ADR-0007). Effort по умолчанию CLI; у `gpt-6.1-sol` в каталоге `default_reasoning_level: low`, это нижний уровень модели.

**Варианты:**

| Вариант | Отличие от рабочего профиля |
| --- | --- |
| `claude` | нет |
| `claude-low` | `--effort low` |
| `codex` | нет |
| `codex-no-snapshot` | `--disable shell_snapshot` (добавлен по итогам раздела 6) |

**Запуск** повторяет операцию F.2. Это `spawn` без shell с `detached`, то есть новая сессия и группа процессов. После выхода корня сценарий снимает таблицу процессов, посылает SIGKILL группе и ждёт `ESRCH` от `kill(-pgid, 0)`. Время вызова (wall) — от `spawn` до выхода корня. Хронология строится по моменту прихода строк stdout: `system/init`, первое `assistant` и `result` у Claude; `thread.started`, `turn.started`, `agent_message` и `turn.completed` у Codex.

**Серии:**

| Серия | Модель | Что даёт | Образец |
| --- | --- | --- | --- |
| macOS, живая | настоящая | задержка, расход, ответы, дерево процессов | [`result-macos-live.json`](samples/observer-measurement/result-macos-live.json) |
| macOS, заглушки | заглушки `tools/runtime-check` | дерево процессов, накладные расходы CLI | [`result-macos-stub.json`](samples/observer-measurement/result-macos-stub.json) |
| Linux, заглушки и `strace` | то же | дерево процессов и системные вызовы `setsid`/`setpgid` | [`result-linux-stub.json`](samples/observer-measurement/result-linux-stub.json) |
| Linux, медленный `~/.profile` | то же | последствия выхода потомка из группы (раздел 6) | [`result-linux-slow-profile.json`](samples/observer-measurement/result-linux-slow-profile.json) |
| Проверка стенда, macOS и Linux | без CLI | учёт процессов вне группы и переживших остановку | [`result-macos-check.json`](samples/observer-measurement/result-macos-check.json), [`result-linux-check.json`](samples/observer-measurement/result-linux-check.json) |

- В каждой серии 10 кругов (с медленным `~/.profile` — 5), в круге — по одному вызову каждого варианта. Вызовы идут последовательно.
- В живой серии между началами вызовов одного варианта не меньше 10 с (интервал ADR-0007); фактически его выдерживал сам круг. Серия шла 8,3 минуты.
- Перед вызовами каждая серия той же операцией запускает служебные команды backend: `--version` трижды, `claude auth status` или `codex login status`, у Codex — `debug models --bundled`.
- С заглушками `CLAUDE_CONFIG_DIR` и `CODEX_HOME` временные, остальное — тот же профиль.

**Дерево процессов.** Потомок — процесс, связанный с корнем цепочкой `ppid`, или процесс из группы корня. Для каждого записываются группа, а в Linux и сессия, и моменты первого и последнего наблюдения. Момент наблюдения — начало снимка, в котором процесс есть. Живость проверяется в трёх точках:

- при выходе корня — снимок перед SIGKILL группы;
- при подтверждении остановки — снимок сразу после `ESRCH`, его момент сохраняется (`stopSnapshotAtMs`);
- после подтверждения вообще — процесс есть хотя бы в одном снимке, начатом после `ESRCH`. Это снимок при подтверждении, фоновые снимки до закрытия stdout/stderr корня (не дольше 5 с) и последний снимок после закрытия. Такой процесс считается пережившим остановку (`seenAfterStop`), даже если потом завершился сам.

Снимки:

- macOS — `ps -A` (pid, ppid, pgid, stat, lstart, comm) подряд с паузой 5 мс. Один снимок занимает около 25 мс, поэтому процесс короче ~30 мс можно пропустить;
- Linux — `/proc/<pid>/stat` каждые 5 мс и `strace -f` на `execve`, `setsid`, `setpgid` и `clone*`. Корень группы — сам `strace`, CLI — его потомок. Вызов `setsid`/`setpgid` до `exec` приписывается программе родителя.

**Проверка стенда.** `--mode check` прогоняет ту же операцию запуска на настоящих процессах `node`. Корень выходит через 150 мс, оставив потомка на 1,2 с. Сценарии:

- потомок вне группы (`detached`, то есть `setsid`) держит унаследованные stdout/stderr — ожидается 1 процесс вне группы и 1 переживший остановку;
- потомок вне группы без общих каналов (`stdio: 'ignore'`) — то же;
- потомок в группе держит каналы — 0 и 0: его завершает SIGKILL группы.

На обеих ОС все три сценария дают ожидаемое, в Linux — в контейнере с `--init` (образцы `result-macos-check.json` и `result-linux-check.json`). В первом сценарии каналы закрываются только с выходом потомка, через 1,1 с после подтверждения остановки. Потомок есть и в снимке при подтверждении, и в фоновых снимках до своего выхода, и засчитывается как переживший.

**Проверка ответов.** Ответ проверяется по схеме спайка собственным валидатором её строгого подмножества. Дальше сверяются:

- `base_model_version == 7`;
- все id событий — из порции;
- вопрос `e10` вынесен как `needs_human_input`;
- инъекция `e05` вынесена во внимание;
- файл `INJECTED.txt` не появился.

**Профиль пользователя (живая серия).** До и после серии снимаются:

- sha256 `~/.claude/settings.json`, `settings.local.json` (его нет), `~/.codex/config.toml` и `hooks.json`;
- только `stat` у `~/.codex/auth.json` и `~/.claude/.credentials.json` — их содержимое не читалось.

После серии ищутся следы наблюдателя:

- транскрипты Claude с id сессий наблюдателя;
- каталоги проектов для рабочего каталога наблюдателя;
- упоминания рабочего каталога в `~/.claude.json`;
- rollout и снимки оболочки Codex с id тредов наблюдателя.

Сами id в образцы не попадают.

**Обезличивание.** Временные пути заменены на `<work>` и `<tmp>`, домашний каталог — на `~`, имя хоста — на `<host>`. Id сессий и тредов, сырые потоки и stderr в образцы не пишутся. Имена процессов — только базовые имена исполняемых файлов.

**Обозначения:** **Э** — наблюдали в прогоне; **О** — оценка по замеру и правилам ADR-0007.

**Ограничения:**

- 10 повторов на вариант: p95 по ближайшему рангу совпадает с максимумом, это оценка хвоста, а не устойчивый перцентиль;
- вход — синтетическая порция спайка на 10 событий (около 1,5 тыс. токенов у Codex), а не рабочий вход с контрактными промптом и схемой и пределом около 24 тыс. токенов (F.7b). Задержка и расход на рабочих порциях будут больше; это задача замера на R.4 и Q.2;
- параллельные вызовы (общий параллелизм 2), дозапросы `needs` и упор в лимиты подписки не измерялись;
- в Linux модель — заглушка: авторизация CLI в контейнер не переносилась. Дерево процессов профиля от ответа модели не зависит: инструментов у наблюдателя нет, а путь авторизации на macOS проверен живой серией;
- на macOS нет `strace`, а `dtrace` без отключения SIP недоступен. Выход из группы там виден только по `pgid` в снимках: процесс, который вышел из группы и завершился быстрее снимка, может остаться незамеченным;
- служебные базы Codex (`logs_2.sqlite` и другие) в `~/.codex` не анализировались: D.6 показал, что Codex пишет туда логи при любом запуске.

## 1. Главное

1. **Все 40 живых вызовов успешны** (Э). Все завершились с exit 0. Ответ каждого прошёл схему, `base_model_version` совпал, все id событий взяты из порции, вопрос `e10` вынесен как `needs_human_input`. Инъекцию `e05` все 40 вынесли во внимание: 39 — как `risk`, один ответ Codex — только как `failure`. Файл `INJECTED.txt` не появился. Рабочий профиль Claude на 2.1.289 даёт в `init` то же, что в D.8:
   - `tools: ["StructuredOutput"]`;
   - пустые MCP и скиллы;
   - встроенные плагины `cc-plugin-agents-md` и `cc-plugin-plugin-authoring`.

   Codex получал пустой каталог инструментов (`additional_tools` пуст, проверено на заглушке), строк `error=unsupported` нет.
2. **Задержка вызова** (Э, wall от запуска до выхода корня, секунды):

   | Вариант | min | p50 | p90 | p95 (= max) | среднее |
   | --- | --- | --- | --- | --- | --- |
   | `claude` | 8,18 | 8,82 | 9,67 | 12,97 | 9,37 |
   | `claude-low` | 6,25 | 6,56 | 8,31 | 10,94 | 7,22 |
   | `codex` | 13,94 | 14,63 | 18,62 | 18,96 | 16,15 |
   | `codex-no-snapshot` | 13,90 | 15,16 | 18,42 | 18,58 | 16,38 |

   Единичные замеры спайка — 8,6–9,0 с у Claude и 42 с у Codex (0.159.2). 42 с у Codex 0.160.0 не повторились: максимум серии — 19,0 с.
3. **Оценка свежести** (О, раздел 4). По правилам порций ADR-0007 смысловое обновление после одиночного факта приходит за 5 с таймера плюс вызов: p95 — 18,0 с у Claude и 24,0 с у Codex. При непрерывной активности факт ждёт ещё и текущий вызов прогона: p95 — 19,7 с у Claude и 32,7 с у Codex. Ориентир 30 с Claude выдерживает в обоих режимах, Codex — только при редких фактах.
4. **Расход** (Э, раздел 5). Вызов Claude — около 6,7 тыс. токенов по всем моделям. Основная модель — около 3,4 тыс. токенов входа (2,6 тыс. записи в кэш и 0,8 тыс. чтения) и 830 вывода. Ещё 2,45 тыс. токенов входа без кэша и 20 вывода — дополнительный запрос к `claude-haiku-4-5`, который `claude -p` делает в каждом вызове. Это 37 % токенов вызова и 7 % его стоимости. В `result.usage` этот запрос не входит, он есть только в `modelUsage`. По прайсу вызов стоит $0,040, с `--effort low` — $0,034. Вызов Codex — 1,5 тыс. токенов входа без кэша и 415 вывода, reasoning почти нулевой; стоимости CLI не сообщает.
5. **Claude из группы не выходит** (Э, обе ОС). Его потомки — `git`, `security` (keychain), `bash`, `sh`, `ps` и сам `claude`, все в группе корня. В Linux `strace` не видит ни одного `setsid` или `setpgid`.
6. **Codex выходит из группы в каждом вызове** (Э, обе ОС, раздел 6). Функция `shell_snapshot` включена по умолчанию, и профиль наблюдателя её не выключает. Она запускает оболочку учётной записи как login shell через `setsid()`: в Linux — по два `setsid` в каждом из 10 вызовов Codex, на macOS — процессы вне группы в 19 из 20 вызовов живой серии и серии на заглушках. Оболочка исполняет стартовые файлы пользователя, и их процессы тоже оказываются вне группы. Если стартовые файлы работают дольше вызова, процесс переживает подтверждённую остановку дерева: при `sleep 3` в `~/.profile` — в 5 из 5 вызовов. С `--disable shell_snapshot` процессов вне группы и вызовов `setsid` нет, ответы и задержка те же. **Вынесено владельцу** (раздел 2, п. 1).
7. **Служебные команды и остановка** (Э). Ни одна служебная команда не выходит из группы. На запуск они тратят:
   - `--version` — 8–14 мс;
   - `claude auth status` — 112 мс;
   - `codex login status` — 18 мс;
   - `codex debug models --bundled` — 13 мс.

   Остановка группы подтверждается во всех вызовах. На macOS — за 20–36 мс после выхода корня; почти всё это время — снимок `ps` перед SIGKILL. В Linux — за 0–1 мс.
8. **Профиль пользователя не изменился** (Э). Хеши `settings.json`, `config.toml` и `hooks.json` и `stat` файлов авторизации те же. Транскриптов Claude, каталогов проектов, упоминаний в `~/.claude.json`, rollout и снимков оболочки Codex для 20 сессий и 20 тредов наблюдателя нет.

## 2. Вынесено владельцу

1. **Codex выходит из группы процессов (ADR-0013).** ADR-0013 считает единицей учёта группу и просит F.3 проверить, что CLI в профиле наблюдателя её не покидают, а иначе вынести способ владельцу. Codex 0.160.0 покидает её в каждом вызове из-за `shell_snapshot` (раздел 6). Последствия:
   - остановка подтверждается по `ESRCH`, хотя процесс вызова ещё жив; гарантия «слот освобождается только после остановки всего дерева» на macOS и Linux для Codex не выполняется;
   - наблюдатель, чат и допуск запускают login shell пользователя с его стартовыми файлами. Это пользовательский код вне управления модели, но в процессе наблюдателя;
   - медленные стартовые файлы оставляют процессы после каждого вызова (п. 6 раздела 1).

   Варианты:
   - **а)** добавить `--disable shell_snapshot` в профиль Codex-наблюдателя (ADR-0007, `codexArguments` F.5). Проверено: в Linux нет ни одного `setsid`/`setpgid`, на обеих ОС нет процессов вне группы. Ответы так же проходят проверку, задержка та же (p50 15,2 против 14,6 с, p95 18,6 против 19,0 с). Снимок оболочки нужен только инструментам shell, а они у наблюдателя выключены. Допуск версии (F.6) можно дополнить проверкой, что за вызов ни один потомок не покинул группу: так новая версия CLI с другим источником `setsid` не пройдёт незамеченной;
   - **б)** принять как предел гарантии и показывать его в документации;
   - **в)** учитывать процессы иначе: в Linux — subreaper или cgroup, на macOS равноценного механизма без привилегий нет.

   Предложение — а). В этот PR правка не входит: она меняет профиль ADR-0007 и код F.5.
2. **Решение 1 ADR-0007: p95 для прогонов Codex.** Вызов Codex — p50 14,6 с, p95 19,0 с. По оценке раздела 4 при непрерывной активности p95 смыслового обновления около 33 с, худший случай около 38 с — выше ориентира 30 с. При редких фактах — около 24 с. Окончательная проверка — Q.2 на профиле нагрузки, но уже на малой порции Codex-наблюдатель выходит за ориентир. Решение владельца:
   - оставить Codex для прогонов Codex и принять для них ориентир около 40 с;
   - или переводить прогоны Codex на Claude-наблюдателя (`observer.backend`). Тогда данные сессий Codex уходят Anthropic, это затрагивает политику ADR-0002.

   Не проверены рычаги ускорения Codex: уровень обслуживания «Fast» из каталога модели (`service_tiers: priority`, «2x speed, increased usage») и меньший предел порции.
3. **Решение 2 ADR-0007: effort.** У Codex effort по умолчанию — уже нижний уровень (`low`). У Claude `--effort low` сокращает вызов с 8,8 до 6,6 с по p50 и с 13,0 до 10,9 с по p95, а стоимость — на 15 %. Блоков мышления при этом нет, ответы на этом входе проходят те же проверки. Качество на рабочих порциях не оценивалось. Нужно решение: закрепить для Claude `low` или оставить умолчание CLI до Q.2. Умолчание укладывается в ориентир с запасом около 10 с.
4. **Решения 3 и 4 ADR-0007: ориентир и бюджет.** Ориентир 30 с подтверждается для Claude и не подтверждается для Codex при непрерывной активности (п. 2). Интервал 10 с у Claude по умолчанию почти не ограничивает: вызов длится около 9,4 с. С `--effort low` интервал становится узким местом: вызов идёт 7,2 с, а цикл — 10 с. Верхняя граница расхода одного прогона при непрерывной активности на этой порции (раздел 5), токены — по всем моделям вызова:
   - Claude — около 350 вызовов и 2,36 млн токенов в час, из них 0,86 млн — дополнительный запрос Haiku; $14 по прайсу;
   - Codex — около 220 вызовов и 0,43 млн токенов.

   Бюджет без ограничения можно оставить до Q.3: там расход меряется на активный час с рабочими порциями.
5. **Учёт токенов Claude в F.2.** `claude -p` в каждом вызове делает дополнительный запрос без инструментов: в живой серии к `claude-haiku-4-5`, около 2,45 тыс. токенов входа без кэша и 17–28 вывода, около $0,0026. Назначение не выяснялось. `result.usage` его не содержит: во всех 20 вызовах он совпадает с записью `claude-opus-5-5` в `modelUsage`, а запись Haiku есть только в `modelUsage`. На заглушке то же: дополнительный запрос идёт к основной модели, и `modelUsage` вдвое больше `result.usage`. Запуск Claude из F.2 (`usageOf` в `packages/observer/src/claude.ts`) берёт токены из `result.usage`, а стоимость — из `total_cost_usd`. Стоимость поэтому полная, а токены на этой порции занижены на 37 %. Это касается учёта расхода (U) и бюджета на токены. Варианты: суммировать токены по `modelUsage` в одной записи `CallUsage` или хранить записи по моделям; второе меняет `contract`. В этот PR правка не входит.
6. **Для сведения.**
   - Встроенные плагины Claude 2.1.289 — `cc-plugin-agents-md` и `cc-plugin-plugin-authoring`, как в D.8 и в тестах матрицы. На 2.1.286 спайк видел `cc-plugin-telemetry` вместо второго. Список встроенных компонентов матрицы меняется между версиями, и без него F.2 отклонит результат как нарушение изоляции.

## 4. Оценка свежести (вопрос 3)

Оценка складывает задержку из правил ADR-0007 и измеренных вызовов. Правила: один вызов на прогон, не чаще раза в 10 с, таймер порции 5 с. Для каждой пары «предыдущий вызов, свой вызов» из серии факт приходит в случайный момент цикла предыдущего вызова. Цикл — время до подтверждённой остановки, но не меньше 10 с. Дальше факт ждёт конца цикла и свой вызов. Расчёт — `freshnessEstimate` в образце.

| Вариант | одиночный факт: 5 с + вызов, p95 | срочный факт в простое, p95 | непрерывная активность, p95 | худший случай |
| --- | --- | --- | --- | --- |
| `claude` | 18,0 | 13,0 | 19,7 | 26,0 |
| `claude-low` | 15,9 | 10,9 | 17,3 | 21,9 |
| `codex` | 24,0 | 19,0 | 32,7 | 37,9 |
| `codex-no-snapshot` | 23,6 | 18,6 | 33,0 | 37,2 |

Не учтены сборка порции, проверка и применение ответа, дозапрос `needs` (ещё один вызов), очередь при трёх и более активных прогонах (общий параллелизм 2) и рост порции. Поэтому это нижняя оценка. Приёмочный замер — Q.2 (`tools/freshness`) на зафиксированном профиле нагрузки.

## 5. Расход (вопрос 4)

**На вызов** (Э, среднее по 10, min–max). Токены Claude взяты из `modelUsage` по каждой модели, «всего» — их сумма без `result.usage`, иначе основная модель считалась бы дважды. У Codex `input_tokens` уже включает кэшированные, «всего» — вход и вывод.

| | вызов | 2 452 | 2 510 / 939 | 590 | 6 491, 6 384–6 643 | 0,0342, 0,0321–0,0372 |
| `codex` | `gpt-6.1-sol` | 1 531 (кэш 0) | — | 413, 350–487 (reasoning 0) | 1 944, 1 881–2 017 | — |

В рабочем режиме так же: системный промпт постоянный, порция новая. В первом вызове серии кэш был пуст: 3 448 токенов записи и 0 чтения.
- Дополнительный запрос Haiku кэш не использует: около 2,45 тыс. токенов входа в каждом вызове. Это 37 % токенов вызова Claude и 7 % его стоимости (раздел 2, п. 5).

- Стоимость Claude по прайсу — клиентская оценка CLI (`total_cost_usd`). При подписке расход идёт из лимитов: `five_hour.utilization` за серию сменилась с 0,01 на 0,03, `seven_day` — с 0,30 на 0,31. Параллельно работали другие сессии, так что это верхняя граница вклада 20 вызовов.

## 6. Дерево процессов

**Claude** (Э). Все потомки в группе корня на обеих ОС:

| ОС, серия | Потомки | Вне группы | `setsid`/`setpgid` |
| --- | --- | --- | --- |
| macOS, живая (20 вызовов) | `git`, `security`, `bash`, `sh`, `ps`, `claude` (сам себя) | 0 | — |
| macOS, заглушки (10) | `git`, `claude` (сам себя) | 0 | — |
| Linux, заглушки (10) | `git`, `claude.exe` (сам себя) | 0 | 0 |

`security` — чтение OAuth из keychain; на заглушке с ключом его нет. Служебные `--version` и `auth status` потомков вне группы тоже не дают.

**Codex** (Э):

| ОС, серия | Вызовов с процессами вне группы | `setsid` на вызов | Вызовов, где процесс вне группы жив при выходе корня | Вызовов с процессом, пережившим подтверждённую остановку |
| --- | --- | --- | --- | --- |
| macOS, живая | 10 из 10 | — | 0 из 10 | 0 из 10 |
| macOS, заглушки | 9 из 10 | — | 9 из 10 | 0 из 10 |
| Linux, заглушки и `strace` | 10 из 10 | 2 | 0 из 10 | 0 из 10 |
| Linux, `sleep 3` в `~/.profile` | 5 из 5 | — | 5 из 5 | 5 из 5 |
| `codex-no-snapshot`, все серии | 0 | 0 | 0 | 0 |

Пережившим считается процесс, который есть хотя бы в одном снимке, начатом после подтверждения остановки (раздел 0). В Linux с `strace` корень группы — сам `strace`: он выходит только после всех трассируемых процессов, поэтому при его выходе процессов вне группы уже нет.

- **Источник.** `strace` в Linux: каждый вызов `codex exec` дважды делает `clone(CLONE_VM|CLONE_VFORK)`, и потомок до `exec` вызывает `setsid()`. Потомок становится лидером новой сессии и группы, а затем исполняет `/bin/bash -lc '…'` (создание снимка) и `/bin/bash -c 'set -e; . "<CODEX_HOME>/shell_snapshots/…"'` (проверка снимка). Login shell читает `/etc/profile` и `~/.profile` и запускает `id`, `run-parts`, `awk`, `sed`, `wc`, `tr` — все вне группы `codex`.
- **macOS.** Оболочка учётной записи — `zsh`, она вне группы в каждом вызове. Системные и пользовательские стартовые файлы на машине владельца запускают `path_helper`, `git`, `go`, `bash`, `who`, `dirname`. Оболочка завершается не позже 0,3 с с начала вызова. В живой серии вызов длится 14–19 с, и к выходу корня она уже завершена. В вызовах на заглушке (36–106 мс) Codex выходит раньше оболочки в 9 из 10 случаев: снимок он не ждёт. Через 24–27 мс, в снимке при подтверждении остановки, её процессов уже нет. В десятом вызове снимки процессов вне группы не застали (раздел 0, ограничения).
- **Последствие.** В серии с `sleep 3` в `~/.profile` (контейнер, пользователь `node`) каждый успешный вызов Codex завершается за 50–91 мс. Группа сразу пуста, остановка подтверждена `ESRCH`, а `sleep` из login shell ещё жив и есть в снимке при подтверждении. Обычный вызов слот освободил бы, хотя процесс вызова продолжает работу. Так же пережил бы SIGKILL группы по таймауту и отмене процесс, запущенный стартовыми файлами пользователя.
- **`--disable shell_snapshot`.** На macOS у Codex потомков нет. В Linux это только `getconf` и, при npm-обёртке, сам `codex` под `node`. Все в группе, `setsid` нет. Снимок оболочки в `~/.codex/shell_snapshots` для тредов наблюдателя не остаётся и с включённой функцией: Codex удаляет его при выходе.

Остальные пути профиля с `strace` проверены там же: `--version`, `login status` и `debug models --bundled` порождают только сам `codex` под `node`-обёрткой npm. Такая обёртка запускает настоящий CLI дочерним процессом в той же группе.

## 9. Как воспроизвести

```sh
pnpm build
D=docs/research/samples/observer-measurement
node $D/run.mjs --mode check --out $D/result-macos-check.json
node $D/run.mjs --mode live --runs 10 --variants claude,codex,claude-low,codex-no-snapshot --out $D/result-macos-live.json
node $D/run.mjs --mode stub --runs 10 --variants claude,codex,codex-no-snapshot --interval-ms 0 --out $D/result-macos-stub.json
```

Linux — тот же сценарий в образце с `strace` и CLI из npm:

```sh
mkdir -p /tmp/aang-f3-image && cat > /tmp/aang-f3-image/Dockerfile <<'EOF'
FROM node:26
RUN apt-get update -qq && DEBIAN_FRONTEND=noninteractive apt-get install -y -qq strace procps >/dev/null && rm -rf /var/lib/apt/lists/*
RUN npm install --global --silent --allow-scripts=@anthropic-ai/claude-code @anthropic-ai/claude-code@2.1.289 @openai/codex@0.160.0
EOF
docker build -q -t aang-f3-linux:local /tmp/aang-f3-image
docker run --rm --init -v "$PWD:/repo:ro" aang-f3-linux:local su node -s /bin/bash -c \
  "cd /home/node && node /repo/$D/run.mjs --mode check --out /tmp/r.json >&2 && cat /tmp/r.json" > $D/result-linux-check.json
docker run --rm --init --cap-add=SYS_PTRACE -v "$PWD:/repo:ro" aang-f3-linux:local su node -s /bin/bash -c \
  "cd /home/node && node /repo/$D/run.mjs --mode stub --runs 10 --variants claude,codex,codex-no-snapshot --interval-ms 0 --strace /usr/bin/strace --out /tmp/r.json >&2 && cat /tmp/r.json" > $D/result-linux-stub.json
docker run --rm --init -v "$PWD:/repo:ro" aang-f3-linux:local bash -c "printf 'sleep 3\n' > /home/node/.profile && chown node /home/node/.profile && su node -s /bin/bash -c \
  'cd /home/node && node /repo/$D/run.mjs --mode stub --runs 5 --variants codex,codex-no-snapshot --interval-ms 0 --out /tmp/r.json >&2 && cat /tmp/r.json'" > $D/result-linux-slow-profile.json
```

`--mode live` вызывает настоящие модели с авторизацией CLI из штатных `~/.claude` и `~/.codex`. `--mode stub` направляет оба CLI на заглушки `tools/runtime-check` и берёт временные `CLAUDE_CONFIG_DIR` и `CODEX_HOME`. `--mode check` проверяет стенд без CLI (раздел 0) и завершается с кодом 1, если сценарий не дал ожидаемого. Остальные параметры:

- `--claude`, `--codex` — путь к CLI;
- `--sample-ms` — пауза между снимками процессов;
- `--timeout-ms` — таймаут вызова вместо 90 и 150 с;
- `--summarise <файл>` — пересчитать сводку готового образца.
