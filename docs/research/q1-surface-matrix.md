# Сквозная матрица поверхностей (Q.1)

Статус: отчёт по автоматической части пункта Q.1 плана (`docs/plan/mvp.md`). Это не ADR: вопросы, которые решает владелец, собраны в разделе 6, чек-листы владельца — `docs/research/q1-owner-checklist.md` (macOS, SSH-режим Desktop, OAuth на Linux) и `docs/research/q1-owner-checklist-windows.md`.
Дата: 2026-10-07. Ветка: `feat/q1-surface-matrix`.

## 0. Область, версии, метод

Q.1 проверяет каждую поверхность сквозь весь продукт: настоящий CLI или SDK → hooks, которые ставит `aang install` → работающий демон → API и UI. Контрактный прогон (R.5a, R.5b) и E2E (H.12) проверяют то же на проигрывании эталонных записей; здесь — живой путь в каждом размещении матрицы ADR-0010, которое можно поднять без владельца.

**Версии** — те же, что у эталонных записей R.4 и в `support/matrix.json`: Claude Code 2.1.289, Claude Agent SDK 0.3.289 (движок 2.1.289), Codex CLI 0.160.0, Codex SDK 0.160.0; Node 26. Модель — заглушки `tools/record` (Messages API и Responses API), настоящая модель не вызывалась, авторизации нет.

**Метод.** Инструмент `tools/surface-check` (`tools/surface-check/README.md`), workflow `Surface matrix` (`.github/workflows/surfaces.yml`).

- Каждый сценарий каталога `tools/record` идёт в своём временном профиле, как при записи: те же хосты CLI и SDK, заглушка модели, собственные проверки сценария, его плагин и spool. Поверх этого aang подключён продуктовым путём и в порядке README: `aang install --claude` или `--codex` при остановленном демоне перед первой командой сценария, `aang start`, `aang watch <проект>`, экспорт OTel Codex в приёмник демона. Перед каждой командой сценария `aang status` доводит до конца проверку hooks демона (раздел 6, п. 6). В `reconnect` демон перезапускается в контрольной точке `daemon-restart`.
- После сценария, когда spool пуст и последовательность изменений демона не растёт 2 с, инструмент читает `/api/status`, `/api/runs` и каждый прогон, а после остановки демона — его хранилище, и требует: прогон есть; каждая сессия подписана поверхностью сценария; `/api/status` перечисляет версию `(рантайм, поверхность, ОС, размещение, версия движка)`; hooks Claude активны; `reconnect` перезапустил демон; прогоны, сессии (версия, режим поддержки, число непознанных записей), агенты, действия по инструменту и исходу, вопросы по виду, пункты внимания по виду и автору и сырые записи событий (hooks, rollout, строки `user`, `assistant`, `attachment`, `system` транскрипта) по типу и состоянию разбора совпадают со снимком контрактного прогона эталонной записи той же версии, поверхности, ОС и сценария (`support/contract`).
- Решения по вопросам и разрешения пунктов внимания сравниваются, но расхождение не валит проверку, а попадает в заметки: в контрактном прогоне они зависят от времени проигрывания (раздел 6, п. 2). После исправления контрактного прогона они сравниваются строго.
- Набор сценариев (`core`): `tools`, `subagents`, `resume`, `compaction`, `reconnect`, `approval`, `question` — те из них, что есть у поверхности на этой ОС. Это пользовательские сценарии RFC §2 в части фактов (действия, дочерние агенты, ожидания и вопросы) и столбцы матрицы: resume, сжатие, дочерние сессии, переподключение.
- Доступ к UI: вход по новой ссылке `aang open`, список прогонов и отметка просмотра (`POST /api/runs/:run/viewed`) с `Origin` той страницы, которую открыл бы браузер.

**Размещения.**

| Размещение | Где | Доступ к UI |
| --- | --- | --- |
| `local` | раннеры `ubuntu-latest`, `macos-latest`, `windows-latest` | loopback |
| `docker` | контейнер образа `aang` (`Dockerfile`) с настоящими CLI и SDK (`tools/surface-check/surface.Dockerfile`), раннер Linux | опубликованный порт 4280; другой порт 4380; адрес контейнера |
| `vm` | Ubuntu 24.04 cloud image под QEMU/KVM на раннере Linux, aang развёрнут в VM так же, как в образе | `ssh -L 4280:127.0.0.1:4280`; `ssh -L 4380:127.0.0.1:4280` |
| `desktop_ssh` (эмуляция) | та же VM, проверка запущена через SSH | `ssh -L 4280:127.0.0.1:4280` |

**Ограничения:**

- модель поддельная: проверяются доставка событий, разбор и объекты наблюдения, а не карта наблюдателя (у наблюдателя нет авторизации, демон работает без карты);
- `desktop_ssh` — эмуляция: движки Claude Desktop и Codex Desktop заменены CLI с флагами и окружением Desktop из `tools/record`. Что на самом деле ставит и запускает Desktop на удалённом хосте, проверяет только владелец; строки матрицы `desktop_ssh` эмуляция не заводит;
- VM — гостевая ОС на раннере CI, а не машина пользователя; «другая машина» для UI — сам раннер через SSH-туннель.

## 1. Главное

1. **Все поверхности, доступные без владельца, проходят сквозную проверку** нативно на трёх ОС, в Docker и в VM: Claude CLI, Claude Agent SDK, `codex exec`, Codex SDK и TUI Codex (кроме Windows). Объекты и сырые записи событий, которые показывает живой демон, совпадают с эталонными записями тех же версий. Подробности — разделы 2, 3 и 8.
2. **`aang install` в Docker-образе не работал** (`ENOENT`: образ не клал бинарь туда, где его ищет установщик). Исправлено в `Dockerfile`, smoke Docker-образа проверяет установку.
3. **Записи R.4 Claude CLI для Linux и Windows aang читает как сессии Agent SDK.** Workflow `Scenarios` задавал версию SDK переменной `CLAUDE_AGENT_SDK_VERSION`, она попала в окружение движка и hooks, а по ней адаптер определяет SDK. Рекордер теперь эту переменную не наследует, workflow её не задаёт; записи нужно перезаписать (раздел 6, п. 1).
4. **Контрактный прогон оценивает запросы разрешения Claude иначе, чем живой демон**: «ответ неизвестен, ожидание кончилось без ответа» вместо «одобрено» или «отклонено» (раздел 6, п. 2).
5. **UI через туннель или опубликованный порт с другим номером и через явный `--bind` работает только на чтение**: изменения отвечают 403 по правилу `Origin` ADR-0003. README теперь это говорит; вопрос владельцу — раздел 6, п. 3.
6. **На Windows `codex app-server` демона и Codex пользователя мешают друг другу при одновременном старте**: установка hooks Codex при работающем демоне падала по таймауту, `app-server` сценария — с ошибкой инициализации состояния (раздел 6, п. 6).
7. **Путь OAuth на Linux**: Claude входит по коду из браузера хоста без публикации портов, Codex в контейнере — только по коду устройства (раздел 4). Вход с настоящей учётной записью — чек-лист владельца.
8. **Матрица**: строки `docker` и `vm` для Linux получили проверку размещения; столбцы пользовательских сценариев заполнены по E2E 1 и 4 на эталонных записях; для Desktop и TUI Claude матрица требует чек-лист владельца (раздел 7).

- Число служебных строк транскрипта Claude (`last-prompt`) меняется от прогона к прогону; такие строки в проверке — заметки, а не ошибки (`tools/surface-check/README.md`).

| Размещение | Где | Поверхности | Сценарии | Доступ к UI |
| --- | --- | --- | --- | --- |

| `vm` | Ubuntu 24.04.5 под QEMU/KVM на `ubuntu-latest`, 3 vCPU, 8 ГБ | те же | как в разделе 2 | `ssh -L 4280:127.0.0.1:4280`: 200; `ssh -L 4380:127.0.0.1:4280`: отметка — 403 |

- **Docker.** Демон сам распознаёт контейнер: `/api/status` перечисляет версии с размещением `docker` (`claude claude_cli linux docker 2.1.289` и т. д.). `aang install` в контейнере работает после исправления `Dockerfile` (раздел 1, п. 2).
- **VM.** aang развёрнут в гостевой системе так же, как в образе: `pnpm deploy` пакета `aang`, матрица поддержки, ссылка на `aang-hook`. Размещение `vm` задаётся в конфиге (`placement`), и `/api/status` перечисляет `claude claude_cli linux vm 2.1.289`. Для Node 26 в облачном образе Ubuntu нужен `libatomic1`.
- **SSH-режим, эмуляция.** Движки, запущенные на VM через SSH с флагами и окружением Desktop, дают сессии с поверхностями `claude_desktop` и `codex_desktop` и версиями `… linux desktop_ssh …`; hooks aang из пользовательского scope и `hooks.json` работают в окружении SSH-сессии без профиля оболочки. Сравнения со снимками нет: записей движков Desktop для Linux нет.
- Строки `docker` и `vm` получили проверку размещения в `support/verification.json` по отчётам этих заданий (`placement import`, раздел 7). Эмуляция строк `desktop_ssh` не заводит.

## 4. Путь OAuth на Linux

Проверено в контейнере образа `aang` с Claude Code 2.1.289 и Codex 0.160.0 от пользователя `node`, без браузера:

- `claude auth login` пишет «Opening browser to sign in…», затем ссылку `https://claude.com/cai/oauth/authorize?…&redirect_uri=https%3A%2F%2Fplatform.claude.com%2Foauth%2Fcode%2Fcallback&…` и ждёт «Paste code here if prompted». Callback идёт на страницу Anthropic, которая показывает код, поэтому порт контейнера публиковать не нужно: ссылка открывается в браузере хоста, код вставляется в `docker exec --interactive --tty`. Тот же путь работает на VM через `ssh -t`.
- `codex login` поднимает сервер входа на `localhost:1455` внутри контейнера с `redirect_uri=http://127.0.0.1:1455/auth/callback` и сам советует `codex login --device-auth` для удалённой машины. Браузер хоста до этого сервера не дойдёт даже при опубликованном порте: сервер слушает loopback контейнера. На VM подходит туннель `ssh -L 1455:127.0.0.1:1455` или вход по коду устройства. Есть и `--with-api-key` и `--with-access-token`.
- До входа `claude auth status` — `{"loggedIn": false, …, "configDirectory": "/home/node/.claude"}`, `codex login status` — `Not logged in`, оба с кодом 1.
- Наблюдатель aang запускает CLI в чистом окружении с `HOME` пользователя (ADR-0007), поэтому берёт авторизацию из профиля по умолчанию. Вход с `CLAUDE_CONFIG_DIR` или `CODEX_HOME`, отличными от умолчания, наблюдатель не увидит.

Вход с настоящей учётной записью, расположение и права файлов авторизации и допуск наблюдателя с этой авторизацией — `docs/research/q1-owner-checklist.md`, раздел 5. README (раздел «Docker») описывает этот путь вместо пометки «не проверено».

## 5. Ограничения Desktop для решения владельца

RFC §4 требует выносить ограничения Desktop владельцу, а не исключать поверхность молча. Известные на сейчас:

1. **Desktop на Windows не проверяется** в MVP (ADR-0013, решение 3); строки `unverified` с причиной.
2. **Живой GUI обоих Desktop не проверен автоматически.** Эталонные записи и E2E Desktop идут на движках Desktop в эмуляции (R.2, R.3); ADR-0010 требует ручного чек-листа. Матрица теперь держит причину «нет чек-листа владельца» в строках Desktop (раздел 7), чек-лист D.7 владельцем ещё не выполнен.
3. **SSH-режим обоих Desktop проверен только в эмуляции.** Неизвестно, какой движок, какой версии и с какими источниками настроек Desktop запускает на удалённом хосте; от этого зависит, загрузится ли пользовательский плагин aang и как сессии будут подписаны. Записей движков Desktop для Linux нет, поэтому строки `desktop_ssh` и после чек-листа останутся без контрактных столбцов, пока такие записи не появятся (план, R.2 их не предусматривает).
4. **Codex Desktop адаптер отличает только по `originator`**; UI подписывает его «предположительно» (H.12).
5. **Сессии, порождённые Desktop** (spawn task, Dispatch, scheduled tasks), связаны с родителем только через метаданные Desktop; формат связи проверяет чек-лист D.7, шаг 3a.
6. **Версии движков Desktop обновляются самим приложением** и отстают от CLI (сейчас 2.1.286 у Claude Desktop и 0.159.2 у Codex Desktop при CLI 2.1.289 и 0.160.0). Каждая новая версия требует эталонных записей (ADR-0010, решение 1), иначе строка `unverified`.

## 6. Находки и вопросы владельцу

1. **Перезапись R.4 Claude CLI для Linux и Windows.** В записях `fixtures/sessions/claude/2.1.289/claude_cli/{linux,windows}` каждый файл spool содержит `CLAUDE_AGENT_SDK_VERSION=0.3.289`, и снимки `support/contract` показывают их сессии как `claude_sdk`. Записи macOS сделаны локально и верны. Исправлено в этом PR: рекордер не наследует `CLAUDE_AGENT_SDK_VERSION`, переменные версий workflow `Scenarios` получили префикс `AANG_`. Перезапись — отдельный PR записей (R.4); до неё строки `claude_cli` Linux и Windows не получают пользовательских сценариев, а варианты E2E Claude CLI идут только на macOS. Предлагается также инвариант контрактного прогона: поверхность сессий записи равна поверхности её манифеста; сейчас он сломал бы CI на этих двух записях.
2. **Время в контрактном прогоне.** `tools/support` проигрывает записи без `recordTime`: строки транскриптов и rollout сохраняют время записи, а hooks приходят со временем проигрывания. Запрос разрешения (`PermissionRequest`, время проигрывания) оказывается позже, чем завершение своего действия в транскрипте (время записи), и движок не связывает их: снимки показывают `permission unknown` и `ended_without_answer`. Живой демон и E2E (`recordTime: 'playback'`) видят `approved` или `rejected` и `answered`, как и было в сценарии. Это расхождение есть во всех сценариях Claude с разрешениями и в `approval` TUI Codex. Предлагается проигрывать контрактный прогон со сдвигом времени записи к проигрыванию (R.5, отдельный PR с перегенерацией снимков); до этого `tools/surface-check` записывает такие расхождения заметками. **Исправлено после Q.1:** контрактный прогон проигрывает записанную шкалу времени на одних часах, сдвинутой к проигрыванию (`tools/support/README.md`, «Record time»); снимки перегенерированы, и решения по вопросам и разрешения пунктов внимания совпадают со всеми 123 сценариями живого демона итогового прогона раздела 8, а `tools/surface-check` сравнивает их строго.
3. **`Origin` и удалённый UI.** По решению 1 ADR-0003 запросы с cookie, меняющие состояние, принимаются только с `http://127.0.0.1:P` и `http://localhost:P`, где P — порт демона. Проверено в Docker и VM: туннель или публикация с тем же портом — чтение и запись работают; другой локальный порт и адрес хоста при `--bind` — чтение работает, отметка просмотра отвечает 403. Значит, режим «явный bind на интерфейс с токеном» из того же ADR даёт UI только на чтение: отметки, снятие пунктов внимания, правила вида и чат недоступны. Нужно решение: оставить так (README уже говорит, что для полного UI нужен туннель с тем же портом) или разрешить заданные в конфиге внешние origin.
4. **Свежий профиль.** В новом контейнере или VM корней рантаймов (`~/.claude/projects`, `~/.codex/sessions`) нет до первой сессии; демон замечает их обходом раз в 60 с, и файлы первой сессии видны с этой задержкой (hooks приходят сразу). Проверка создаёт корни заранее, как у профиля, где рантайм уже запускался. README (раздел «Docker») это описывает. Решение не требуется, если задержка первой сессии допустима.
5. **TUI Claude на Linux.** ADR-0010 требует чек-лист (a)–(h) для интерактивного TUI Claude, а план (D.7, Q.1) ставит его владельцу только на macOS и Windows. Матрица требует чек-лист для строк `claude_cli` на всех ОС, поэтому строки Linux (`local`, `docker`, `vm`) остаются с этой причиной. Нужно решение: чек-лист на Linux или достаточно записей TUI в `expect` (`teammates`, `input-dialogs`).
6. **`codex app-server` параллельно на Windows.** В первом прогоне на `windows-latest` демон был запущен до `aang install --codex`, как бывает у пользователя, который ставит hooks при работающем aang. `aang install --codex` трижды из пяти упал по таймауту `codex app-server: timed out after 10000 ms`, а `codex app-server` сценария `question` Codex SDK вышел с «failed to initialize sqlite state runtime under …\.codex». В это время демон сам запускает `codex app-server` для проверки hooks (G.7): на каждое изменение `hooks.json` и `config.toml`, на всех ОС и даже без установленных hooks aang. После того как установка пошла при остановленном демоне (порядок README), а каждая команда сценария стала ждать конца проверки демона (`aang status`), сбоев нет. На Linux и macOS такого не было. Риск для пользователя Windows: Codex сам пишет `config.toml` (доверие проекту, `/hooks`), демон отвечает запуском `app-server`, и тот может столкнуться со стартующим Codex пользователя. Нужна отдельная проверка на Windows (в духе D.8) и решение: оставить, проверять реже или не запускать `app-server`, пока hooks Codex на Windows не установлены (решения владельца 2026-10-06 делают их необязательными).
7. **Пробелы каталога сценариев.** `codex_exec` на Linux и Windows без `resume` (живой сценарий `resume-compaction` записан только на macOS, ADR-0010 запрещает копировать авторизацию во временный профиль); у `codex_sdk` нет сценариев сжатия и переподключения, и столбцы `compaction` и `reconnect` у его строк `not_run`, хотя причиной это не считается (матрица требует только сценарии каталога).
