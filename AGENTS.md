# aang — правила проекта

Источник требований — `rfc.md` (одобрен). Архитектурные решения фиксируются в `docs/adr/` и вступают в силу только после одобрения владельцем проекта.

## Код

- Любые комментарии и докстринги в исходном коде запрещены — во всех языках и файлах (`//`, `/* */`, `#`, `/** */`, JSDoc, docstring). Код самодокументируется через имена, типы и структуру. Пояснения место в ADR, README и описании PR.
- Исключения — только синтаксически значимые конструкции, которые не являются пояснением: shebang, директивы инструментов там, где без них нельзя (например, `/// <reference>`), и сгенерированный код.

## Тестирование

- Массированное юнит-тестирование запрещено. Юнит-тест пишется только для действительно важного фрагмента, который нужно проверить атомарно и который нельзя адекватно покрыть E2E или интеграционным тестом.
- Цель — 100% покрытие бизнес-логики и пользовательских сценариев через E2E, функциональные и интеграционные тесты. Правило одинаково для бэкенда и фронтенда.
- Тест проверяет поведение, видимое пользователю или соседнему компоненту, а не детали реализации. Моки — только на внешних границах (LLM, сторонние процессы); собственные модули не мокаются.

## Процесс

- Каждый PR логически цельный и ревьюабельный: обычно один-два пункта плана. Жёсткого лимита строк нет. Крупная задача поставляется стеком последовательных PR.
- Реализация выполняется агентами Claude Code на Opus; каждый этап проходит кросс-ревью агентом Codex на gpt-6-astra (reasoning xhigh) до мержа.
- Ключевые архитектурные решения оформляются ADR и не реализуются до одобрения владельцем.
- Границы MVP задаёт раздел 4 `rfc.md`; изменение охвата требует отдельного решения владельца.
